CHAPTER 0 — HOW TO READ THIS DOCUMENT
================================================================================================

0.1 WHAT THIS PROJECT IS, IN ONE PARAGRAPH

    A Python program that opens Google Chrome, logs into the Order58 restaurant admin panel as a
    real human would, and creates a DEMO (test) food order by clicking through the website:
    fill the customer form, search a product, set quantity, add to cart, walk the checkout
    wizard, choose Cash, and press Submit once. It is a robot that uses the website. It is NOT a
    database script and NOT an API client.

    Gujarati: aa ek Python program chhe je Chrome kholi ne, Order58 admin panel ma manush ni
    jem click kari ne ek DEMO order banave chhe. Database ma sidha lakhvanu kaam nathi karto.

0.2 WHAT IT IS NOT

    - It is NOT part of the Knowledge Forge (Yii3/PHP) application. It shares no code, no
      database, no configuration and no dependency with it.
    - It does NOT write the order JSON files on EC2. A separate, already-existing listener does
      that (see Chapter 11).
    - It is NOT a finished product. Several advertised features are not implemented. Chapter 15
      lists exactly which.

0.3 SAFETY RULES THAT APPLY WHENEVER YOU USE THIS TOOL

    1. Only `joymeal.order58.com` over HTTPS is allowed. Anything else is refused before Chrome
       even starts.
    2. Only an explicit list of exact demo page paths may be opened. See Chapter 10.
    3. Never run a submission command without authorization from whoever owns the store data.
    4. Never delete `state/phase-b-attempt-*.json`. It is the file that stops the same order
       being submitted twice. See section 10.9.
    5. Never commit or paste the contents of `state/`. It holds a live logged-in session, which
       is as sensitive as a password.
    6. The tool never asks for, stores or types your password. You log in by hand.

0.4 VOCABULARY USED THROUGHOUT

    Source Order ID ... The template order the demo is cloned from. Here: 16655531
    Demo Order ID ..... The new test order the tool created. Here: 16630311
    Customer ID ....... The customer the demo order belongs to. Here: 6959001
    Allowlist ......... A written list of permitted things. Anything not on the list is refused.
    Fail closed ....... When unsure, STOP. Never guess and continue.
    Dry run ........... Do everything except the irreversible action.
    UNKNOWN ........... The result could not be established. NOT the same as "failed".

--- order58/lockfile.py ------------------------------------------------------------------------
PURPOSE   Only one run at a time per demo order.
KEY ITEMS class AlreadyRunning(RuntimeError)
          for_order(lock_dir, order_id) -> context manager
MECHANISM fcntl.flock(LOCK_EX | LOCK_NB) on state/locks/order-<id>.lock
          NON-BLOCKING on purpose: a second run is told immediately, instead of queueing and then
          acting on a cart that changed while it waited.

          The lock FILE is never deleted (deleting a held lock file is how two processes both
          believe they are alone).

3.1 PREREQUISITES

    - Ubuntu (verified on 22.04.5 LTS)
    - Python 3.10 or newer, with the venv module

    - A normal user account that owns the project directory. Root is NOT required.

3.2 THE COMMANDS (documented, not executed by this review)

    # 1. Go to the automation directory. Every command below assumes you are here.
    cd /var/www/html/knowledge-forge/order58-automation

    # 2. Create an isolated Python environment, so this tool's packages cannot affect
    #    anything else on the server.
    python3 -m venv venv

    # 3. Update the installer inside that environment.
    ./venv/bin/pip install --upgrade pip

    # 4. Install the one dependency.
    ./venv/bin/pip install -r requirements.txt

    # 5. Confirm Chrome exists. This prints a version; it does NOT open a window.
    /usr/bin/google-chrome --version

    THERE IS NO `playwright install` STEP. Explanation: browser.py uses channel="chrome", which
    drives the Chrome already on the machine. This avoids a ~150 MB Chromium download and means
    the automation sees exactly what a human sees. The project's existing browser tests
    (tests/E2E, puppeteer-core) make the same choice against the same binary.

3.3 VALIDATION COMMANDS (safe, no browser, no network)

    ./venv/bin/python --version                    # expect Python 3.10.12
    ./venv/bin/pip list                            # expect playwright 1.63.0
    ./venv/bin/python -m py_compile create_demo_order.py order58/*.py   # expect no output
    ./venv/bin/python create_demo_order.py --help  # prints the command list

3.4 AUTHENTICATION SETUP (opens a visible browser)

    ./venv/bin/python create_demo_order.py login

    What happens: a visible Chrome window opens on the demo page. YOU type the username and
    password yourself. The tool waits (default 420 seconds), then saves the session to
    state/order58.storage.json with permissions 0600.

    The tool never sees, stores, logs or transmits your password. It only keeps the resulting
    session cookie file.

3.5 SECURITY PROTECTIONS CREATED BY SETUP

    state/ ......... git-ignored; session file chmod 0600 (owner read/write only)
    screenshots/ ... git-ignored (they are pictures of a live admin panel with customer data)
    logs/ .......... git-ignored, and redacted by the formatter before anything is written
    config.json .... git-ignored (would name real stores and phone numbers)

4.4 THE --headless FLAG

    Implemented by `_bool()`, which accepts both styles:
        --headless              -> True   (uses argparse const)
        --headless true         -> True   ("1", "true", "yes", "y", "on" are all True)
        --headless false        -> False  (anything else is False)
        (flag omitted)          -> the command's own default

    Defaults differ ON PURPOSE: `inspect` defaults to VISIBLE (False) because a human is reading
    the page; every automated step defaults to headless (True).

4.7 HOW TO STOP EXECUTION

    Press Ctrl+C. The browser is closed by the `launch()` context manager's finally block, and
    the kernel releases the flock automatically. No manual cleanup is needed.
    IMPORTANT: if you interrupt during or just after a submit click, the outcome is UNKNOWN. Do
    NOT re-run with --submit. Verify by hand first (Chapter 11).

4.8 HOW TO READ THE RESULT

    EXIT CODE  MEANING
       0       Completed as intended (for phase-b without --submit: all checks passed)
       5       Identity or cart verification FAILED. Nothing was written.
       6       A pre-submission gate FAILED. Nothing was submitted.
       7       Landed on a route that is not allowlisted. Recorded as UNKNOWN.
       9       An attempt marker already exists for this order. Refused before opening a browser.

    Check it with:  echo $?

    The printed outcome line of phase-b --submit is one of:
       "SUCCESS (the incomplete banner is gone)"
       "UNKNOWN (navigated, but the order still reports itself incomplete)"
       "VALIDATION FAILED"      (the page showed validation errors)
       "UNKNOWN"                (the landing route was refused, or no navigation was observed)

    READ THIS CAREFULLY: UNKNOWN does NOT mean the order failed. It means the tool could not
    prove the result. The order may well have been placed. Never retry on UNKNOWN.

4.9 WHERE OUTPUT GOES

    Terminal ........ the full human-readable report (the primary output)
    logs/automation.log ... every log line, redacted
    screenshots/ .... HHMMSS-<name>.png, full page, at each significant point
    state/ .......... session, locks, submission markers

4.10 WHEN THE SESSION EXPIRES

    Any command that loads a page calls `_require_live_session()`. If the browser has been
    redirected to /admin/site/login it exits with:
        "The saved session has expired. Run `login` again."
    If the session FILE is missing entirely, browser.py raises SessionMissing before any
    navigation:
        "No saved sign-in was found. Run `python create_demo_order.py login` first"
    Fix: run `login` again. Nothing else is affected.

4.11 WHEN AN ORDER HAS ALREADY BEEN SUBMITTED

    `phase-b` checks for state/phase-b-attempt-<order-id>.json BEFORE launching Chrome. If it
    exists, it prints the marker's contents, explains that a previous attempt (successful OR of
    unknown outcome) blocks another, and exits with code 9. No browser opens.

5.1 WHERE THE INPUTS COME FROM — THE SHORT ANSWER

5.2 THE EXAMPLE VALUES, AND HOW EACH ONE REACHES THE CODE

    +-------------------+--------------------------------+------------------------------------+
    | Value             | Example                        | How it is supplied                 |
    +-------------------+--------------------------------+------------------------------------+
    | Demo URL          | https://joymeal.order58.com/   | HARDCODED as DEFAULT_URL           |
    |                   | admin/demo/order/make/         | (create_demo_order.py:44).         |
    |                   | 16655531-15163932150           | Overridable with --url on inspect, |
    |                   |                                | login, step3, step6b, run only.    |

    | Product           | Spring Roll                    | --product. Default "Spring Roll".  |

    | Order type        | take-out                       | NOT a flag. HARDCODED behaviour:   |

    |                   |                                | selects/verifies take-out.         |

    |                   |                                | cmd_phase_b as the CASH selector.  |
    +-------------------+--------------------------------+------------------------------------+

    Two of the six are NOT configurable at all: order type and payment method. Changing either
    requires editing Python.

5.3 HOW THE PRODUCT NAME IS READ AND USED

    `--product` is a plain string. It is passed to `product_menu.search(page, term)`, which:
      1. clears #product-search (so an earlier term's suggestions cannot be misread as these),
      2. types the term,
      3. waits up to 4000 ms for `.tt-menu .tt-dataset-ProductSearch .tt-suggestion`,
      4. reads every suggestion's text,
      5. parses each into code / name / category,
      6. classifies each as EXACT or NEAR.

5.4 HOW EXACT MATCHING WORKS

    Comparison uses `_normalise()`, which collapses whitespace and lowercases, but KEEPS
    punctuation — because punctuation distinguishes real products.

        _normalise(suggestion.name) == _normalise(term)   -> EXACT
        term is contained in the name                      -> NEAR

    "Spring Roll" matches a product named "Spring Roll".
    It does NOT match "Shrimp Spring Roll" or "Roast Pork Egg Roll (1)".

5.5 HOW AN UNKNOWN PRODUCT IS HANDLED

    NEAR matches are reported and NEVER used. If there is no exact match, the run STOPS and
    reports the near matches explicitly as "NOT used, and not substituted".

    Gujarati: jo product nu naam exactly match na thaay, to automation bijo product kadi pasand
    nahi kare — e atkai jaay chhe. Khoto product order thai jaay e sauthi kharab result chhe.

5.6 HOW QUANTITY IS SET AND VALIDATED

    The popup field #cartform-count carries aria-required="true", min="1", max="99" and ARRIVES
    ALREADY SET TO "1". `product_popup.set_count(page, qty)` reads the current value first:
      - if it already equals the requested quantity, it returns
        "already N — verified, not retyped" and writes NOTHING,
      - otherwise it fills the new value and reports what it was before.

    Writing "1" over "1" would be a change that looks like one and is not — and it would mask a
    popup that had not loaded properly. There is no Python-side range check against min/max;
    the browser's own validation applies.

5.7 HOW INPUT ERRORS ARE REPORTED

    Missing required flag ..... argparse error + usage, exit code 2
    Bad URL (wrong host/scheme) `_check_url()` raises SystemExit before Chrome starts
    Wrong identifiers ......... printed per-field comparison, then "Refusing to continue: the
                                page is not the authorised demo order.", exit 5
    Product not found ......... full search report + "NO EXACT MATCH", run stops
    Cart not empty ............ cart report + "STOPPING before adding anything", exit 5
    Totals mismatch ........... explicit expected-vs-actual line, exit 6

5.8 CROSS-CHECKED NUMERIC EXPECTATIONS

    step6, step6b, phase-a and timing require `--expect-total`.
    phase-b additionally requires `--expect-subtotal` and `--expect-tax`.
    These are not cosmetic: the run ABORTS if the page disagrees. You are asserting in advance
    what the page must say, which is what makes the later submission trustworthy.

5.9 WHAT YOU CAN CHANGE WITHOUT EDITING PYTHON

    CAN CHANGE:  --product, --qty, --customer-name (step3), --order-id, --customer-id,
                 --source-order, --expect-subtotal, --expect-tax, --expect-total,
                 --headless, --verbose, --wait (login)
    CANNOT CHANGE WITHOUT EDITING PYTHON:
                 the store / source order (hardcoded in 4 places + the guard allowlist),
                 the order type (always take-out),
                 the payment method (always cash),
                 the number of products (always one),
                 any checkout route (each is an exact string in guard.ALLOWED_PATHS)

5.10 MULTIPLE PRODUCTS

    NOT IMPLEMENTED. `--product` is one string; `--qty` is one integer. `cmd_step5` searches for
    one product, opens one popup, and presses Add to Cart once. It also REFUSES to run unless the
    cart is confirmed EMPTY, so it cannot be called repeatedly to build a multi-line cart.

    If multiple products were added later, the natural shape would be the `products` array in
    config.example.json — but note that nothing reads that file today (section 1.4).

5.11 EXAMPLE CONFIGURATION JSON — *** NOT IMPLEMENTED ***

    The file below exists on disk as config.example.json. It is shown here for completeness and
    future reference ONLY. No code reads it. Creating a config.json will have NO effect.

        {
          "demo_url": "https://joymeal.order58.com/admin/demo/order/make/16655531-15163932150",
          "customer_name": "Jignesh",

5.12 DIFFERENT STORES OR SOURCE ORDERS

    The segment `16655531-15163932150` is embedded in:
      - DEFAULT_URL (create_demo_order.py:44)
      - MENU_URL (create_demo_order.py:45)
      - all six entries of guard.ALLOWED_PATHS
      - the inline checkout URL strings in cmd_step6b, cmd_phase_a, cmd_timing, cmd_phase_b

    So a different store requires editing Python in several places AND adding the new paths to
    the allowlist. That friction is deliberate: the allowlist is what prevents the tool from ever
    driving a live-order route, and a wildcard would remove the protection.

================================================================================================
CHAPTER 6 — DEMO URL GENERATION LOGIC
================================================================================================

6.1 THE CLIENT'S SPECIFIED FORMAT

    https://ACCOUNTHOST/admin/demo/order/make/SOURCEORDERID-CUSTOMERPHONE

    Component       Meaning                              Stated origin
    ------------    ---------------------------------    ---------------------------------
    ACCOUNTHOST     the store's admin hostname           Account.host
    SOURCEORDERID   the template order being cloned      Order.id
    CUSTOMERPHONE   the customer's phone number          Reservation.phone inside Order.data

    Worked example:
        ACCOUNTHOST   = joymeal.order58.com
        SOURCEORDERID = 16655531
        CUSTOMERPHONE = 15163932150
        =>  https://joymeal.order58.com/admin/demo/order/make/16655531-15163932150

6.2 WHAT IS ACTUALLY IMPLEMENTED

    DYNAMIC URL GENERATION IS **NOT IMPLEMENTED**.

    The script consumes an ALREADY-GENERATED URL. There is no database connection, no Account /
    Order / Reservation model, and no code that assembles the URL from parts. The complete URL
    sits in `DEFAULT_URL` as a literal string and can be overridden with `--url` on four
    commands.

    No database connection was introduced by this review, and none should be added without a
    separate decision.

6.3 WHICH COMPONENT WOULD SUPPLY THE DATA LATER

    NOT VERIFIED — no such component exists in this project. If built, it would need read access
    to the Order58 Account, Order and Reservation data. That is a design decision, not a fact
    about the current code.

6.4 HOW THE URL AND IDs PREVENT TOUCHING THE WRONG ORDER OR STORE

    This part IS implemented, in four independent layers:

    LAYER 1 — before Chrome starts
        `_check_url()` rejects any non-HTTPS scheme and any hostname that is not exactly
        `joymeal.order58.com`.

    LAYER 2 — on every navigation
        `Guard.allows_navigation()` parses the URL and compares hostname EXACTLY and path
        EXACTLY against ALLOWED_PATHS. Query strings are ignored (the demo pages legitimately
        carry ?order_id=...), but the path itself must BE an approved page, not merely contain
        one.

    LAYER 3 — identity verification from the page's own response
        Every write command re-derives all three identifiers from the URL the APPLICATION
        returned, and compares them to what you passed:

            source_order = path's last segment, before the "-"
            order_id     = query parameter order_id
            customer_id  = query parameter customer_id

        Any mismatch => "Refusing to continue: the page is not the authorised demo order."
        The identifiers are never written down in the tool; they are always read back from the
        application.

    LAYER 4 — the demo-route marker before submission
        `DEMO_PATH_MARKER = "/admin/demo/"` must appear in the path of the page about to be
        submitted. cmd_phase_b re-checks this immediately before the click.

CHAPTER 9 — PLAYWRIGHT DETAILS
================================================================================================

9.1 HOW PLAYWRIGHT CONTROLS CHROME

    Playwright speaks the Chrome DevTools Protocol directly. There is no chromedriver, no
    Selenium server and no version-matching problem. `channel="chrome"` tells it to use the
    Chrome already installed on the machine:

        browser = playwright.chromium.launch(channel="chrome", headless=headless)

9.2 WHY THE SYNCHRONOUS API

    The project imports `playwright.sync_api`. That is why `greenlet` is a dependency: it lets a
    synchronous API sit on top of an async core, so the workflow reads top to bottom with no
    `async`/`await`. For a linear, human-mimicking script this is far easier to audit.

9.3 BROWSER CONTEXT

        context = browser.new_context(
            storage_state=state,                      # the saved login, or None
            viewport={"width": 1440, "height": 900},
        )
        context.set_default_timeout(30_000)

    One context, one page, per run. TLS verification is left ON and must never be disabled.

9.4 SESSION REUSE

    `context.storage_state(path=...)` writes cookies and local storage to JSON. Passing that file
    back as `storage_state` restores the logged-in session. The file is chmod 0600 and
    git-ignored. Its CONTENTS are never logged, printed or included in this document.

9.5 NAVIGATION AND WAITING

    Two patterns are used deliberately:

        # Normal: wait for the DOM
        page.goto(url, wait_until="domcontentloaded")

        # For a site that stalls: commit first, then settle separately
        page.goto(url, wait_until="commit", timeout=60000)
        try:
            page.wait_for_load_state("domcontentloaded", timeout=30000)
        except Exception:
            pass          # a stalled settle must not fail the run
        page.wait_for_timeout(3000)

    "commit" means the navigation has been committed and the URL is known, which is enough to
    tell WHERE the browser is. This matters because this site produced 30 s and 90 s navigation
    timeouts on pages that had loaded fine minutes earlier.

9.6 THE NAVIGATION GUARD, IN CODE

        page.on("framenavigated", on_navigated)   # only the MAIN frame counts
        page.on("request", on_request)            # records every non-GET as (METHOD, path)

    Attached in Session.__init__ BEFORE the first navigation, so nothing can slip past during
    startup. An embedded iframe is not "where the browser is", hence the parent_frame check.

9.7 LOCATORS AND SELECTORS

    Every selector in this project was READ FROM THE LIVE DOM by the `inspect` command. None was
    guessed from a screenshot. Full list in Chapter 17.4.

9.8 THE TYPEAHEAD

    The product search is a Twitter typeahead that queries the SERVER. Results arrive
    asynchronously in `.tt-menu .tt-dataset-ProductSearch` as `.tt-suggestion` elements. The code
    waits for the selector (4 s) and treats "no suggestions" as a real answer rather than an
    error.

9.9 DYNAMIC AJAX UPDATES — AND HOW THEY ARE SURVIVED

    See Step 9 in Chapter 7 for the full story. The pattern worth copying:

        def _settled_payment_total(page, expected, attempts=20):
            for _ in range(attempts):
                total = _payment_page_total(page)
                if total == expected:
                    return total
                page.wait_for_timeout(1000)
            return _payment_page_total(page)

    Poll for the condition you actually need. Do not sleep a fixed time and hope.

9.10 TIMEOUTS IN USE

    context default .......... 30_000 ms
    page.set_default_timeout .. 90_000 ms in timing and phase-b
    navigation (goto) ......... 60_000 ms
    submit expect_navigation .. 90_000 ms
    typeahead suggestions ..... 4_000 ms
    product modal ............. 8_000 ms
    settle poll ............... 20 x 1_000 ms

9.11 MODAL INTERACTION

    `page.wait_for_selector(MODAL, state="visible", timeout=8000)` then a 500 ms settle, because
    the popup fades in and its fields need a moment.

9.12 THE OFF-CANVAS DRAWER

    `#right-sidebar` is `position: fixed; right: -800px` — parked past the viewport edge. Its TEXT
    is readable from the DOM wherever it sits, which is why every cart READ works without
    opening it. But a control at x=2064 on a 1440-wide viewport cannot be clicked, and Playwright
    correctly refuses to try. Widening the viewport does not help, because the offset is relative
    to the right edge. `cart.open_panel()` clicks `div.right-sidebar-toggler-wrapper` instead —
    measured as presentational only, with zero non-GET requests.

9.13 HEADLESS MODE

    Per-command default (Chapter 4.4). Headless is used for automated steps; visible for `login`
    and `inspect`, where a human is involved.

9.14 SCREENSHOTS — TWO ATTEMPTS, AND A `required` CONTRACT

    Named `HHMMSS-<name>.png`. They are pictures of a live admin panel containing customer names
    and phone numbers, which is exactly why `screenshots/` is git-ignored.

    `Session.screenshot(name, *, required=True)` makes TWO attempts:

        1. full page    page.screenshot(..., full_page=True,  timeout=20_000)
        2. viewport     page.screenshot(..., full_page=False, timeout=10_000)
                        saved as HHMMSS-<name>-viewport.png

    The `-viewport` suffix is deliberate: a partial capture must never be mistaken for a full one.
    Worst case is 20 s + 10 s, the same ceiling as the single 30 s attempt it replaced, so a
    slow-but-working capture cannot regress.

    If BOTH attempts fail:
        required=True  -> raises. This is what makes a capture taken BEFORE an irreversible click
                          fail closed: no picture, no click. Used at step3-before-continue,
                          step5-before-add, timing-before, phase-b-cash-selected.
        required=False -> logs a WARNING, returns None, and the run continues. Used for the
                          `inspect` diagnostic and for all seven captures taken AFTER a server-side
                          write, where raising would discard the verification and outcome reporting
                          for something the server has already done.

    WHY A RETRY IS ALLOWED HERE AND NOWHERE ELSE
        A screenshot is a pure read. It is the only operation in this project that can be retried
        without risking a duplicate action. Every write is still clicked once and never repeated.

    WHY THIS EXISTS
        A full-page capture timed out after 30 s in a HEADED browser, hanging immediately after
        Playwright's "fonts loaded" step, and took a complete successful inspection down with it.
        The browser-level cause is **NOT PROVEN**. Page size was ruled out by evidence (no capture
        in this project exceeds 1440x1780, far inside Chrome's limits) and fonts were ruled out by
        the call log, but whether the blockage was frame compositing, a busy renderer or something
        else was never established. The failure did NOT reproduce on retest: after the change, both
        headless and headed runs captured the full page in about 6 seconds. So treat this as
        improved resilience and error handling, not a diagnosed and cured defect.

9.15 ERROR RECOVERY PHILOSOPHY

    There is deliberately very little. Reads are retried where safe (the settle poll). WRITES ARE
    NEVER RETRIED. An unclear write outcome is reported as unclear. A retry on an unclear write
    is how one order becomes two.

9.16 BROWSER CLEANUP

    `launch()` is a `@contextmanager` whose `finally` block always closes the context and the
    browser. A browser left running after a crash is a process somebody has to hunt down, and on
    a desktop it is a window that stays on screen.

9.17 WHY BROWSER AUTOMATION RATHER THAN AN INVENTED API

    No documented Order58 API was available. Any "API" would have had to be reverse-engineered
    from the site's own JavaScript, which means:
      - guessing undocumented endpoints and payloads,
      - reimplementing CSRF handling and session semantics,
      - bypassing the validation the UI enforces.
    Driving the UI means the application's own validation, authorization and business rules all
    still apply. The automation is a user, not a back door. It is slower, and it is honest.

     Near matches are reported and never substituted. See Chapter 5.4.

10.5 EMPTY VERSUS UNKNOWN CART ............................... IMPLEMENTED
     CartStatus has THREE values. An unreadable, missing or self-contradictory cart is UNKNOWN,
     and the caller stops. `is_definitely_empty()` returns True only when the page SAID it was
     empty. The method name is the contract.
     Gujarati: cart vanchi na shakay to "khali chhe" em kadi na manvu — UNKNOWN kahi ne atkvu.

10.6 CART QUANTITY VERIFICATION .............................. IMPLEMENTED
     Lines are parsed from the real shape `1 [1]Spring Roll` with the price on the following
     line, and cross-checked against the cart's own printed "1 items" count. If the two disagree
     the state is UNKNOWN rather than a guess about which is right. Money is read where the page
     prints it, never computed.

10.7 PER-ORDER FILE LOCK ..................................... IMPLEMENTED
     flock(LOCK_EX | LOCK_NB) on state/locks/order-<id>.lock. Non-blocking, kernel-released on
     crash, and the lock file is never deleted. PROVEN in practice: a second process was refused
     and a third acquired the lock after release.

10.8 ONE-CLICK SUBMISSION AND NO AUTOMATIC RETRY ............. IMPLEMENTED
     Every write click happens exactly once. There is no retry loop anywhere around a write. An
     ambiguous outcome is classified UNKNOWN and reported.

10.9 *** THE SUBMISSION ATTEMPT MARKER *** ................... IMPLEMENTED
     FILE      state/phase-b-attempt-16630311.json   (permissions 0600, git-ignored)
     CREATED   by cmd_phase_b, immediately BEFORE the Submit click
     CONTAINS  order_id, customer_id, attempted_at, total, payment_method, landed_on, outcome
     CHECKED   at the very start of phase-b, BEFORE Chrome is launched. If present: print it,
               explain, exit 9.

     WHY IT IS WRITTEN BEFORE THE CLICK, NOT AFTER
         If it were written afterwards and the process died mid-POST, nothing would record the
         attempt — and the next run would happily submit the same order again. Writing first
         means a crash leaves the marker behind, and the order is protected.

     *** WHY YOU MUST NOT DELETE IT ***
         An order whose submission outcome is UNKNOWN may ALREADY BE PLACED. Deleting the marker
         removes the only thing preventing a duplicate real order. Treat it as a permanent record.
         Removing one is a deliberate decision that needs the data owner's approval, never a
         troubleshooting step.
     Gujarati: aa file ne bhuli ne pan delete na karvi. Aa file j duplicate order atkave chhe.

10.10 TIMEOUT HANDLING ....................................... IMPLEMENTED
     Every timeout is finite. A stalled settle is swallowed (it must not fail a run), but a
     stalled WRITE is reported as UNKNOWN and never retried.

10.11 UNEXPECTED REDIRECT .................................... IMPLEMENTED
     The guard records a refusal. After a submission the tool notes the landing URL as evidence
     (the application chose it), reads NOTHING from that page, and verifies via approved pages
     instead.

10.12 SECRET HANDLING ........................................ IMPLEMENTED
     Redaction lives in the logging FORMATTER, so a call site cannot forget it. Cookie, session,
     csrf, token, bearer and authorization patterns are removed everywhere including inside URLs.
     CSRF field values are reported as `<withheld>`. The session file is 0600 and git-ignored.
     No password is ever handled by the tool.

10.13 GIT ISOLATION .......................................... IMPLEMENTED
     A directory-local .gitignore covers state/, *.storage.json, screenshots/, logs/,
     config.json, venv/, __pycache__/ and more. The ROOT .gitignore was never modified. No Yii3
     file, route, migration, service or configuration was touched by this project at any point.

10.14 WHAT IS ONLY RECOMMENDED, NOT IMPLEMENTED
     - pinning transitive dependency versions (pip freeze)
     - any automated test suite (Chapter 14)
     - server-side confirmation of completion inside the tool (Chapter 11)
     - a machine-readable run report (only --json on `inspect` exists)

CHAPTER 12 — TROUBLESHOOTING
================================================================================================

    Format: PROBLEM -> LIKELY CAUSE -> HOW TO VERIFY -> SAFE RESOLUTION
    No item below ever tells you to delete state, remove a lock, or retry a submission blindly.

 1. "python3: command not found"
    Cause: Python not installed / not on PATH.
    Verify: `which python3`
    Fix: install Python 3.10+. Then rebuild the venv (Chapter 3.2).

 2. "No such file or directory: ./venv/bin/python"
    Cause: the virtual environment does not exist, or you are in the wrong directory.
    Verify: `pwd` and `ls -d venv`
    Fix: cd to the automation directory; if venv is genuinely missing, follow Chapter 3.2.

 3. "ModuleNotFoundError: No module named 'playwright'"
    Cause: you used the system `python`/`python3` instead of `./venv/bin/python`, or
           dependencies were never installed.
    Verify: `./venv/bin/pip list | grep playwright`  (expect 1.63.0)
    Fix: always use `./venv/bin/python`. If missing: `./venv/bin/pip install -r requirements.txt`

 4. "Chromium distribution 'chrome' is not found"
    Cause: Google Chrome is not installed at /usr/bin/google-chrome.
    Verify: `/usr/bin/google-chrome --version`  (expect 143.0.7499.109 on this machine)
    Fix: install Google Chrome. Do NOT switch to bundled Chromium without a decision — the
         project deliberately drives the same binary the existing E2E tests use.

 5. "The saved session has expired. Run `login` again."
    Cause: the admin panel logged the session out.
    Verify: the message itself; the browser was redirected to /admin/site/login.
    Fix: `./venv/bin/python create_demo_order.py login` and sign in by hand. Nothing else is
         affected; no order state changes.

 6. "No saved sign-in was found."
    Cause: state/order58.storage.json does not exist.
    Verify: `ls -l state/order58.storage.json`  (check existence and 0600 — never print contents)
    Fix: run `login`.

 7. Login redirect loop, or a page that keeps returning to the login form
    Cause: cookies rejected, or the saved state is stale/partial.
    Verify: run `inspect`; PageReport.looks_like_sign_in will be True.
    Fix: run `login` again to overwrite the session file. Do not hand-edit it.

 8. "Refusing a non-HTTPS URL" / "Refusing '<host>': this tool only drives joymeal.order58.com"
    Cause: a bad `--url`.
    Verify: re-read the URL you passed.
    Fix: correct the URL. Never relax the host check. This is the outermost safety layer.

 9. "path '<...>' is not an approved page"
    Cause: the page is not in guard.ALLOWED_PATHS — often a legitimate redirect, as when
           checkout-customer dispatches elsewhere, or the post-submit checkout-completed page.
    Verify: the log line names the exact refused path (paths survive redaction intact, by design).
    Fix: this is usually CORRECT behaviour, not a bug. If a new path is genuinely needed, add
         ONE exact path after approval from the data owner. NEVER add a wildcard or prefix.

10. "Refusing to continue: the page is not the authorised demo order." (exit 5)
    Cause: --source-order / --order-id / --customer-id do not match what the application returned.
    Verify: the printed per-field expected-vs-actual table.
    Fix: correct the flags. Do not relax the check.

11. "NO EXACT MATCH for '<product>'"
    Cause: no product has exactly that name. Near matches may exist.
    Verify: the printed search report lists every suggestion with code, name and category.
    Fix: use the exact name from the report. NEVER accept a near match as a substitute — that is
         how an order goes through, looks right, and is wrong. ("Egg Roll" does not exist on this
         menu; "Spring Roll" does.)

12. Duplicate product / two identical cart lines
    Cause: Add to Cart ran twice — most likely two concurrent runs.
    Verify: read the cart report (lines and the cart's own stated item count).
    Fix: this is what the flock prevents; confirm you are not running two processes. Correct the
         cart through the normal admin UI, by hand. The tool cannot undo a cart line.

13. The product popup does not open, or shows the wrong product
    Cause: slow modal, or a mis-click on the wrong suggestion.
    Verify: screenshots/ around that timestamp; the report prints the modal's product name.
    Fix: re-run the READ-ONLY `step4` to inspect. It never presses Add to Cart.

14. Quantity did not change
    Cause: it was already correct. set_count() verifies rather than retyping.
    Verify: the report says "already N — verified, not retyped".
    Fix: nothing. This is intended.

15. Unexpected add-ons or required options in the popup
    Cause: a product with mandatory option groups (the verified case, Spring Roll, has none).
    Verify: PopupReport prints required_fields and every add-on group with whether a default is
            selected.
    Fix: STOP and ask the data owner what should be chosen. Do not invent a selection.

16. Cart status UNKNOWN
    Cause: the panel was missing, rendered no text, or said two contradictory things.
    Verify: `why_unknown` plus the verbatim raw panel text in the report.
    Fix: re-run the read-only inspection. If the page is genuinely broken, stop and report. Never
         "assume empty" — that is precisely the failure the three-state design prevents.

17. Total mismatch (exit 6)
    Cause: the page states a different amount than --expect-total.
    Verify: the printed expected-vs-actual line, and the raw cart text.
    Fix: find out WHY the amount differs before doing anything else. Do not just change the
         expected value to make the gate pass.

18. The payment total reads `None`, or the Cash radio reads unchecked
    Cause: THE AJAX RE-RENDER RACE. Selecting a payment method makes the page re-request
           /admin/demo/cart/list/... and replace the summary block; during that window both the
           total and the radio states read wrongly.
    Verify: wait and read again — the values settle. The server's own HTML contains
            `value="cash" checked`.
    Fix: already handled by `_settled_payment_total()`, which polls up to 20 x 1 s. If you write
         new code against this page, poll for the condition; never use one fixed sleep.
         This race caused a false "the automation changed server state" alarm once. It had not.

19. Unexpected checkout redirect (e.g. you asked for checkout-info and landed on
    checkout-customer?_redirect=0)
    Cause: either checkout-customer acting as a dispatcher, or the order has ADVANCED beyond that
           stage (a completed order no longer renders the wizard).
    Verify: compare the requested URL with the landed URL — both are printed.
    Fix: interpret it as information about the order's state. Do not force the old stage.

20. Pickup-time validation worry ("is schedule_datetime required?")
    Cause: uncertainty about whether an empty pickup time is accepted.
    Verify: the form's own validators. schedule_datetime has only
            `yii.validation.string(..., skipOnEmpty:1)` and NO `required` rule, whereas dine_type
            on the same form DOES have `required`.
    Fix: leave it EMPTY. That is the application's automatic "(AUTO) Pickup Time: 15 minutes"
         path, and the server accepted it. Never invent a date or time.

21. Payment selection seems not to apply
    Cause: usually item 18 above.
    Verify: read cash.checked and card.checked AFTER the summary settles.
    Fix: rely on the settle poll. Also confirm no card input is both visible and enabled — the
         two REQUIRED card fields are disabled and hidden, so they cannot block a Cash submit.

22. Navigation timeout (30 s / 90 s) on a page that worked earlier
    Cause: the remote site stalling. Observed repeatedly; not a defect in this code.
    Verify: the timeout message plus the log timestamps.
    Fix: for READS, re-run. For a WRITE, treat the outcome as UNKNOWN and go to item 24. Never
         re-run a write because it timed out.

23. "path '/admin/demo/order/checkout-completed' is not an approved page"
    Cause: the submission succeeded and the application redirected to its completion page, which
           is deliberately not allowlisted.
    Verify: the printed landing URL contains your demo order id.
    Fix: nothing is wrong. The tool records the URL as evidence, reads nothing from that page,
         and verifies via approved pages. To read it directly, the path would have to be approved
         and added as one exact entry — a decision for the data owner.

24. Submission outcome UNKNOWN
    Cause: refused landing route, a timeout, or the order still reporting itself incomplete.
    Verify: IN THIS ORDER —
            (a) the guard's non-GET list: was a POST to checkout-payment actually made?
            (b) the landing URL that was recorded;
            (c) the approved pages: is the cart empty? is the incomplete banner gone?
            (d) the EC2 JSON (Chapter 11.4) — the authoritative answer.
    Fix: *** DO NOT RE-SUBMIT. *** UNKNOWN frequently means SUCCESS that could not be proven.
         Establish the truth from (d) before any further action.

25. "an attempt was already recorded for this order" (exit 9)
    Cause: state/phase-b-attempt-<id>.json exists — this order already had a submission attempt.
    Verify: the command prints the marker's contents.
    Fix: this is the duplicate-prevention system WORKING. Verify the real status (Chapter 11.4).
         If a new test is needed, create a NEW demo order. Do not delete the marker.

26. "Another run already holds demo order <id>"
    Cause: a second process is working on that order.
    Verify: `ls -l state/locks/` and check for a running process.
    Fix: wait for the other run to finish. NEVER delete a lock file another process holds —
         that is how two processes each come to believe they are alone.

27. Missing EC2 JSON file
    Cause: the listener did not receive the event, is not running, or the order did not complete.
    Verify: `ls -l /data/orders/demo_mix_orders/` on EC2 (read-only).
    Fix: report it to whoever owns the EC2 listener. Do NOT restart PM2 from here, do not modify
         the listener, and never create the file by hand to make a check pass.

28. EC2 JSON field mismatch
    Cause: the order differs from expectations, or the schema differs from what was documented.
    Verify: the `jq` output in Chapter 11.4.
    Fix: report the actual values. Do not edit the JSON.

29. Browser crash mid-run
    Cause: resource exhaustion or a Chrome fault.
    Verify: the traceback plus the last screenshot.
    Fix: the flock is released by the kernel and the context manager closes the browser, so no
         cleanup is needed. For a READ step, re-run. If it crashed around a WRITE, treat the
         outcome as UNKNOWN (item 24) and verify before doing anything.

30. A screenshot is named `*-viewport.png`
    Cause: the full-page capture failed and the viewport fallback was used.
    Verify: a WARNING line in the output names both the file and the original error.
    Fix: nothing is broken, but the image shows only the visible area, NOT the whole page. Do not
         treat it as full-page evidence. If it happens repeatedly, capture the warning text - the
         underlying browser cause is still unproven.

31. A screenshot failed entirely and the run continued
    Cause: both attempts failed on a capture marked `required=False` (the `inspect` diagnostic, or
           post-write evidence).
    Verify: the WARNING naming both failures; the printed report is still complete.
    Fix: intended behaviour. The printed report, not the PNG, is the evidence. A pre-write capture
         would instead have raised and stopped before the click.

32. No screenshots or no log output
    Cause: the directory could not be created, or a permissions problem.
    Verify: `ls -ld screenshots logs` and check ownership.
    Fix: ensure your user owns the automation directory. `Session.screenshot()` returns None
         harmlessly when no directory is configured, so a run is not failed by this.

13.6 DEFECTS FOUND AND FIXED DURING DEVELOPMENT

    (a) CART SUBTOTAL / TOTAL CONFUSION ...................................... FIXED
        The regex `total` matched inside "Sub-total-", so the subtotal was reported as the total
        ($1.85 instead of $2.04). Patterns are now anchored to the start of a line (`^sub`,
        `^total`) so one cannot match inside the other.

    (b) TAX LABEL NOT PARSED ................................................. FIXED
        The label is "TAX(10.00%):", with the rate between the word and the colon. The pattern
        now allows for that instead of assuming a bare label.

    (c) WHOLE CART PANEL READ AS ONE LINE .................................... FIXED
        A cart with two products would still have counted as one. Lines are now parsed from the
        real shape `1 [1]Spring Roll` with the price on the following line, and cross-checked
        against the cart's own "1 items".

    (d) WRONG PAGE SELECTOR FOR THE CART TOTAL ............................... FIXED
        `cart.read()` targets `#right-sidebar`, which exists only on the product-menu page. Asking
        it for a total on the PAYMENT page returned None and stopped two runs at the final gate.
        The gate was correct; the source was wrong. `_payment_page_total()` now reads the payment
        page's own summary (a label element with the amount in the next sibling).

    (e) TEMPORARY `None` TOTALS DURING THE PAYMENT SUMMARY REFRESH ........... FIXED
        The AJAX re-render race of Chapter 7 Step 9. Fixed by `_settled_payment_total()` polling
        until the stated total matches. This also explained a false alarm in which the cash radio
        appeared to have been changed by the automation; it had not.

    (f) BROKEN PRODUCT SCANNER / FALSE "NOT FOUND" ........................... FIXED
        The original grid scanner captured price blobs rather than names and could only see one
        category, producing a false "Egg Roll not found". Rebuilt around the real typeahead and
        verified POSITIVELY (finding "Spring Roll") before any negative result was trusted.

    (g) SOURCE FILE ACCIDENTALLY EXPANDED TO 86,239 LINES .................... FIXED
        A runaway string-replace corrupted create_demo_order.py. It was deleted and rewritten
        cleanly. Later edits assert occurrence counts before substituting.

    (h) REDACTION DESTROYED THE USEFUL PART OF EVERY LOG LINE ................ FIXED
        `16655531-15163932150` is digits-dash-digits and matched the phone-number rule, reducing
        URLs to `.../make/<redacted-phone>50`. URLs and bare paths are now lifted out before the
        phone and token rules run, while the cookie/token rules still apply inside them.

    (i) "Go to Checkout" CLICK TIMED OUT ..................................... FIXED
        The cart is an off-canvas drawer at x=2064 on a 1440-wide viewport. Playwright correctly
        refused to click it. Resolved via `div.right-sidebar-toggler-wrapper`.

CHAPTER 16 — SUPERVISOR QUESTIONS AND ANSWERS
================================================================================================

Q1. What is this automation, in one sentence?
    A Python program that drives Google Chrome to create a DEMO order in the Order58 admin panel
    by clicking through the website the way a person would.

Q2. Why Python?
    It was the stated requirement, it has first-class Playwright support, and the EC2 listener
    this work sits alongside is already Python. It also keeps the tool completely separate from
    the PHP application.

Q3. Why Playwright and not Selenium?
    Playwright needs no separate driver binary to install and version-match, has built-in waiting
    that reduces flaky timing bugs, and can reuse a saved login via `storage_state`. It can also
    drive the Chrome already on the machine, so no extra browser download is needed.

Q4. Which Python version?
    3.10.12, inside an isolated virtual environment at order58-automation/venv.

Q5. Which Playwright version?
    1.63.0 — the only package pinned in requirements.txt, and the version actually installed.

Q6. Which browser, and where does it come from?
    The Google Chrome already installed on the server, version 143.0.7499.109 at
    /usr/bin/google-chrome. We use `channel="chrome"`, so no ~150 MB Chromium is downloaded and
    there is no `playwright install` step.

Q7. Do we need Node.js or npm?
    No. Verified: nothing in the Python sources invokes node, npm or any subprocess.

Q8. How do I execute the script?
    cd /var/www/html/knowledge-forge/order58-automation
    ./venv/bin/python create_demo_order.py <SUBCOMMAND> [flags]
    Start with `--help`. Always use ./venv/bin/python, never plain python3.

Q9. Where is the entry point?
    create_demo_order.py — 1835 lines, containing every CLI command. The reusable library lives
    in order58/ (10 modules).

Q10. Can I just run `create_demo_order.py --product "Spring Roll" --qty 1`?
    No. A subcommand is mandatory, so that form errors out. And the `run` subcommand that would
    accept those flags is a stub that exits with "not implemented". Use the step commands.

Q11. Where do I pass the URL?
    Usually nowhere — it is hardcoded as DEFAULT_URL. Four commands (inspect, login, step3,
    step6b) accept `--url`. The host is locked to joymeal.order58.com and the path must be on the
    allowlist.

Q12. Where do I pass the product name?
    `--product "Spring Roll"`. It must match EXACTLY. If it does not exist, the tool stops rather
    than substituting something similar.

Q13. How does quantity work?
    `--qty 1`. The popup's quantity field already arrives set to 1, so the tool verifies it
    instead of retyping. Values above 1 are supported by the code but have never been run end to
    end.

Q14. Can I submit multiple products in one order?
    No. Not implemented. One product, one quantity. `step5` also refuses to run unless the cart
    is confirmed empty, so it cannot be called repeatedly to build up a cart.

Q15. Can I use another store or another source order?
    Not without editing Python. The segment 16655531-15163932150 is hardcoded in four places and
    in every allowlist entry. That friction is deliberate — the allowlist is what prevents the
    tool ever driving a live-order route.

Q16. How is login handled? Do we store a password?
    We never store, see, log or type a password. You run `login`, a visible Chrome window opens,
    YOU sign in by hand, and the resulting session is saved.

Q17. Where does the session live, and how is it protected?
    state/order58.storage.json, permissions 0600 (owner only), git-ignored. Its contents are
    never logged or printed. Treat it as equivalent to a password.

Q18. What if the session expires?
    The tool detects the redirect to the login page and stops with "The saved session has expired.
    Run `login` again." No order state is affected.

Q19. How does product search work?
    The page uses a Twitter typeahead that queries the server. We type into #product-search, wait
    up to 4 seconds for `.tt-suggestion` results, and read them. We do NOT scan the visible
    product grid — the grid only renders one category, which once produced a false "not found".

Q20. How does the cart work, and what if it cannot be read?
    `cart.read()` returns one of three states: EMPTY, HAS_ITEMS or UNKNOWN. UNKNOWN means we
    could not tell, and the run stops. That third state is the whole point: a parser that said
    "empty" when it had merely failed would let us add a second line to a cart that already had
    one.

Q21. How is Cash selected?
    By the radio `input[name='CheckoutPaymentMethod[payment_method]'][value='cash']`. We then
    wait for the page's AJAX summary to finish rebuilding, and only then verify that Cash is
    checked, Credit Card is not, and no card input is both visible and enabled.

Q22. What does a dry run do?
    `phase-b` WITHOUT `--submit` performs every verification — identifiers, cart, totals,
    Take-Out, the incomplete banner, the whole payment form and its validators — then stops and
    reports. It makes no non-GET request at all.

Q23. How do we avoid submitting the same order twice?
    Three layers. A per-order flock stops two runs at once. A marker file
    state/phase-b-attempt-<id>.json is written BEFORE the click and checked before Chrome even
    launches, so even a crash mid-POST blocks a second attempt. And there is no retry logic
    anywhere around a write.

Q24. Why is the marker written BEFORE the click rather than after?
    Because if it were written afterwards and the process died mid-POST, nothing would record the
    attempt, and the next run would submit the same order again.

Q25. What happens if the browser crashes?
    The kernel releases the flock, and the context manager closes the browser. No cleanup is
    needed. If it crashed near a write, the outcome is UNKNOWN and must be verified before
    anything else is done.

Q26. What if a timeout occurs after pressing Submit?
    It is reported as UNKNOWN and NEVER retried. The order may well have been placed. We verify
    from the approved pages and then from the EC2 JSON.

Q27. What does UNKNOWN actually mean? Did it fail?
    Not necessarily. UNKNOWN means the tool could not PROVE the outcome. In our real run the
    evidence strongly indicates success; the tool still said UNKNOWN because the completion page
    is deliberately not on the allowlist. It is a statement about evidence, not about failure.

Q28. Where is the order output stored?
    Not by this tool. The order lives in Order58's own system. A separate EC2 listener writes the
    JSON. Locally we keep only the terminal report, logs/automation.log, screenshots/ and state/.

Q29. Who generates the JSON file?
    /root/order58/get-mix-order.py on EC2, managed by PM2, which listens for `new-order-created`
    and writes /data/orders/demo_mix_orders/<source>-<demo>.json. NOT VERIFIED from this machine.

Q30. Did we modify the WebSocket listener or restart PM2?
    No. Verified from source: nothing here touches EC2, SSH, PM2, /data/orders/ or any WebSocket
    library.

Q31. Did this change the Knowledge Forge Yii3 application?
    No. `git status` shows only the untracked order58-automation/ directory. No PHP file, route,
    migration, service, dependency or configuration was modified, and the root .gitignore was not
    touched.

Q32. How do we test it? Are there unit tests?
    There is NO automated test suite — no pytest, no test files, no linters. What we do have:
    py_compile passes on all 11 files, all CLI help works, the lock was proven with real
    concurrent processes, the parser was verified in both directions, and every selector was read
    from the live DOM. Chapter 14.4 proposes a real test suite.

Q33. Can it run automatically in the background, on a schedule?
    No. Not implemented, and not advisable yet: it needs a human-created login session, and it
    writes to a live admin panel. Scheduling it would remove the human authorization step that is
    currently the main control.

Q34. Is it production-ready?
    No. See 15.3: no tests, `run` is a stub, the store is hardcoded, only one scenario has been
    exercised, and completion is not verified in-tool.

Q35. What has actually been proven to work?
    One complete demo order: Spring Roll x1, Take-Out, Cash, $2.04, on order 16630311, with
    exactly one payment POST and a redirect to the application's own completion route.

Q36. What is the single biggest risk right now?
    That server-side completion of 16630311 has not been independently confirmed. The EC2 jq
    check in Chapter 11.4 closes that gap and takes seconds to run.

Q37. What is the next development step?
    The Level 1 unit tests in 14.4 — they need no browser or live site and they protect the guard
    and the parsers, where a silent failure would do the most damage. After that, either implement
    the config file or delete the misleading example, and refresh README.md.

Q38. Why does the pickup time get left empty? Isn't that a missing field?
    No. The form's own validator for schedule_datetime is a max-length check with
    `skipOnEmpty: 1` and NO `required` rule, while dine_type on the same form DOES have
    `required`. Empty is the application's automatic "(AUTO) Pickup Time: 15 minutes" path, and
    the server accepted it. We never invent a date or time.

Q39. Why so many separate step commands instead of one button?
    Each was built and approved only after the previous one's real selectors had been read off the
    page, and each write step needed its own authorization. The commands are the audit trail of
    that process. Consolidating them into `run` is proposed in 15.4.

Q40. What is that scary red warning on the payment page?
    "WARNING!! You are not at this store's call session! please double checking!!" It is a
    page-level banner outside the payment form, identical on all three checkout stages, with no
    validation styling. It was displayed when the Timing & Info stage submitted successfully, so
    it does not block submissions. It was judged environmental rather than order-specific.

Q41. Can the tool accidentally create a LIVE (real customer) order?
    Several layers make this very unlikely: the host is locked, only seven exact paths are
    reachable, every path is a /admin/demo/ route, "/admin/demo/" must be in the path immediately
    before any submission, and all three identifiers are re-checked against the application's own
    response. A prefix wildcard was explicitly refused for this reason.

Q42. How much does a run cost in time?
    A dry-run phase-b verification takes roughly 15-30 seconds in headless mode. The remote site
    has occasionally stalled for 30-90 seconds, which dominates when it happens.

CHAPTER 16A — THE ONE-COMMAND WORKFLOW AND THE ONE-CLICK LAUNCHER
================================================================================================

16A.1 THE THREE WRITE GATES

    run                      preflight. Reads only. Zero server writes.
    run --create             create, add to cart, check out, select Cash, then STOP as `prepared`.
    run --create --submit    all of the above, and ONE submission.
    run --resume             re-verify a prepared order. Reads only.
    run --resume --submit    submit THAT order. CANNOT create one.

    `--submit` on its own is refused. So is `--create --resume`. Both refusals happen at argument
    parsing, before a browser opens. A single flag that both created an order and submitted it
    would be one typo away from an order nobody wanted.

    WHY A PREFLIGHT CANNOT CHECK THE PRODUCT OR THE TOTALS
        The product menu and every checkout stage are addressed by `?order_id=`, and that id does
        not exist until an order has been created. So a zero-write run can validate the URL, the
        session, the approved tuple, the phone on the page and the make-page form — and nothing
        more. It says so rather than implying otherwise.

16A.2 auto_order.py — ONE FILE, PRESS RUN

    *** RUNNING IT CREATES AND SUBMITS ONE DEMO ORDER. There is no confirmation prompt. ***

    Four writes reach the live admin panel: Continue, Add to Cart, the Timing & Info POST, and the
    payment POST. None can be undone by this tool.

    Configuration — the only five lines to edit:

        DEMO_URL      = "https://joymeal.order58.com/admin/demo/order/make/16655531-15163932150"
        CUSTOMER_NAME = "Jignesh"
        PRODUCT       = "Spring Roll"
        QUANTITY      = 1
        HEADLESS      = False

    It builds the same argparse Namespace the command line would produce and calls
    `create_demo_order.cmd_run` directly. No subprocess, no shell, no second copy of the workflow,
    no selector of its own — there are tests asserting each of those (tests/test_launcher.py).

    TO RUN IT FROM AN IDE the interpreter MUST be `order58-automation/venv/bin/python`, because
    Playwright is installed there and nowhere else.
        VS Code : Ctrl+Shift+P, "Python: Select Interpreter", pick ./order58-automation/venv/bin/python
        PyCharm : Settings > Project > Python Interpreter > add that path as an existing environment

    PREREQUISITE: a saved sign-in. `./venv/bin/python create_demo_order.py login`. The launcher
    never asks for, stores or logs a password.

16A.3 THE RUN JOURNAL — WHAT BLOCKS A SECOND ORDER

    state/runs/run-<segment>-<timestamp>.json, mode 0600, created with exclusive `open(path,"x")`
    and fsynced — file AND directory — BEFORE the first write.

    Status                Resumable?   Blocks a new --create?
    in_progress           no           YES   (this is also what a crashed run leaves behind)
    prepared              YES          YES   (resume it; do not orphan it)
    unknown               NEVER        YES   (and never retried)
    aborted_after_write   no           YES
    validation_failed     no           YES
    aborted_no_write      no           no
    completed             no           no
    resolved_by_operator  no           no

    TWO GUARANTEES WORTH KNOWING
      1. A run that attempted a write can NEVER be filed as `aborted_no_write`. `close()`
         reclassifies it to `aborted_after_write` automatically. So "the order was created but the
         product was not found" blocks the next creation, as it must.
      2. `completed` is reachable only from a positive confirmation. A timeout, an exception or a
         redirect to a route the guard refused all produce `unknown`.

    NOTHING EXPIRES ON ITS OWN. No TTL, no sweeper, no auto-release. The only way out:

        python create_demo_order.py journal                       # read-only listing
        python create_demo_order.py journal --show <file>          # read-only detail
        python create_demo_order.py journal --resolve <file> \
            --reason "..." --evidence "..."                        # the only route out

    Both a reason and the supporting verification are required and must be substantive. Resolving a
    journal changes NO order and removes NO submission marker.

16A.4 THE NINE PRE-SUBMISSION CHECKS

    Matching totals prove the two stages agree, not that either is right. So:

      1  exactly one cart line
      2  product name matches exactly
      3  quantity matches
      4  line price x quantity == subtotal
      5  subtotal + tax == total          <- an unintended charge cannot hide from this
      6  the add-on selection is byte-identical before and after setting the quantity
      7  every money row is one of {Subtotal, TAX, TOTAL, Delivery}
      8  the payment page's own stated total == the cart total
      9  no enabled AND visible required field on the payment form

    Check 7 accounts for a verified quirk: a take-out cart prints `Delivery $3.49` and EXCLUDES it
    from the $2.04 total. A check that summed every money row would abort every correct order.
    A number the page never printed FAILS its check rather than being skipped.

16A.5 LOCKS

    state/locks/source-<segment>.lock   held for the whole run (the order does not exist yet)
    state/locks/order-<id>.lock         acquired the moment the application issues the id

    Both are flock(LOCK_EX|LOCK_NB), released by the kernel on a crash.

HOW TO EXPLAIN THIS PROJECT TO MY SIR IN 2 MINUTES
================================================================================================

    "We needed to create test orders in the Order58 admin panel without doing it by hand every
     time. So I wrote a small Python program that opens Chrome and clicks through the website
     exactly like a person: it fills the customer form, searches for the product, sets the
     quantity, adds it to the cart, walks through the checkout, picks Cash, and presses Submit.

     I deliberately did NOT build it by calling hidden APIs or writing into the database. By
     driving the real website, all of Order58's own validation and permission rules still apply.
     The automation is just a user — it can't do anything a logged-in person couldn't do.

     Safety was the main part of the work, because this touches a live admin panel. It can only
     ever reach one website and seven specific demo pages — anything else is refused before the
     browser even opens. It checks all three order identifiers against what the application
     itself returns before it writes anything. It presses every button only once and never
     retries, because a retry is how one order becomes two. It takes an exclusive lock so two
     copies can't run on the same order. And before it submits, it writes a marker file, so even
     if the machine crashed mid-submission, it will refuse to submit that order a second time.

     We tested it end to end once: one Spring Roll, Take-Out, Cash, two dollars four cents, on
     demo order 16630311. It made exactly one payment request, the site redirected to its own
     'checkout-completed' page, the cart emptied, and the 'order incomplete' warning disappeared.
     The tool still labelled the result UNKNOWN rather than SUCCESS — on purpose, because that
     confirmation page isn't on its allowed list, so it won't claim a success it couldn't read
     directly. I'd rather it under-claim than over-claim. There's a one-line check on the EC2 box
     that confirms it properly, and that's the one thing still outstanding.

     On the honest side: it does one scenario. One product, quantity one, Take-Out, Cash, one
     store. Multiple products, a config file, and a single one-command run are not built yet, and
     there is no automated test suite — only the checks I ran by hand. And it does not touch our
     Knowledge Forge PHP application at all: separate folder, separate dependencies, nothing
     shared. Git confirms not one existing file was changed.

     Next step I'd recommend is a small set of unit tests for the safety guard and the cart
     parser. They need no browser, and those two pieces are where a quiet bug would do the most
     damage."
