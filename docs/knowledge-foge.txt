0. HOW TO READ THIS DOCUMENT - THE VERIFICATION TAGS
--------------------------------------------------------------------------------------

Every non-obvious claim in this document carries one of four tags. They are not
decoration. They tell you how much weight a statement can bear.

  [CODE]
      Verified by reading the source in this working tree. This is the strongest tag
      and most of the document carries it. A file path and often a line number is
      given so you can check it yourself.

  [DEV]
      Verified by running something on THIS development machine (hostname `latitude`,
      16 GB RAM, 8 logical CPUs, PHP 8.2.28, MySQL 8.0.46). A [DEV] fact describes the
      developer box and NOTHING ELSE.

  [PROD-OBS]
      Observed indirectly - from a screenshot of the production site
      (joymeal.seawolf.io), or asserted by an existing document. The behaviour was
      seen; the configuration that produced it was NOT inspected.

  [UNVERIFIED-PROD]
      Cannot be checked from here at all. Production server configuration, its crontab,
      its .env, its installed timers, its PHP-FPM pool. Anything tagged this way is an
      open question, not a claim.

THE RULE THIS DOCUMENT FOLLOWS, AND WHY IT MATTERS

  A [DEV] fact NEVER implies the same thing about production.

  Two concrete examples, because both are live traps in this codebase:

    * The Order58 import timer is NOT installed on the dev box [DEV]. That says
      nothing about production. Screenshots show the feature running there [PROD-OBS],
      so it is presumably scheduled somehow - but the mechanism was not inspected
      [UNVERIFIED-PROD].

    * The `order58_call_imports` table is empty on dev [DEV]. Production screenshots

  If you are reading this document to decide something about production, treat [DEV]

1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------------

1.1 WHAT KNOWLEDGE FORGE IS

Knowledge Forge is an internal admin application that builds and serves AI knowledge
bases for restaurant stores, and turns their phone call recordings into reviewed,
speaker-separated transcripts.

Two halves, one database:

  KNOWLEDGE  - mirror store/rule/agent data from the Order58 platform, turn it into
               documents, index those documents into OpenAI vector stores, and let
               administrators and call-centre agents ask grounded questions about them
               in chat.

  AUDIO      - take a call recording (uploaded by hand, or imported automatically from
               Order58's recording service), transcribe it with Whisper or Deepgram,
               work out who was speaking, let a human correct the result, and
               optionally re-voice it as clean AI training audio.

1.2 WHO USES IT

  ADMINISTRATOR  - full access. Manages knowledge bases, documents, rules, store audio,
                   call imports, reports, settings. Authenticated against
                   `admin_users` [CODE].

  AGENT          - a call-centre agent mirrored from Order58 into `order58_agents`.
                   Sees only chat: store chat for stores they are allowed to see, plus
                   rule chat. Cannot reach any admin page. Authenticated through the
                   Order58 API with a local mirror fallback [CODE].

  There is no public-facing surface. Of 137 routes, exactly 4 are reachable without a
  session, and all 4 are login endpoints [CODE].

1.3 MAJOR MODULES

  Order58        145 files   external platform mirror: stores, agents, knowledge,
                             rules, call recordings

2. IMPORTANT INVARIANTS - READ THIS BEFORE CHANGING ANYTHING
--------------------------------------------------------------------------------------

These are the rules the system depends on. Most are enforced by a test, and the test
name is given so you can find out immediately if you have broken one. They are at the
front of this document deliberately: they are the section most likely to prevent
damage, and they are wasted at the end.

INV-1  THE WEB TIER MUST NEVER EXECUTE TRANSCRIPTION.
       A web request may create an `audio_transcription_jobs` row. It may not run
       ffmpeg, whisper-cli or the diarizer. A 900 MB, 400-second subprocess inside a
       PHP-FPM worker takes the site down.
       Enforced by: `tests/Unit/AudioToText/WebTierCannotRunWhisperTest.php` [CODE]

INV-2  AUDIO-TO-TEXT AND EVERY OTHER MODULE MUST NOT NAME EACH OTHER.
       `src/AudioToText/**` may not contain `App\Order58\`, `App\Chat\`, `App\Rules\`,
       `App\KnowledgeBase\`, `App\Document\`, `App\Agent\`, `App\Ai\`, `App\Reports\`
       or `App\Worker\`. And every file under `src/` EXCEPT `src/AudioToText/` may not
       contain the string `App\AudioToText`.
       The test scans RAW SOURCE, so even a docblock that spells the namespace fails.
       Cross-module traffic goes through `src/Shared/` (section 4.5) or through a
       shared TABLE NAME.
       Enforced by: `tests/Unit/AudioToText/ModuleIsolationTest.php` [CODE]

INV-3  THE MACHINE TRANSCRIPT IS IMMUTABLE.
       What Whisper or Deepgram produced is never edited. Human corrections live in a
       separate reviewed layer (`audio_transcription_jobs.reviewed_*` columns and
       `audio_segment_revisions`). Reverting a correction means dropping the reviewed
       layer, and the machine result is still there underneath.
       Why: without this you cannot answer "did the model get it wrong, or did a human
       change it?", which is the whole point of a review workflow. [CODE]

INV-4  THE TRANSCRIPTION PROVIDER IS COPIED ONTO THE JOB AT ENQUEUE TIME.
       `audio_transcription_jobs` carries its own provider column. Changing the global
       default in `audio_to_text_settings` does NOT re-route work already queued.
       Why: an administrator switching the default must not silently change what
       already-queued recordings will be billed against.
       Enforced by: `tests/Unit/AudioToText/ProviderIndependenceTest.php` [CODE]

INV-5  EVERY BACKGROUND COMMAND HOLDS ITS OWN LOCK FILE. NEVER SHARE ONE.
       Three distinct locks, and each pairing has a specific failure mode:
         - transcription worker : runtime/audio-to-text/worker.lock
         - TTS worker           : runtime/audio-to-text/tts-worker.lock
         - Order58 importer     : runtime/locks/order58-import.lock
         - document drainer     : runtime/locks/worker.lock
       Sharing the transcription lock with the importer makes a download block a
       transcription for no reason. Pointing a CRON WRAPPER at the application's own
       lock file makes EVERY RUN SKIP - cron takes it, then PHP cannot. That mistake is
       recorded in `docs/server/cron/knowledge-forge-audio-transcription` [CODE].

INV-6  RESOURCE ADMISSION IS CHECKED BEFORE THE CLAIM, NEVER AFTER.
       A worker that cannot afford the work must leave its queue row exactly as it
       found it: not claimed, not failed, no attempt consumed. It logs a reason and
       exits 0.
       Why: an admission check after the claim would burn a retry every time the
       machine was busy, and a queue would fail its way to empty. [CODE]

INV-7  ADMISSION FAILS CLOSED.
       If `/proc/meminfo` or `/proc/loadavg` cannot be read, the tick DEFERS. A guard
       that admits work when it cannot measure resources is not a guard.
       Consequence you must accept: an unmeasurable machine stalls the queue. That is
       why every deferral is logged with its reason. [CODE]

INV-8  ORDER58 `company` IS RESOLVED SERVER-SIDE, NEVER ACCEPTED FROM THE BROWSER.
       The recording fetch URL carries a `company` parameter. It comes from
       `order58_stores.company` for the selected store, via `RecordingCompanyResolver`.
       A posted `company` is IGNORED OUTRIGHT, not validated.
       Why: there is no value a browser could send that the server should prefer to the
       store's own, and a wrong one fetches somebody else's audio. [CODE]

INV-9  THE BROWSER'S LIST OF CALLS IS NEVER TRUSTED.
       `Calls\SyncAction` re-asks the provider for today's calls and keeps only the
       intersection with what was posted. The fetch date comes from that fresh answer,
       never from the form.
       Why: a posted call id becomes a path segment in an outbound HTTP request. [CODE]

INV-10 CHANNEL VOCABULARIES MUST NOT BE COLLAPSED.
       Three separate vocabularies exist on purpose:
         RecordingChannel  mixed / caller / callee   (lowercase - the provider's words)
         RecordingType     MIXED / CALLER / CALLEE   (uppercase - the audio module's)
         SourceRole        COMMON / CUSTOMER / AGENT (who is speaking)
       CALLER IS NEVER "CUSTOMER". CALLEE IS NEVER "AGENT". Who spoke is decided by
       diarization and confirmed by a human, not by which channel a file came from.
       Enforced by: `tests/Unit/Order58/RecordingChannelIsolationTest.php` [CODE]

INV-11 IDEMPOTENCY KEYS ARE UNIQUE CONSTRAINTS, NOT APPLICATION CHECKS.
       `order58_call_imports` has UNIQUE (store_source_id, call_session_id, channel).
       Duplicate work is prevented by INSERT-and-catch-IntegrityException, not by a
       SELECT-then-INSERT that races. `order_id` is deliberately NOT part of the key -
       one order can have several calls, and each call three channels. [CODE]

INV-12 A WORKER CLAIM IS A CONDITIONAL UPDATE WHOSE AFFECTED-ROW COUNT IS THE LOCK.
       `UPDATE ... SET status='FETCHING' WHERE id=:id AND status='PENDING'`, then check
       affected === 1. Two workers cannot both win. No SELECT FOR UPDATE, no
       transaction needed. [CODE]

INV-13 SECRETS NEVER REACH A RENDERED PAGE OR A LOG.
       Every message stored in `order58_call_imports.error_message` passes through
       `SecretRedactor::redactAndTruncate($msg, 1000)`. The redactor is seeded with the
       live credentials at construction, so even a provider error body that echoes the
       request back cannot carry one into a log file. [CODE]

INV-14 NO INLINE JAVASCRIPT, EVER.
       The Content-Security-Policy is `script-src 'self'`. A `<script>` block or an
       `onclick=` attribute is silently dropped by the browser. All behaviour attaches
       via `addEventListener` against `data-` attributes. Same for styles -
       `style-src 'self'` means a `style=""` attribute does nothing. [CODE]

INV-15 AUDIO-TO-TEXT CSS STAYS UNDER THE `.a2t-` PREFIX.
       A test scans everything after the "Audio to Text" marker comment in
       `assets/main/admin.css` and fails on any selector without that prefix. If you
       add CSS for another module, put it BEFORE that marker.
       Enforced by: `ModuleIsolationTest::testAudioToTextCssIsScopedToItsOwnPrefix`
       [CODE]

INV-16 THE SHARED WORKER MUST NOT RUN TRANSCRIPTION.
       `kf:worker:run` and `WorkerRunner` may not contain the string `AudioToText`.
       A transcription holds a core for ~90-400 seconds; running it inside the shared
       drainer would stall document processing and Order58 sync behind every recording.
       Enforced by: `ModuleIsolationTest::testTheSharedWorkerDoesNotRunTranscription`
       [CODE]

INV-17 THERE MUST BE EXACTLY ONE EXTERNAL SCHEDULER PER WORKER.
       cron OR systemd timer, never both, and never alongside a permanent foreground
       worker. Running a worker without `--once` turns it into a daemon that holds its
       lock forever and makes every scheduled tick skip. [CODE]

3.2 FRAMEWORK - YII 3, AND WHAT THAT MEANS

  This is NOT Laravel and NOT Yii 2. It is a set of Yiisoft PSR packages wired by hand.
  Consequences a Laravel or Yii 2 developer must internalise:

    * No ActiveRecord. No models. Queries are written with `Yiisoft\Db\Query\Query`
      inside an `Infrastructure/` class behind a `Domain/` interface.
    * No controllers with many methods. One route = one invokable class with
      `__invoke()`.
    * No facades, no `app()`, no service locator. Constructor injection only.
    * No `config:cache`. There is no compiled config and no compiled container.
      `runtime/cache/` holds only Psalm's cache [DEV]. Changing `.env` takes effect on
      the next request.
    * Views are plain PHP, not Blade or Twig, and they live NEXT TO their action inside
      the module - not in a central `resources/views/`.

  Key packages [CODE, composer.json]:
    yiisoft/yii-runner-http   the HTTP entry runner
    yiisoft/di                the container
    yiisoft/config            merges config/ by a plan, not by convention
    yiisoft/router            route definitions and URL generation
    yiisoft/middleware-dispatcher
    yiisoft/db, db-mysql, db-migration
    yiisoft/yii-view-renderer plain-PHP view rendering
    yiisoft/csrf, yiisoft/session, yiisoft/error-handler
    yiisoft/assets            asset bundles, content-hashed publishing
    guzzlehttp/guzzle         every outbound HTTP call
    httpsoft/http-message     PSR-7 implementation
    vlucas/phpdotenv          a PRODUCTION dependency, not dev - see 3.3
    league/commonmark         markdown rendering in chat answers
    smalot/pdfparser          PDF text extraction
    symfony/console           the `./yii` CLI

3.3 WHY PHPDOTENV IS A PRODUCTION DEPENDENCY

  It used to be a dev dependency guarded by `class_exists()`. That meant a production
  `composer install --no-dev` SILENTLY IGNORED `.env` and every setting fell back to
  its default. It is now required, loaded from a fixed path in `src/bootstrap.php`
  [CODE]. This is also what guarantees PHP-FPM and the cron worker resolve the SAME
  configuration - both run as the same user and read the same file.

3.4 FRONTEND - DELIBERATELY NO BUILD STEP

  No package.json, no webpack, no vite, no node_modules [DEV]. No React, Vue or
  jQuery. Four CSS files and four JS files, served as-is through `yiisoft/assets`:

    assets/main/admin.css              102,295 bytes - the whole design system
    assets/main/site.css                 1,245 bytes
    assets/audio-store/audio-store.css  33,645 bytes
    assets/conversion-audio/*.css         7,448 bytes

    assets/audio-store/audio-store.js  106,828 bytes

  WHY no build step: the CSP is `script-src 'self'` with no unsafe-inline and no CDN.
  A build step would add a deployment stage that can fail, for an application whose
  entire JavaScript surface is under 200 KB [CODE].

4. REPOSITORY STRUCTURE AND ARCHITECTURE
--------------------------------------------------------------------------------------

4.1 TOP-LEVEL DIRECTORIES

  public/        Web root. Only `index.php` and static assets are reachable by URL.
                 `public/assets/` holds content-hash-named published copies of
                 `assets/` - never edit anything in here, it is generated.

  src/           ALL application code. PSR-4 `App\` => `src` [CODE, composer.json].

  config/        Configuration, split by runtime (common / web / console) and merged by
                 `yiisoft/config` according to `config/configuration.php`.

  assets/        Source CSS and JS, published into `public/assets/` by the asset
                 manager on demand.

  runtime/       Everything the application writes: logs, locks, job storage, temp.
                 Never in version control.

  tests/         Codeception suites. `tests/_data/` holds fixtures including real WAVs.

  docs/          This file and its predecessors, plus deployable server configuration
                 (systemd units, cron examples, nginx configs, permission scripts).

  vendor/        Composer dependencies.

  yii            The console entry point. `./yii <command>`.

4.2 THE MODULE PATTERN - VERTICAL SLICES, NOT LAYERS

  `src/` is organised BY FEATURE, not by layer. Laravel puts all controllers together;
  this puts everything about Order58 together. A module owns its full stack:

    src/Order58/
        Domain/           interfaces, enums, value objects. NO framework, NO SQL.
        Application/      business services and orchestration
        Infrastructure/   the SQL implementations of Domain interfaces
        Client/           outbound HTTP to the Order58 platform
        Contract/         DTOs crossing the client boundary
        Console/          CLI commands
        Web/              one folder per page: Action.php + template.php

  The dependency direction is inward: Web and Console depend on Application, which
  depends on Domain. Infrastructure implements Domain interfaces and is wired in by the
  container. Domain depends on nothing.

  WHY: it means a Domain rule can be unit-tested with no database, and an
  Infrastructure class can be swapped without touching business logic. It is also what
  makes INV-2 (module isolation) enforceable at all - the boundaries are real
  directories, so a test can scan them.

4.3 THE WEB LAYER - ONE FOLDER PER PAGE

  Every page is a directory containing its action and its template:

    src/Order58/Web/Calls/
        Action.php        GET  /admin/order58/calls
        SyncAction.php    POST /admin/order58/calls/sync
        RetryAction.php   POST /admin/order58/calls/retry
        template.php      the view
        CallsAsset.php    the page's JS bundle

  There is EXACTLY ONE `template.php` per folder [CODE - verified across all
  `src/*/Web/*/` folders]. A second page means a second folder. This is why the new
  Sync History page lives in `src/Order58/Web/CallHistory/` rather than as a second
  template inside `Calls/`.

4.4 DEPENDENCY INJECTION

  Container definitions live in `config/common/di/*.php` (glob-loaded) and
  `config/web/di/*.php`. There is no service-provider registration list to edit -
  dropping a new file into the directory is enough [CODE, config/configuration.php].

  Three kinds of definition:

    1. Autowired by type. Most classes need no entry at all.
    2. Interface binding, e.g.
         CallImportRepositoryInterface::class => DbCallImportRepository::class
       (config/common/di/order58.php:54) [CODE]
    3. Scalar injection, because a bool or int cannot be autowired, e.g.
         App\Order58\Web\Calls\Action::class => [
             '__construct()' => ['importEnabled' => $params['app/order58']['recordingImportEnabled']],
         ]
       (config/common/di/order58.php:89-91) [CODE]

  `config/common/di/app-params.php` is the boundary where a raw string from
  `params.php` becomes a typed readonly object. Everything downstream is typed.

4.5 src/Shared/ - THE CROSS-MODULE SEAMS  (undocumented before this file)

  INV-2 forbids modules from naming each other. `src/Shared/` is how they talk anyway.
  Two of its sub-packages exist purely as seams and are worth understanding:

  4.5.1 src/Shared/Audio/ - the audio ingestion port

    AudioIngestionPortInterface     ingestFile(storeSourceId, path, filename,
                                               recordingType, orderId, provider,
                                               generateAiAudio, adminUserId)
    AudioIngestionOutcome           queued | rejected | unavailable

    WHY IT EXISTS: `App\Order58\Application\RecordingImportProcessor` needs to hand a
    downloaded WAV to the transcription queue. It may not name `TranscriptionQueue`,
    `RecordingType` or `TranscriptionProvider` - all live in `App\AudioToText`.

    HOW IT WORKS: every value crossing the boundary is a PLAIN STRING - 'MIXED',
    'WHISPER'. `AudioIngestionService` (inside AudioToText, which implements the port)
    re-hydrates them with `RecordingType::fromStorage()` and
    `TranscriptionProvider::fromStorage()` on its own side of the wall. An unrecognised
    value is a REJECTION, not a default - quietly transcribing with Whisper because a
    caller sent an unknown provider name would report success for a choice nobody made
    [CODE].

    A TRAP: the isolation test scans raw source, so this interface's own docblock may
    not spell `App\AudioToText`. It is worded around the namespace on purpose.

    A BUG THIS SEAM FIXED: before `AudioIngestionService` existed,
    `AudioUploadValidator` ran only in `Job/Store/Action.php`, while
    `TranscriptionQueue` enforced only duration. `Job/Store/Group/ReplaceAction.php`
    therefore bypassed the size and MIME checks in shipped code. Both callers now route
    through the service, so validation cannot be skipped by construction [CODE].

  4.5.2 src/Shared/Machine/ - resource admission  (undocumented before this file)

    MachineResourceProbeInterface   availableMegabytes(), loadAveragePerCore()
    ProcMachineResourceProbe        reads /proc/meminfo and /proc/loadavg
    ResourceBudget                  minAvailableMegabytes, maxLoadPerCore
    ResourceAdmission               decide(ResourceBudget): AdmissionDecision
    AdmissionDecision               admit() | defer(reason)

    WHY IT EXISTS: two unrelated background workers need the same two numbers with
    DIFFERENT thresholds. A transcription peaks near 904 MB and should wait for roughly
    that much again; a recording download peaks near 92 MB and must not.

    WHY THE BUDGET IS A PARAMETER: a single global threshold gets one of them wrong.
    Passing the budget in is also what keeps `ResourceAdmission` free of any module's
    settings class, which is what lets it live in `Shared` at all.

    MEMAVAILABLE, NOT MEMFREE: on a machine with several GB in page cache, `MemFree`
    reports a few hundred MB and would defer every job forever. `MemAvailable` is the
    kernel's own estimate of what a new allocation could obtain [CODE].

    WHAT DELIBERATELY STAYED IN AudioToText: `foreignWhisperRunning()` (a `pgrep -x
    whisper-cli`), `ForeignLockGuard`, and `AUDIO_WORKER_FOREIGN_LOCKS`. Those are
    questions about WHISPER, not about MACHINES. A worker that runs no whisper has no
    reason to ask and no reason to wait.

    `App\AudioToText\Domain\SystemResourceProbeInterface` now EXTENDS
    `MachineResourceProbeInterface` and adds only `foreignWhisperRunning()`. The
    extraction changed no behaviour - the pre-existing
    `tests/Unit/AudioToText/WorkerAdmissionGuardTest.php` passes UNCHANGED, which is the
    proof [CODE].

  4.5.3 The rest of src/Shared/

    Application/Correlation    CorrelationId - one id per request, added to logs
    Application/Health         HealthChecker - powers `./yii kf:health`
    Application/Time           AppTimeZone - the America/New_York business calendar
    Application/Transaction    TransactionRunnerInterface
    Domain/Clock               ClockInterface / SystemClock - so time is injectable
    Domain/ValueObject         SecretValue - a string that will not print itself
    Infrastructure/Db          DbParams, DbConnectionFactory, DbDateTime
    Infrastructure/Log         SecretRedactor (INV-13), SafeLogContext
    Infrastructure/Markdown    MarkdownRenderer for chat answers
    Infrastructure/Storage     StoragePaths
    Web/Flash                  FlashMessages
    Web/Middleware             SecurityHeaders, CorrelationId, BasePath, DomainException
    Web/Support                FormData, Redirect, AlphabetIndex

4.6 THE OTHER CROSS-MODULE TRICK - SHARING A TABLE NAME

  Where an interface is overkill, a module reads ANOTHER MODULE'S TABLE BY NAME.
  `App\Order58\Infrastructure\DbAudioProviderDefault` reads `{{%audio_to_text_settings}}`
  as a literal string precisely because it may not import
  `App\AudioToText\...\TranscriptionProvider` [CODE]. The provider then travels as the
  storage string the column holds.

5.2 TWO THINGS WORTH UNDERSTANDING

  THE ROUTER IS A MIDDLEWARE, NOT A PHASE. Everything above it in the list runs before
  any route is matched. That is why the session and CSRF cookie exist even on a 404.

  THE ACTION IS THE LAST MIDDLEWARE. `Route::action(SomeClass::class)` APPENDS the
  class to the route's middleware list (`vendor/yiisoft/router/src/Route.php:210`).
  `MiddlewareFactory` then checks `method_exists($definition, '__invoke')` and wraps it
  as `[$class, '__invoke']`, resolved from the container [CODE]. There is no separate
  "controller dispatch" step.

5.3 ORDER MATTERS IN THE MIDDLEWARE STACK

  `ErrorCatcher` is FIRST so that even an error response passes back out through the
  security-header and correlation middleware. `BasePathMiddleware` is before everything
  that reads the path or generates a URL - once the application is mounted on a prefix,
  that includes the session cookie, the error pages and every action [CODE].

5.4 ENVIRONMENT VALIDATION - WHY IT IS DIFFERENT FROM LARAVEL'S env()

  `Environment::prepare()` validates all 126 declared keys against a typed SPEC: type,
  default, min, max, and a `secret` flag [CODE]. Consequences:

    * A misspelt boolean throws AT BOOT with the key named, rather than becoming null.
    * A required key with no default (DB_USER) throws if absent.
    * `Environment::bool()` uses `filter_var(..., FILTER_VALIDATE_BOOLEAN,
      FILTER_NULL_ON_FAILURE)`, so "true"/"1"/"on"/"yes" are true, "" is false, and
      "maybe" is a startup exception.

  A TRAP THAT HAS BITTEN THIS PROJECT: `safeLoad()` deliberately IGNORES a `.env` it
  cannot read. If the web user loses read permission on `.env`, every setting silently
  falls back to its default and the first symptom is
  "Environment variable DB_USER is not set" - which points at the database and is
  nothing to do with it. The fix is an ACL, not a config change:
  `docs/deploy/grant-web-access-acl.sh` [CODE].

6. AUTHENTICATION AND AUTHORIZATION
--------------------------------------------------------------------------------------

6.1 TWO SEPARATE REALMS

  Knowledge Forge has two independent identity systems. They share a session cookie
  name but nothing else.

  ADMIN
    Table        admin_users (username, password_hash, is_active, last_login_at)
    Hashing      NativePasswordHasher - PHP password_hash() defaults. The column is
                 varchar(255) so a future algorithm upgrade is a code change, not a
                 migration [CODE]
    Login        GET/POST /login
    Middleware   RequireAdminMiddleware - RE-LOADS THE ACCOUNT FROM THE DATABASE ON
                 EVERY REQUEST. Deactivating an admin takes effect immediately, not at
                 next login [CODE]
    Throttling   auth_login_attempts, governed by AUTH_LOGIN_MAX_ATTEMPTS and
                 AUTH_LOGIN_LOCKOUT_MINUTES [CODE]
    Reaches      108 admin routes

  AGENT
    Table        order58_agents (mirrored from the Order58 platform)
    Login        GET/POST /agent/login
    Auth path    AgentLoginService calls the Order58 API. If that rejects or is
                 unreachable, it falls back to Order58ValidateCredentials (a DIFFERENT
                 host and token). Held apart so rotating one credential cannot silently
                 change the other [CODE]
    Gate         user_type == 'agent' - an Order58 user who is not an agent cannot sign
                 in here [CODE]
    Activity     agent_login_activity
    Middleware   RequireAgentMiddleware
    Reaches      25 agent routes, all chat

6.2 ROUTE PROTECTION IS STRUCTURAL

  Protection is not declared per route. It comes from the enclosing group in
  `config/common/routes.php`:

    Group::create()
        ->middleware(RequireAdminMiddleware::class)      line 66-68
        ->middleware(DomainExceptionMiddleware::class)

    Group::create()
        ->middleware(RequireAgentMiddleware::class)      line 542-544
        ->middleware(DomainExceptionMiddleware::class)

  A route added inside a group is protected WITHOUT the author writing an auth line.
  That is a feature and a hazard: a route added in the wrong place is silently public.
  Only 4 routes sit outside both groups, and all 4 are login endpoints [CODE].

6.3 DomainExceptionMiddleware

  Turns a domain-level "not found" or "not permitted" into a flash message and a
  redirect, rather than a 500 or a raw exception page. This is what lets actions throw
  a meaningful domain exception instead of assembling an error response by hand [CODE].

6.4 STORE-LEVEL PERMISSIONS

  Agents do not see every store. Visibility is driven by the agent's own Order58
  record and by `knowledge_bases.agent_access_enabled`, toggled by an admin at
  POST /admin/order58/stores/{storeId}/agent-access [CODE].

  Isolation is tested: `tests/Integration/Agent/AgentConversationIsolationTest.php`
  asserts an agent cannot read another agent's conversations [CODE].

6.5 CSRF

  `CsrfTokenMiddleware` is applied application-wide in the middleware stack, not per
  route. Every POST form renders `$csrf->hiddenInput()`; the one fetch-based POST in
  the codebase (the Audio-to-Text store page) sends an `X-CSRF-Token` header instead
  [CODE].

8.1 PAGE: Manage Order58 Calls
======================================================================================

URL            GET /admin/order58/calls
ROUTE NAME     order58.calls                          routes.php:306
ACTION         src/Order58/Web/Calls/Action.php
TEMPLATE       src/Order58/Web/Calls/template.php
ASSET          src/Order58/Web/Calls/CallsAsset.php -> assets/order58-calls/order58-calls.js
ACCESS         Admin group (RequireAdminMiddleware + DomainExceptionMiddleware)
SIDEBAR        "Order58 calls", icon phone, match `order58.calls`

WHAT
  Discovers the calls a store had TODAY from the external Order58 recording service,
  lets an administrator tick the ones wanted, and queues those recordings for
  background import into the existing Audio-to-Text pipeline.

WHY IT EXISTS
  Before it, the only route from a call recording to a transcript was: open the hidden
  diagnostic page, type a call id, download a WAV to a laptop, re-upload it by hand on
  the store's Audio-to-Text page. That is minutes of human attention per recording, and
  the human had to know the call id in advance. This page discovers the calls and does
  the fetching.

WHEN THINGS HAPPEN - THREE SEPARATE CLOCKS
  Confusing these is the main way to misread this feature.
    1. The page      - only when a human opens it. Opening it contacts NO provider.
    2. The call list - only when `?store=<id>&load=1` is present, which is what the
                       Load button submits. One outbound GET.
    3. The audio     - never in a web request. The `kf:order58:import-recordings`
                       worker does all downloading.

UI ELEMENTS
  Heading         "Manage Order58 Calls"
  Subtitle        "Bring a store's call recordings into Audio to Text. Imported
                  recordings appear on that store's own Audio to Text page, alongside
                  anything uploaded by hand."
  Header action   [View Sync History]  -> /admin/order58/calls/history   (btn--secondary)
  Breadcrumbs     Order58 Data Management / Manage Order58 Calls
  Warning banner  Shown ONLY when the feature flag is off:
                  "Recording import is turned off on this server." + the env var name
  Card 1          "Find today's calls"
                    - store <select> ("Choose a store…" + one option per active store,
                      labelled "<name> — #<sourceId>")
                    - [Load today's calls] (btn--primary)
                    - hint when no stores are mirrored yet
  Card 2          "Today's calls — <business date>"   (only after an explicit load)
                    - Select-all checkbox in the header row
                    - columns: [x] | CALL SESSION ID | CALL TIME | ORDER ID | SYNC STATUS
                    - live "n calls selected" hint
                    - transcription provider <select>
                    - [ ] "Generate clean AI audio after transcription" (unchecked
                          every render - see CONDITIONS)
                    - [Sync selected] (btn--primary; carries `disabled` when the flag
                          is off)
  Card 3          "Sync history" - store-scoped, 40 most recent calls
                    - columns: STORE | CALL | ORDER | CALL TIME | MIXED | CALLER |
                      CALLEE | OVERALL | PROVIDER | AI AUDIO | UPDATED | (actions)

TRIGGER AND FLOW - GET
  1. `storeId`    <- `/\A\d{1,9}\z/` on `?store`, then `> 0`; anything else = no store
  2. `wantsCalls` <- `load === '1' && storeId !== null`                 (Action.php:75)
  3. `usingFixtures` <- FixtureAvailability::isRequested(?source)       (Action.php:82)
     TWO conditions, both required: APP_ENV is one of the two environments allowed to
     use fixtures (checked as an ALLOW-LIST, so an unrecognised value falls through to
     the live API) AND this request carries `source=fixture`. No default, no stickiness.
  4. LIVE path: LatestCallsRequest::fromStrings(store, '200') ->
     ChannelApiProbe::latestCalls() -> TodayCallFilter::today()
  5. `statusesFor(storeId, sessionIds)` reads local import rows for the "already synced"
     column
  6. `history(storeId, 40)` reads the local tables

CONDITIONS
  - LIMIT = 200 calls requested (Action.php:52) - "well inside the provider's own
    ceiling of 500"
  - HISTORY = 40 calls (Action.php:55)
  - The store dropdown filters on `knowledge_bases.source_active`, NOT
    `order58_stores.active`. The latter is 0 for ALL 235 mirrored rows [DEV], so a
    dropdown built on it would be EMPTY. Action.php:167-168 says exactly this [CODE].
  - "Today" means the America/New_York business date from `AppTimeZone::businessDate()`,
    compared as TEXT to the leading YYYY-MM-DD of the provider's `callTime`. No timezone
    conversion is performed [CODE].
  - The AI-audio checkbox is rebuilt UNCHECKED on every render. Presence is the yes; an
    unticked checkbox posts nothing, which is what makes "off" the reliable default
    rather than something the form has to remember.

DATA READ    knowledge_bases, order58_stores, order58_call_imports,

DATA WRITTEN nothing - GET is entirely read-only

FAILURE PATH
  A transport failure is CAUGHT, not allowed to 500 (Action.php:143). The page still

RELATED FILES   Action.php, SyncAction.php, RetryAction.php, template.php,

   #  line  check                              failure message
   1   :82  store matches /\A\d{1,9}\z/, > 0   "Choose a store first."

  NOTE THE ORDER: the flag gate (2) runs BEFORE the re-fetch (7), so a disabled server
  makes no outbound request at all when someone posts to this endpoint.

WHY STEP 7 EXISTS (INV-9)
  It costs one extra HTTP request per Sync click and removes a class of problem:
    - a forged id would otherwise become a path segment in an outbound fetch
    - a stale tab's ids would queue work for calls that no longer exist
    - the call's `callTime` is taken from the FRESH answer, never from the form, and
      it decides the date the recording is fetched with

  `selectedIds()` (:285) is SHAPE ONLY - `/\A\d{1,20}\z/` per value. Its own comment
  says it "just keeps obvious rubbish out of an IN clause"; the intersection is the
  check that matters.

WHAT IT WRITES
  One `order58_call_import_batches` row:
    store_source_id, triggered_by='MANUAL', requested_by_admin_id=CurrentAdmin id,
    transcription_provider, generate_ai_audio, recording_company (SNAPSHOT), created_at
  Then up to three `order58_call_imports` rows per accepted call, status='PENDING',
  one per channel, in the order mixed, caller, callee (which is what makes the worker
  process mixed first).

ALL THREE CHANNELS, EVERY TIME (SyncAction.php:213)
  `RecordingChannel::all()`. Which channels a merchant actually produces is the
  provider's answer to give; a 404 on caller or callee is recorded as "Not available"
  rather than guessed at in advance.

PRESSING SYNC TWICE IS SAFE
  `queueCall()` inserts and catches `IntegrityException` on the unique key, so an
  already-requested call is SKIPPED, not refused. The flash says so:
  "Nothing new to queue — all N selected call(s) had already been requested." /
  "N call(s) queued. ... M had already been requested."

  Retry posts a store id and redirects back to THAT STORE'S calls page. A button on an

  calls are retried from their own store's page [CODE].

THE PAGINATION PROBLEM - WHY NEW CODE WAS NEEDED
  This is the most subtle thing on the page and it is worth understanding.

  ONE CALL IS UP TO THREE ROWS in `order58_call_imports` (one per channel), but the
  table shows ONE ROW PER CALL with a column per channel. The store-scoped
  `history()` over-fetches rows (`LIMIT $limit * 3`) and groups them in PHP, stopping
  once it has enough calls. That is sound for a fixed peek and UNUSABLE for paging:

    An OFFSET counted in ROWS lands mid-call. The same call appears at the bottom of
    one page and the top of the next, each copy showing only SOME of its channels -
    and every status on both copies looks perfectly plausible. Nobody reports it as a
    bug; they just quietly read the wrong numbers.

  So `historyPage()` selects the PAGE OF CALLS first and fetches rows afterwards:
    1. COUNT(DISTINCT store_source_id, call_session_id)     - the total
    2. GROUP BY store_source_id, call_session_id
       ORDER BY MAX(id) DESC LIMIT/OFFSET                   - this page's identities
    3. fetch every channel row for those identities         - via the shared itemQuery()

  THREE QUERIES regardless of page size. No N+1, no query per store, nothing loaded
  into memory and sliced in PHP. The grouping loop is shared with `history()` so a
  column added to the table appears on both pages and they cannot drift [CODE].

  A YII QUERY-BUILDER TRAP FOUND HERE: `->select('COUNT(DISTINCT a, b)')` is read as a
  COLUMN NAME and quoted into `COUNT(DISTINCT AS \`a\`, \`b\`)` - a syntax error. Same
  for `->orderBy(['MAX(id)' => SORT_DESC])`. Both need `new Expression(...)` [CODE].

RELATED TESTS  tests/Web/Order58CallHistoryCest.php (12 tests, 44 assertions), including
               `pagingSplitsCallsNeverChannels` which creates 26 calls over a
               25-per-page table and asserts the one call pushed onto page 2 appears
               there IN FULL and not on page 1.

DEFAULT FILTER - "Uploaded audio", applied as page policy

  When the `audio` query parameter is COMPLETELY ABSENT the page defaults to
  StoreAudioFilter::WithAudio (`?audio=with`). Anything present is parsed exactly as it
  always was.

      absent                -> WithAudio   (the new default)
      ?audio=with           -> WithAudio
      ?audio=all            -> All         (unchanged; every bookmark keeps working)
      ?audio=<unrecognised> -> All         (unchanged enum fallback)

  WHY IN THE ACTION AND NOT IN THE ENUM: `StoreAudioFilter::fromRequest()` cannot tell
  "no filter was asked for" from "a filter was asked for and we do not know it" - both
  arrive as a string it does not recognise. Those are different questions and only one
  should land on Uploaded audio. Changing the enum's fallback would make `?audio=typo`
  silently mean Uploaded audio, which is a second decision smuggled in behind the first.
  So the enum keeps `All` as its neutral value and `Action::audioFilter()` applies the
  page's policy on ABSENCE alone [CODE].

  WHY THE DEFAULT CHANGED: of the mirrored stores only a handful have ever had a
  recording uploaded, so landing on All stores showed an administrator mostly stores
  with none.

  FILTER SEMANTICS ARE UNCHANGED. "Uploaded audio" still means "has at least one row in
  `audio_conversations`", via `StoreAudioCountsInterface::storesWithAudio()`, which was
  not touched. It is still applied as an id restriction INSIDE the directory query, so
  rows, total and letter counts narrow together.

CARD BREAKDOWN - Mixed / Caller / Callee / Other

  The top-right pill is still TOTAL and still means conversions in
  `audio_conversations`. Below the store meta a four-cell strip shows how that total
  splits by `audio_conversations.recording_type`.

  Total is deliberately NOT repeated in the strip: the same number in two places is two
  places that can disagree.

  TOTAL IS NOT MIXED + CALLER + CALLEE, and never will be. `recording_type` is NULLABLE
  and three populations legitimately carry no type:

    1. Every conversation created before the column existed
       (M260921100000AddConversationRecordingType, 21 Sep 2026). On the dev database
       that was 46 of 59 rows at the time of writing [DEV].
    2. A SEPARATE (Customer + Agent) upload. None of MIXED/CALLER/CALLEE describes a
       pair, and the conversation's `mode` already says what it is [CODE].
    3. A COMMON upload whose posted recording type was not one of the three allowed
       values. Deliberately not an error - refusing the recording would let a stale open
       tab cost somebody their upload over a caption [CODE].

  So the fourth cell is `Other`, defined as:

      Other = total - mixed - caller - callee          (clamped at zero)

  DERIVED, not selected, so the four values cannot disagree with each other. Counting
  null as Mixed would claim a channel the uploader never stated, and would still look
  entirely plausible on screen - which is why
  `tests/Integration/Order58/StoreAudioCountsTest.php` asserts it explicitly.

  The `Other` cell carries a title explaining it covers recordings without a
  MIXED/CALLER/CALLEE type, including older recordings and separate Customer + Agent
  uploads.

QUERY - still ONE for the whole page

  `DbStoreAudioCounts::countsFor()` gained three conditional aggregates on the SAME
  grouped scan that already produced the total:

      SELECT store_source_id,
             COUNT(*)                        AS total,
             SUM(recording_type = 'MIXED')   AS mixed,
             SUM(recording_type = 'CALLER')  AS caller,
             SUM(recording_type = 'CALLEE')  AS callee
      FROM audio_conversations
      WHERE store_source_id IN (:page_ids)
      GROUP BY store_source_id

  The round-trip count did not change: one query for a page of up to 36 stores, guarded
  by a test that measures MySQL's own `Questions` counter. `Expression` is required -
  the builder reads a bare string in `select()` as a column name and quotes it into a
  syntax error. Returns `array<int, StoreAudioBreakdown>`; an absent key and a zero mean
  the same thing, so stores with nothing are omitted.

CSS  `.store-card__audio*` in assets/main/admin.css - a four-column grid (`1fr` each) so
     values align down the whole card grid, always rendered with zeros so cards keep one
     height, collapsing to two columns under 420px. Zeros carry
     `.store-card__audio-value--zero` because CSS cannot match on a number's value.

8.3 THE o58-wide LAYOUT PATTERN        [NEW - missing from all prior documentation]
======================================================================================

PROBLEM
  `.content` is capped at `max-width: 1240px` (assets/main/admin.css:862). The two
  Order58 call tables carry eleven columns. On a 1920px screen ~1592px is available
  after the 248px sidebar and gutters, so ~350px of usable width was being discarded.
  Worse, `.table { width: 100% }` with no `min-width` and no `white-space` rule means
  the browser COMPRESSES columns and wraps text rather than overflowing - store names
  broke over two lines, timestamps over four.

  `.table-wrap` already had `overflow-x: auto` (admin.css:274). Scrolling inside the
  card always worked; it never TRIGGERED, because the table shrank itself to fit first.

SOLUTION - THE PROJECT'S OWN EXISTING PATTERN
  Audio-to-Text solved this first (admin.css:1381):
      .content:has(.a2t-wide) { max-width: 1600px; }
  A marker class on the page's own card, plus `:has()`. Scoped by construction - it
  cannot reach another page - and needs NO change to `layout.php`.

  The Order58 equivalent (admin.css, placed BEFORE the "Audio to Text" marker comment
  so it stays outside the CSS isolation test's scanned region - see INV-15):

      .content:has(.o58-wide)             { max-width: 1680px; }
      .main:has(.o58-wide) .topbar__inner { max-width: 1680px; }
      .o58-table                          { min-width: 1100px; }
      .o58-table th, .o58-table td        { white-space: nowrap; }
      .o58-table .field__hint             { white-space: normal; }

  1680 rather than 1600: this table has one more column, and 1680 is what a 1920px
  screen can actually give.

  The breadcrumb bar widens too, via `.main:has(...)`, because widening only `.content`
  leaves the header visibly offset from the page below it. Both are children of `.main`,
  which is what makes that selector reachable.

  `nowrap` is what TRIGGERS the scroll: holding cells on one line makes the table take
  its natural width, at which point the existing `overflow-x: auto` does its job and
  the CARD scrolls - never the page. Hints stay wrapping because a channel cell can
  hold a truncated provider error, and one that could not wrap would widen the whole
  table to fit a single row.

  REUSED BY: `src/Order58/Web/Calls/template.php` (history card) and
  `src/Order58/Web/CallHistory/template.php`.

9.2 THE THREE TRUE WORKERS

--------------------------------------------------------------------------------------
9.2.1  kf:audio:worker  - transcription
--------------------------------------------------------------------------------------
  CLASS      src/AudioToText/Console/AudioTranscriptionWorkerCommand.php
  QUEUE      audio_transcription_jobs (status QUEUED)
  LOCK       runtime/audio-to-text/worker.lock (flock, held for the whole process)
  OPTION     --once : claim at most ONE job, process it, exit

  ORDER OF OPERATIONS (this order IS the design):
    :132  acquireLock()             -> held? warn + exit OK (a refused duplicate is the
                                       guarantee working, not a fault)
    :139  reportConfiguration()     -> unusable config? release + exit DATAERR
    :163  housekeeping (every 300s)
    :168  admission->decide()       -> DEFER: log `audio_worker_deferred`, exit/sleep
    :190  foreignLocks->acquire()   -> DEFER: log `audio_worker_foreign_lock`
    :210  jobs->claimNextQueued()   <-- THE CLAIM, after every gate
    :227  process()

  ADMISSION (WorkerAdmissionGuard -> Shared\Machine\ResourceAdmission)
    AUDIO_WORKER_MIN_AVAILABLE_MB  default 1500  ("1.8x the measured 834 MB whisper
                                                   peak" - .env.example)
    AUDIO_WORKER_MAX_LOAD_PER_CORE default 1.5
    AUDIO_WORKER_YIELD_TO_OTHER_WHISPER default true - `pgrep -x whisper-cli`,
      explicitly "best-effort and racy by construction", never an exclusivity claim

  FOREIGN LOCK COORDINATION - the interesting one
    AUDIO_WORKER_FOREIGN_LOCKS is a comma-separated list of OTHER PROJECTS' lock files.
    `ForeignLockGuard` takes an exclusive non-blocking flock on THAT SAME FILE, opened
    'r' so it is never created. Both projects end up in one kernel-arbitrated queue:
    "There is no window, because flock(2) has no window" [CODE].
    On this machine it points at telecom-billing's cron-worker.lock [DEV].
    FAILS CLOSED: held, missing OR UNREADABLE all defer. The unreadable case is not
    hypothetical - the other project's runtime dir is 0750 www-data:www-data, so a
    worker started as any other user defers EVERY tick. The worker prints an explicit
    warning naming the path at startup rather than stalling silently [CODE].

  A JOB NOT ADMITTED STAYS QUEUED. Not failed, not retried, not counted (INV-6).

--------------------------------------------------------------------------------------
9.2.2  kf:audio:tts-worker  - AI training audio
--------------------------------------------------------------------------------------
  CLASS      src/AudioToText/Console/AudioTtsWorkerCommand.php
  QUEUE      audio_tts_renditions (status QUEUED)
  LOCK       runtime/audio-to-text/tts-worker.lock
  STALE      a rendition in GENERATING past its window is presumed abandoned

  WHY IT IS A SEPARATE COMMAND FROM THE TRANSCRIBER
    The transcriber processes at most ONE job per tick. Generating speech inside it
    would spend a transcription slot and HALVE the rate at which recordings turn into
    text. The two also do not compete for anything: transcription is CPU-bound (one
    core for 90-400s), this is network-bound on HTTPS with one short ffmpeg encode at
    the end. They run side by side [CODE].

  WHAT IT TAKES AND DELIBERATELY DOES NOT
    DOES take WorkerAdmissionGuard - "a machine under memory or load pressure should
      not have a second worker cheerfully adding to it just because its own work is
      cheap" [CODE]. This is the precedent the Order58 importer follows.
    Does NOT take ForeignLockGuard - that lock coordinates with other projects running
      WHISPER. This runs none, so waiting on it would defer ticks for no reason.
    Does NOT write audio_worker_heartbeat - that table is single-row with a
      CHECK (id = 1); writing it here would make the admin status strip report TTS
      ticks as transcription ticks, corrupting a surface that is currently correct.
    Does NOT read AudioToTextSettings::problems() - a mistyped voice name has no
      business stopping every transcription on the machine.

9.2.3  kf:order58:import-recordings  - recording import
--------------------------------------------------------------------------------------
  CLASS      src/Order58/Console/ImportRecordingsCommand.php
  QUEUE      order58_call_imports (status PENDING)
  LOCK       runtime/locks/order58-import.lock (flock, mode 'c', NEVER unlinked)
  CONSTANTS  STALE_AFTER_SECONDS = 900, IDLE_SLEEP_SECONDS = 5
  FLAG       ORDER58_RECORDING_IMPORT_ENABLED (default FALSE)

  EXECUTION ORDER
    1. flag off              -> "Order58 recording import is disabled (...)" + exit OK
    2. TMPDIR unusable       -> error + exit DATAERR   (see WHY below)
    3. acquireLock() failed  -> warning "Another Order58 recording import is already
                                running." + exit OK
    4. recoverStuck(900)     -> anything FETCHING for >15 min returns to PENDING
    5. loop:
         admission->decide(budget)  -> DEFER: log `order58_import_deferred`, exit OK
         processor->processNext()
       with `--once`, break after one iteration either way
    6. "Processed N recording(s)."

  WHY THE TMPDIR CHECK EXISTS
    The downloader writes to `sys_get_temp_dir()` and the hand-off is a `rename()`,
    which FAILS ACROSS FILESYSTEMS. A TMPDIR that does not exist is NOT an error
    `tempnam()` reports - it silently falls back to the system /tmp, undoing the one
    setting that keeps the download on the same filesystem as its destination. The
    command refuses to start rather than quietly undoing it [CODE].
    The resolved path is INJECTED (not read inline) because PHP caches
    `sys_get_temp_dir()` for the process lifetime, so a test cannot move it with
    `putenv()`. The container resolves it with the same call the downloader makes.

  ADMISSION BUDGET - DELIBERATELY SMALL
    ORDER58_IMPORT_MIN_AVAILABLE_MB   default 350
    ORDER58_IMPORT_MAX_LOAD_PER_CORE  default 1.5
    350 is ~3.8x the measured tick peak. It is deliberately far below the transcription
    worker's 1500, which guards a 904 MB whisper job. Applying THAT number here would
    make a 92 MB download wait for a gigabyte - and because the gate fails closed, on a
    small server that means waiting INDEFINITELY [CODE].
    It does NOT take ForeignLockGuard or the whisper pgrep: it runs no whisper.

  MEASURED PROFILE [DEV]
    empty tick, peak RSS                     43.9 MB
    PHP heap while streaming a 30 MB WAV      2.0 MB  (independent of file size)
    ffprobe child, header only               47.6 MB, 0.06 s
    realistic tick peak (parent + child)      ~92 MB
    for comparison, one whisper job          904.4 MB

9.3 THE DRAINER - kf:worker:run

  CLASS    src/Worker/Console/RunWorkerCommand.php
  LOCK     runtime/locks/worker.lock (FlockWorkerLock inside the command, and the cron
           wrapper is documented to take THE SAME FILE - unusual, and deliberate: it
           means a manual `sudo -u www-data ./yii kf:worker:run` cannot collide with a
           cron run either) [CODE, docs/deploy/worker.md:28-35]
  OPTION   --limit=N  caps items PER DRAINER (default DOCUMENT_WORKER_BATCH_SIZE)
  EXITS    0 healthy / nothing to do / lock held
           1 an item failed (expected, visible in the UI)
           70 infrastructure fault (e.g. database unreachable)

  The exit code split exists so monitoring can tell "a document failed" from "the box
  is broken" [CODE].

  WHAT IT DRAINS: provision vector stores -> process documents into the index ->
  clean up remote files after a delete or re-index. Each pass does a SINGLE poll of the
  provider per document and then defers; a document reaches `ready` over several cheap
  runs rather than one long one. It never sleeps waiting on OpenAI [CODE].

  IT DELIBERATELY DOES NOT DRAIN TRANSCRIPTION OR RECORDINGS (INV-16). The comments in
  `config/console/commands.php` state why for each: a transcription holds one core for
  ~94 seconds, and a recording import downloads megabytes over a third-party network
  and then waits on the audio pipeline. Either inside the shared loop would stall
  document processing and Order58 sync behind it.

9.4 THE ONE-SHOT SCHEDULERS

  kf:order58:schedule-knowledge / -rules / -agents
    Enqueue-only. Each inserts ONE `integration_sync_runs` row, idempotent per New-York
    calendar day, and returns. They do NO Order58 or OpenAI work - the per-minute
    drainer picks the row up. Separate jobs with separate run records and separate
    freshness, so a rules failure never affects knowledge [CODE].
    Idempotency: UNIQUE(sync_type, ny_date) in `order58_daily_sync_schedules`
    guarantees AT MOST ONE successful scheduled run per type per NY day - which is what
    makes running them HOURLY safe as a downtime catch-up.

  kf:order58:reconcile-active
    Repairs stale mirror active-status. Idempotent.

  kf:documents:recover
    Requeues documents stuck in `processing` past DOCUMENT_PROCESSING_TIMEOUT_MINUTES.
    The drainer also does this automatically each pass; this is the manual escape hatch.

  kf:ai:reconcile
    Resolves non-idempotent OpenAI operations left ambiguous by a lost response,
    ADOPTING the existing remote object instead of creating a duplicate [CODE].

  kf:rules:* - three maintenance commands for the rule catalog and its projections.
  chat:* - two read-only reporting commands.

9.5 LOCK FILE INVENTORY - ALL OF THEM

  runtime/locks/worker.lock                       document drainer (app + cron wrapper)
  runtime/locks/worker-cron.lock                  legacy artifact, July [DEV]
  runtime/locks/order58-import.lock               importer, INTERNAL
  runtime/locks/order58-import-cron.lock          importer cron wrapper (fallback only)
  runtime/locks/order58-schedule.lock             the daily schedulers
  runtime/audio-to-text/worker.lock               transcription, INTERNAL
  runtime/audio-to-text/tts-worker.lock           TTS, INTERNAL
  runtime/audio-to-text/cron-worker.lock          transcription cron wrapper (fallback)
  <other project>/runtime/audio-to-text/cron-worker.lock   FOREIGN, read-only

  THE RULE (INV-5): a cron wrapper's lock and the application's own lock MUST BE
  DIFFERENT FILES. Point the wrapper at the app's own file and cron takes it first,
  then PHP fails to acquire it, and EVERY RUN SKIPS - silently, because `flock -n`
  exits 1 with no output.

  Lock files are never unlinked. Removing one races with a process that has already
  opened the same path and is about to lock an inode that no longer has a name [CODE].

9.6 SCHEDULING - CONSOLIDATED

  THE PROJECT'S CHOSEN MECHANISM IS SYSTEMD TIMERS.
  `docs/AUDIO_TO_TEXT.md:263-265` states it outright: "The chosen scheduler is a systemd
  timer firing every 2 minutes. Cron remains in the repository only as a fallback for a
  host without systemd. Run one or the other, never both, and never alongside a
  permanent foreground worker."

  WHY A TIMER RATHER THAN CRON: `nice`/`ionice` are PRIORITY controls, not limits - on
  an otherwise idle machine a niced job still takes a whole core. The unit's cgroup
  settings are ceilings the kernel enforces. A timer also needs no outer lock file,
  because systemd will not start a second run of a unit that is still active [CODE].

  TASK                        TRIGGER            FREQ     COMMAND
  -------------------------   ----------------   ------   ---------------------------
  Audio transcription         systemd timer      2 min    kf:audio:worker --once
  AI training audio (TTS)     systemd timer      5 min    kf:audio:tts-worker --once
  Order58 recording import    systemd timer      2 min    kf:order58:import-recordings
                                                          --once
  Document/OpenAI drainer     cron (documented)  1 min    kf:worker:run --limit=1
  Order58 knowledge schedule  cron + CRON_TZ     02:00 NY kf:order58:schedule-knowledge
  Order58 rules schedule      cron + CRON_TZ     03:00 NY kf:order58:schedule-rules

  UNIT FILES IN THE REPO (docs/server/systemd/) - six files, three pairs:
    knowledge-forge-audio-worker.service / .timer
    knowledge-forge-audio-tts-worker.service / .timer
    knowledge-forge-order58-import.service / .timer

  EVERY UNIT FILE CARRIES THE SAME HEADER: "EXAMPLE ONLY - NOT INSTALLED. Nothing in
  this project writes to /etc/systemd." Installation is a deliberate act [CODE].

  RESOURCE CEILINGS, ALL DERIVED FROM MEASUREMENT:

    unit                        CPUQuota  MemoryHigh  MemoryMax  Timeout  Nice
    -------------------------   --------  ----------  ---------  -------  ----
    audio-worker                  100%      1200M       1600M     1200s    15
    audio-tts-worker               25%       256M        512M      900s    15
    order58-import                 25%       192M        256M      300s    15

    audio-worker: CPUQuota=100% because whisper measured 99% of one core at -t 1, and
    every stage is pinned to a single thread by AUDIO_TRANSCRIPTION_THREADS.
    MemoryHigh=1200M is 1.45x the 833.9 MB peak (throttles by reclaiming);
    MemoryMax=1600M is 1.9x (the OOM backstop). TimeoutStartSec=1200 MUST exceed
    AUDIO_TRANSCRIPTION_TIMEOUT (600) + AUDIO_DIARIZATION_TIMEOUT (300) = 900s worst
    case, or systemd kills a job that is merely slow before either child gives up.

    order58-import: sized from the ~92 MB measurement, not from the machine. The point
    is not to ration a 44 MB process - it is that PHP's CLI memory_limit is -1, so the
    cgroup is the ONLY backstop if a future regression buffers a whole response instead
    of streaming it.

  TIMER STAGGERING
    audio-worker      OnBootSec=2min  OnUnitActiveSec=2min  Accuracy=10s  Random=15s
    audio-tts-worker  OnBootSec=4min  OnUnitActiveSec=5min  Accuracy=30s  Random=30s
    order58-import    OnBootSec=6min  OnUnitActiveSec=2min  Accuracy=30s  Random=30s

    The boot offsets separate the FIRST ticks. `OnUnitActiveSec` re-phases from each
    activation, so two units on the same cadence drift into alignment eventually -
    `RandomizedDelaySec` is what actually stops them sharing a second, and it also
    spreads them against another project's on-the-minute cron [CODE].

    `Persistent=false` on all three: missed ticks are NOT made up after downtime.
    Queued work is still in the table and the next ordinary tick collects it; replaying
    a backlog of timer events would only bunch up work for no benefit.

  PrivateTmp
    Set on the two audio units. DELIBERATELY NOT SET on order58-import, because that
    one renames a file out of the temp directory and a private /tmp makes the
    filesystem relationship unpredictable. `Environment=TMPDIR=<runtime>/tmp` solves
    the same isolation problem with no ambiguity [CODE].

  WHAT IS ACTUALLY INSTALLED - CAREFUL READING REQUIRED

    [DEV] On the development machine, `systemctl list-unit-files` shows the two audio
          timers installed and enabled and firing; the order58-import timer is NOT
          installed. `/etc/cron.d/` contains no Knowledge Forge entry, and the root
          crontab's Knowledge Forge lines are all commented out.

    [UNVERIFIED-PROD] NONE of that describes production. The production crontab,
          installed units and www-data crontab were not inspected. Reading the dev
          state as production state would be a serious error.

    [PROD-OBS] Screenshots of joymeal.seawolf.io show Order58 call imports in
          Completed/Imported states with WHISPER and DEEPGRAM providers, so the import
          pipeline demonstrably runs there. HOW it is scheduled there is

      `CallSummary` reads EXACTLY THREE FIELDS and ignores everything else the provider
      sends: callSessionId, callTime, orderId. Ignoring the rest is deliberate - an
      added provider field cannot break this page [CODE].

  ENDPOINT 2 - fetch one recording (CONFIRMED WORKING)
      mixed  : GET {BASE}/fetch/{callSessionId}?time=&company=&name=
      caller : GET {BASE}/fetch/{callSessionId}-caller?time=&company=&name={id}-caller
      callee : GET {BASE}/fetch/{callSessionId}-callee?time=&company=&name={id}-callee

      TWO PROVIDER FACTS ENCODED HERE, both confirmed by the client on 21 Sept 2026 and
      both easy to get wrong:
        * THE CHANNEL SUFFIX BELONGS IN THE PATH, NOT IN `name`. A bare path returns
          the MIXED recording with a 200 - which reads as success.
        * `name` CARRIES NO EXTENSION. The provider appends one, so sending
          "22359279-caller.wav" produces "22359279-caller.wav.wav" on disk. This is the
          entire reason `downloadNameFor()` is a separate method from `fileNameFor()`.
      Two other readings of the caller/callee contract were tried and REJECTED; both
      arms are still written out in full in the same `match` so the difference stays
      visible where it matters rather than living in a commit message [CODE].

  AUTHENTICATION - THERE IS NONE
      ChannelApiProbe sends: connect_timeout 10, timeout 60, Accept: application/json,
      http_errors=false (a 4xx is data to classify, not an exception),
      allow_redirects=true, stream=true (so a large WAV is never held in memory).
      NO Authorization header, no API key, no token.
      ACCESS IS CONTROLLED BY THE CLIENT'S SERVER-SIDE IP ALLOWLIST [CODE].

      CONSEQUENCES, and this is the most important operational fact about the feature:
        * It cannot be made to work by configuring a credential.
        * From a non-allowlisted machine every call fails with a 403 whose body says
          so - classified as `ip-not-whitelisted` and carried into the history row, so
          an administrator reads "ask the client to whitelist this IP" rather than a
          stack trace.
        * A LOCAL FAILURE THEREFORE PROVES NOTHING ABOUT THE API.

      This is a DIFFERENT API from the main Order58 data API, which does use
      ORDER58_API_TOKEN. That token is not sent here and is not involved at all.

10.3 CLASSIFYING THE PROVIDER'S ANSWER

  `ChannelDiagnosis` turns (status, content-type, body sample, bytes) into one of
  SIXTEEN named kinds, stored verbatim in `order58_call_imports.error_code` [CODE]:

    ok                 ip-not-whitelisted   forbidden         unauthorized
    not-found          timeout              connection-failed empty-body
    not-audio          truncated            server-error      unexpected-status
    not-configured     rate-limited         invalid-json      no-calls

  The column is varchar(64) and NOT an enum, precisely so adding a diagnosis kind does
  not need a migration [CODE].

10.4 RETRY CLASSIFICATION  (RecordingImportProcessor::recordFetchFailure, :180)

  Checked in this order:

  (1) 404 on a channel that is NOT mixed -> NOT_AVAILABLE, TERMINAL, NEVER RETRIED
      error_message: "This merchant does not produce a separate Caller recording."
      The MIXED channel gets no such grace - every account is supposed to have one - so
      a 404 on mixed falls through to (3).

  (2) kind in TRANSIENT -> giveUpOrRetry()
      timeout | connection-failed | rate-limited | server-error | truncated
      `truncated` is in this list because a cut-short download is exactly the kind of
      thing that succeeds on a second attempt.

  (3) everything else -> FAILED, terminal
      unauthorized, forbidden, ip-not-whitelisted, not-audio, empty-body,
      unexpected-status, not-configured, and 404-on-mixed.
      The diagnosis ADVICE is appended to the headline, because it is the only part an
      administrator can act on.

  BACKOFF (giveUpOrRetry, :227)
      MAX_BACKOFF_SECONDS  = 3600
      BASE_BACKOFF_SECONDS = 60
      maxAttempts          = ORDER58_RECORDING_IMPORT_MAX_ATTEMPTS (default 3)

      if (attempts + 1 >= maxAttempts)  -> markSettled(FAILED)
      else  next_attempt_at = now + min(3600, 60 * 2 ** attempts)
      i.e. +60s, +120s, +240s ... capped at one hour.

      Deliberately the same shape as IntegrationSyncDrainer, so two background features
      do not answer "how long before we try again" differently [CODE].

  EVERY STORED MESSAGE IS REDACTED (INV-13)
      SecretRedactor::redactAndTruncate($message, 1000), matching the column width.
      Provider response bodies are never stored raw; no file path, no stack trace and
      no token reaches the column, because that string is rendered on an admin page.

10.5 THE DOWNLOAD ITSELF  (RecordingDownloader)

  SAMPLE_BYTES = 8192    enough for a RIFF/WAVE header and a readable error page
  CHUNK_BYTES  = 262144  the streaming read size

  1. build ChannelRecordingRequest from the item. `merchantId` is set to the store id
     and is NOT SENT - the recording endpoint takes no merchant parameter - but the
     request object validates it, so it is given the store it belongs to rather than a
     blank [CODE].
  2. ChannelApiProbe::open(), streamed. A transport throw becomes a diagnosis.
  3. Non-2xx: read a BOUNDED 8 KB sample and stop, so an allowlist refusal is still
     recognisable from the provider's own wording without buffering an error page.
  4. 2xx: tempnam(sys_get_temp_dir(), 'kf-o58-'), chunked copy while counting bytes.
  5. WavSignature::inspect - a 200 that is HTML, or a WAV cut short, is CLASSIFIED
     rather than passed on.
  6. EVERY FAILURE @unlinks ITS OWN TEMP FILE (:104, :137, :158). A partial download is
     never handed on, so no caller can ingest a truncated recording and there is no
     cleanup path for anyone to forget [CODE].

  MEMORY: streaming a 30 MB file costs PHP 2.0 MB of heap, INDEPENDENT of file size.
  Reading the same file whole costs 32 MB [DEV, measured]. The hand-off is a `rename()`
  (httpsoft UploadedFile takes that branch under CLI when constructed from a path), so
  it is a metadata operation on one filesystem.

10.6 THE HAND-OFF AND ITS LIMITS

  `AudioIngestionService::ingestFile()` in order:
    - RecordingType::fromStorage() + TranscriptionProvider::fromStorage(); an
      unrecognised value is a REJECTION, not a default
    - path must be a readable file, else `unavailable` (transient)
    - size > 0, else rejected("The downloaded recording is empty.")
    - wrap as UploadedFile(path, size, UPLOAD_ERR_OK, basename, 'audio/wav')
    - AudioUploadValidator::validate() THEN TranscriptionQueue::enqueueConversation()
      (validation must be first: getStream() throws after moveTo())

  LIMITS AN IMPORTED RECORDING GETS NO EXEMPTION FROM
    extensions                          wav, mp3, m4a, ogg, webm
    AUDIO_TRANSCRIPTION_MAX_SIZE        31457280 (30 MB) [DEV value]
    AUDIO_TRANSCRIPTION_MAX_DURATION    300 s    [DEV value]
    Over either -> TOO_LARGE with the measured `bytes` as evidence, and NEVER retried:
    it would be exactly as big next time. Raising the limits is not a decision the
    importer is authorised to make on its own [CODE].

  THE CHANNEL MAPPING THAT MUST NEVER DRIFT (INV-10)
    RecordingImportProcessor::recordingTypeFor() is a literal three-arm match:
      Mixed -> 'MIXED'   Caller -> 'CALLER'   Callee -> 'CALLEE'
    written out rather than shared, because the two modules may not name each other's
    enums. They happen to agree on all three names.
    CALLER IS NEVER REWRITTEN AS "CUSTOMER". It cannot be, because nothing in this path
    produces a speaker role at all: every conversation is enqueued with mode=COMMON and
    source_role=COMMON. Who spoke is decided later, by diarization, and confirmed by a
    human [CODE].

10.7 QUEUE BACK-PRESSURE

  AUDIO_TRANSCRIPTION_MAX_QUEUE caps QUEUED+PROCESSING jobs installation-wide.
  0 = unlimited (the shipped default; this dev box is set to 20 [DEV]).

  WHY IT MATTERS FOR THIS FEATURE: a human uploading by hand cannot outrun the worker.
  The importer can - at one recording per 2-minute tick it produces up to 30 items an
  hour, while the worker drains roughly 20 (measured: avg 122 s of audio, whisper RTF
  1.19) [DEV].

  REACHING THE CAP LOSES NOTHING. `AudioTranscriptionException::queueFull()` does NOT
  set `recordingIsUnusable`, so `AudioIngestionService` maps it to `unavailable` =
  TRANSIENT, and the Order58 item is requeued with exponential backoff, succeeding once
  the queue drains [CODE]. The only cost is a re-download on the next attempt, because
  the cap is checked AFTER the file has been moved into the job directory.

  A manual upload that hits the cap is refused with "The transcription service is
  currently busy. Please try again later."

10.8 THE FEATURE FLAG - THREE ENFORCEMENT POINTS

  ORDER58_RECORDING_IMPORT_ENABLED, default FALSE (Environment.php:134).

  Chain: .env -> Environment SPEC -> config/common/params.php:209 ->
         config/common/di/order58.php:64 (command), :71 (page), :74 (sync action)

  (a) THE PAGE says so       Action.php:112 -> template banner + `disabled` on Sync
  (b) THE SYNC ENDPOINT refuses   SyncAction.php:93 - BEFORE selection parsing, BEFORE
      the company resolver, BEFORE any write. THIS IS THE REAL GATE.
  (c) THE WORKER exits       ImportRecordingsCommand.php:92, returns OK not error, so a
      cron entry left in place on a disabled server does not fill a mailbox

  CAN A USER BYPASS IT? NO.
    - crafted POST with a valid session and CSRF  -> refused at (b), zero rows written
    - a form rendered before the flag was turned off -> same refusal
    - re-enabling the disabled button in devtools  -> `disabled` is cosmetic; the
      backend refuses

  WHAT THE FLAG DOES NOT GATE: rendering the page, and loading the call list. Both are
  read-only, and confirming the server can reach the provider is exactly what you want
  to do BEFORE enabling import [CODE].

  NO CACHE COMMAND IS NEEDED AFTER CHANGING IT. There is no compiled config and no
  container cache. The next request and the next `--once` run both re-read it. A
  long-running worker started WITHOUT `--once` holds the value it booted with - which
  is one more reason not to run one.

11.1 THE TWO UPLOAD SHAPES

                   speaking. This is what Order58 imports always produce.
  SEPARATE         two files, customer and agent, already split at source. Speaker

  ConversationMode = COMMON | SEPARATE
  SourceRole       = COMMON | CUSTOMER | AGENT

11.2 STATUS LIFECYCLE

  audio_transcription_jobs.status  (JobStatus)
      QUEUED -> PROCESSING -> COMPLETED | FAILED

  audio_conversations.status  (ConversationStatus) - DERIVED from its children
      QUEUED | PROCESSING | COMPLETED | PARTIALLY_COMPLETED | FAILED
      `ConversationStatus::fromChildren()` aggregates job statuses into one row on the
      store page. The Order58 CallImportOutcome aggregation deliberately mirrors this
      shape so nobody has to learn a second one [CODE].

  audio_transcription_jobs speaker separation  (SpeakerSeparationStatus)
      PENDING | PROCESSING | COMPLETED | NEEDS_REVIEW | FAILED | NOT_SUPPORTED

11.3 THE WORKER'S JOB SEQUENCE

  claim (conditional UPDATE) -> CONVERTING (ffmpeg normalise) -> TRANSCRIBING
  -> [DIARIZING -> MAPPING_SPEAKERS] -> SAVING -> COMPLETED

  The stages run SEQUENTIALLY inside one job, so the memory peak is
  max(whisper, diarization) + ~60 MB for the PHP worker, NOT their sum [CODE].

  MEASURED, on the dev machine, at the 5-minute duration cap (297 s of real two-party
  call audio) [DEV]:

    stage                    73.7 s clip   297 s clip   RTF      peak RSS at 297 s
    ffmpeg -threads 1        0.07 s        0.10 s       0.0003x  49.6 MB
    whisper-cli -t 1         82-106 s      354.6 s      1.19x    904.4 MB
    sherpa-onnx diarization  10.4 s        48.9 s       0.16x    368.1 MB
    end to end               ~110 s        403.6 s      1.36x    ~964 MB incl. PHP

  Whisper's memory is dominated by the 487 MB model, so QUADRUPLING THE AUDIO took the
  peak from 833.9 MB to 904.4 MB. Neither speaker separation nor the longer duration
  cap moved the memory ceilings [CODE, docs/AUDIO_TO_TEXT.md].

  AN OOM KILL MID-JOB IS SURVIVABLE BY DESIGN: the transcript is committed to the
  database the moment Whisper succeeds, so stale recovery completes the job and only
  the speaker split is lost [CODE].

11.4 THE ENQUEUE PATH  (TranscriptionQueue::enqueueConversation)

  Order of operations, and it matters:
    1. SLOW WORK FIRST AND OUTSIDE THE LOCK - write the bytes and probe each recording
       - QueuedAudioStorage::store() -> moveTo() -> rename()
       - assertDurationWithinLimit() -> ffprobe, header only, "costs milliseconds"
         The stored name is NOT passed in; it is discovered by listing the job
         directory, which keeps the method honest about what is actually on disk rather
         than what the caller believes it wrote [CODE].
    2. THEN the queue cap, under a named lock:
       - AUDIO_TRANSCRIPTION_MAX_QUEUE <= 0 -> skip the lock entirely. Not just an
         optimisation: holding a 5-second-timeout lock on every upload would mean a busy
         moment could refuse an upload as "queue full" when NO LIMIT EXISTS AT ALL.
       - otherwise assertQueueHasRoom(count(children)) inside enqueueExclusively().
         Room is checked ONCE for the whole upload - asking per child would let a pair
         take the last slot with its Customer and be refused for its Agent.
       - a null return means ONE thing only: the named lock itself was refused.
    3. On any failure the already-stored job directories are discarded.

  CONSEQUENCE FOR THE IMPORTER: a `queueFull` refusal happens AFTER the temp file has
  been moved and ffprobe has run, which is why a refused import re-downloads next time.

11.5 TRANSCRIPTION PROVIDERS

  TranscriptionProvider = WHISPER | DEEPGRAM

  SELECTION
    Global default lives in `audio_to_text_settings.default_transcription_provider`
    (single row). An administrator changes it at POST /audio-to-text/settings/
    default-provider. The store page and the Order58 calls page both PRESELECT it.

  INV-4 - THE PROVIDER IS COPIED ONTO THE JOB AT ENQUEUE
    `audio_transcription_jobs` carries its own provider column. Changing the global
    default does NOT re-route already-queued work.
    WHY: an administrator switching the default must not silently change what
    already-queued recordings will be billed against, nor which engine a half-finished
    batch finishes on.
    Enforced by `tests/Unit/AudioToText/ProviderIndependenceTest.php` [CODE].

  WHISPER (local)
    whisper.cpp via WHISPER_BINARY + WHISPER_MODEL, pinned to
    AUDIO_TRANSCRIPTION_THREADS (1) so one job = one core.
    Bounded by AUDIO_TRANSCRIPTION_TIMEOUT (600 s).
    No network, no per-minute cost, but it holds a core and ~904 MB.

  DEEPGRAM (hosted)
    POST https://api.deepgram.com/v1/listen, key DEEPGRAM_API_KEY.
    Network-bound; costs money per minute; frees the CPU.
    Readiness is checked WITHOUT calling the API - `DeepgramEngineTest` asserts
    "Readiness does not call deepgram" [CODE], so an unconfigured Deepgram is reported
    in the startup warnings rather than discovered mid-job.

  PROVIDER INDEPENDENCE
    Deepgram replaces SPEECH-TO-TEXT ONLY. Speaker separation, review, and AI training
    audio are unchanged whichever engine produced the text [CODE,
    docs/AUDIO_TO_TEXT.md:27].

11.6 SPEAKER DIARIZATION - THE FIVE NEEDS_REVIEW GATES

  TOOL: sherpa-onnx through a Python venv (AUDIO_DIARIZATION_BINARY), with a
  segmentation model and an embedding model. ffmpeg normalises first.

  `SpeakerSeparationService` returns COMPLETED only if it passes ALL FIVE gates.
  Any one failing returns `needsReview(<reason>)` [CODE, verified line by line]:

    pre-gates (these produce NOT_SUPPORTED rather than NEEDS_REVIEW)
      :60  diarization disabled                 -> not supported
      :64  diarizer binary unavailable          -> not supported
      :68  no token timestamps from the engine  -> not supported
      :87  diarizer returned no segments
      :103 no utterances after alignment

    GATE 1  :114  quality->attributedShare < MIN_ATTRIBUTED_SHARE
                  too little of the audio could be attributed to any speaker
    GATE 2  :129  !SeparationBalance::of($utterances)->isUsable()
                  "the recording could not be separated into two speakers" - e.g. one
                  speaker holds 97% of the audio
    GATE 3  :143  $mapping['reason'] !== null
                  role mapping itself reported a problem
    GATE 4  :152  $mapping['confidence'] < AUDIO_DIARIZATION_MIN_CONFIDENCE (0.55)
    GATE 5  :170  $agentText === '' || $customerText === ''
                  one side ended up with no text at all

  WHY FIVE SEPARATE GATES RATHER THAN ONE SCORE: each names a DIFFERENT failure that a
  human reviewer can act on differently, and the reason string is carried into the
  review page so the reviewer knows what the machine was unsure about.

  THE CRITICAL SEMANTIC:
    "The `role` on a decoded utterance is EVIDENCE, NOT A FINDING - a NEEDS_REVIEW
     result stores it, but the view must not print role labels for it" [CODE,
     SpeakerSegmentsDecoder.php:34].
    A NEEDS_REVIEW recording renders as neutral "Speaker 1 / Speaker 2" until a human
    confirms. `EffectiveConversationReader` enforces this through the same gate that
    handles an unconfirmed reviewed conversation.

  AUDIO_DIARIZATION_MAX_SPEAKERS = 2 [DEV] - this is two-party call audio by
  definition.

11.7 REVIEW AND CORRECTION

  TWO LAYERS, AND THE SEPARATION IS THE POINT (INV-3)
    MACHINE layer   what Whisper/Deepgram and the diarizer produced. IMMUTABLE.
    REVIEWED layer  human corrections, in `reviewed_*` columns plus
                    `audio_segment_revisions`.
  Reverting drops the reviewed layer; the machine result is still underneath. Without
  this you cannot answer "did the model get it wrong, or did a human change it?".

  OPERATIONS (all POST, all CSRF-protected, all Post/Redirect/Get):
    /review/turn/{index}/move        move one turn to the other speaker
    /review/turn/{index}/move-text   move part of a turn's text
    /review/turn/{index}/split       split one turn into two
    /review/turn/{index}/merge       merge with the neighbouring turn
    /review/turn/{index}/text        edit the text
    /review/confirm                  CONFIRM ROLES - the publish action
    /review/revert                   drop the reviewed layer

  MERGE HAS A PRECONDITION: the two turns must share the same voice AND the same role.
  Merging across roles would assert something the reviewer has not stated [CODE].

  CONFIRM WRITES TWO THINGS AS ONE STATEMENT
    `ReviewConversationService.php:249-250`: "Confirmation and the derived text are one
    statement: 'roles are confirmed' and 'aggregate text exists' must never disagree,
    because the view's publish gate reads the second."
    So `confirmRoles` MUST write the reviewed segments, not just set a flag.

  AUDIT: `audio_segment_revisions` (142 rows on dev [DEV]) records every change.
  `/review/history` renders it. Optimistic locking prevents two reviewers clobbering
  each other.

11.8 AI TRAINING AUDIO (Deepgram TTS)

  PURPOSE: re-voice a reviewed conversation with clean synthetic speech, for training
  and QA, without the original caller's voice.

  TABLE     audio_tts_renditions (22 columns)
  STATUS    TtsStatus = QUEUED | GENERATING | READY | FAILED
  UI STATE  AiAudioState = NotGenerated | Queued | Generating | Ready | Stale |
            DifferentVoice | Failed  (9 cases - richer than the storage status, because
            the page must explain WHY a Ready rendition is no longer current)
  OUTPUT    TtsOutputType = MIXED | CUSTOMER | AGENT
  ENQUEUE   TtsEnqueueOutcome = Queued | AlreadyRunning | AlreadyCurrent | NotFound

  ELIGIBILITY: roles must be confirmed. The effective transcript (corrected where a
  human corrected it, machine otherwise) is what gets voiced.

  VOICES: separate models per role -
    DEEPGRAM_TTS_MODEL_CUSTOMER / _AGENT / _CALLER / _CALLEE

  GENERATION: the text is CHUNKED (DEEPGRAM_TTS_MAX_CHARS, default ~1900), each chunk
  is one POST to https://api.deepgram.com/v1/speak returning raw PCM, the chunks are
  concatenated with DEEPGRAM_TTS_GAP_MS of silence between turns, and ffmpeg encodes
  the result to MP3.

  COST PROTECTION, and this is why the state machine is as rich as it is:
    - `AlreadyCurrent` - a rendition matching the current transcript already exists, so
      nothing is sent
    - `AlreadyRunning` - deduplication against a concurrent request
    - `Stale` / `DifferentVoice` - the UI tells the administrator the existing audio no
      longer matches, rather than silently regenerating
    - TimeoutStartSec=900 on the unit is generous rather than tight BECAUSE the chunks
      already sent have already been billed [CODE]
  A SIGKILL leaves the row GENERATING; the worker's own stale sweep returns it to
  FAILED an hour later, KEEPING ANY PREVIOUS AUDIO [CODE].

12.1 THE ORDER58 MIRROR

  Knowledge Forge does not own store/agent/rule data - it MIRRORS it. Four mirror
  tables, all written only by sync handlers [CODE]:

    order58_stores             235 rows [DEV]   name, company, active, snapshot_json,
                                                sync_hash
    order58_agents             528 rows [DEV]   the agent identity source
    order58_knowledge_records  115 rows [DEV]
    order58_rule_records       380 rows [DEV]
    order58_store_aliases      469 rows [DEV]   alternative names for matching

  SYNC IS CHANGE-DRIVEN, NOT INCREMENTAL
    The Order58 API exposes NO incremental parameter (only page / per_page), so each
    scheduled run is a FULL PAGINATED SCAN. What makes it cheap is `sync_hash`: an
    unchanged record skips BOTH the database write AND the OpenAI re-index.
    INSERT new / UPDATE changed / SKIP unchanged [CODE].

  MARK-AND-SWEEP DEACTIVATION
    Records missing from the latest sync are deactivated ONLY AFTER A FULLY COMPLETED
    FINAL PAGE. A partial run never sweeps. This is what stops a mid-sync network
    failure from deactivating a merchant's entire rule set [CODE].

  RUN TRACKING - `integration_sync_runs`
    One row per run, with an `active_key` that COALESCES by (type, scope_ref). That
    coalescing is why this table was deliberately NOT reused as the call-import batch:
    a second Sync click for the same store would silently MERGE into the first, which
    is wrong when the two clicks select different calls [CODE].
    Order58SyncType = stores | knowledge | agents | rules | knowledge_store |
                      rebuild_store | health
    SyncRunStatus   = pending | running | completed | completed_with_warnings | failed

    KNOWN LIVE ARTEFACT [DEV]: row id=1486, type=rules, status=pending, created
    2026-09-16, still holds the unique active_key on the dev database. It causes 6
    pre-existing Integration test failures unrelated to any current work. It has been

  THE ACTIVE-FLAG TRAP

12.2 KNOWLEDGE BASES AND DOCUMENTS

  A knowledge base is the aggregate that owns documents and an OpenAI vector store.
  `knowledge_bases` (23 columns, 237 rows [DEV]) carries slug, status, purpose,
  vector_store_id, vector_store_status, source_store_id, source_active,
  agent_access_enabled.

  KnowledgeBaseStatus = active | archived
  VectorStoreStatus   = pending | provisioning | ready | failed

  DOCUMENT PIPELINE
      upload / generate
          -> documents row, status `uploaded` or `queued`
          -> kf:worker:run drains it
          -> OpenAI file upload
          -> vector store attachment
          -> document_index_files row per indexed artefact
          -> status `ready`

  DocumentStatus     = uploaded | queued | processing | indexing | ready | failed |

12.3 CHAT (store chat, rule chat, agent chat)

  One conversation model serves all three surfaces:
    conversations       9 columns   the thread
    messages           17 columns   MessageRole = user | assistant
    message_revisions               edit history
    chat_answer_scores              per-answer rating + optional comment

  ParticipantType = admin | agent - typed participants, so an admin thread and an agent
  thread can never be confused [CODE].

  GROUNDED ANSWERING
    Retrieval from the knowledge base's OpenAI vector store, then a chat completion,
    then GROUNDING VALIDATION. An answer that cannot be grounded in retrieved sources
    falls back to CHAT_FALLBACK_MESSAGE rather than inventing one. Citations resolve
    back to the source document, and
    /chat/{c}/messages/{m}/source/{documentId} renders the cited source [CODE].

  MESSAGE EDITING
    Only the LATEST question is editable, within a 20-minute window, by admin and
    agent. An edit creates a `message_revisions` row, supersedes the old answer
    (hidden but audited) and regenerates. Availability is computed, not guessed.

  CHAT AVAILABILITY POLICY - subtle and worth knowing
    A store's chat is available only when it has a USABLE QUALIFYING DOCUMENT, and
    "usable" means a COMPLETED `document_index_files` row, NOT `documents.status`.
    WHY: using documents.status made availability FLICKER during a refresh. The store
    profile document never counts as qualifying on its own [CODE].
    Enforced by `tests/Unit/Chat/ChatAvailabilityPolicyTest.php` and
    `tests/Integration/Chat/ChatAvailabilityQueryTest.php`.

  AGENT CHAT differs from admin chat in exactly two ways: the identity realm, and
  store visibility. The answering machinery is the same code.
  `AgentConversationIsolationTest` asserts an agent cannot read another agent's threads.

12.4 RULES

  The most involved module, because Order58 rules arrive per store and the same rule
  text is repeated across hundreds of stores.

    order58_rule_records        380 rows [DEV]  raw mirror

13.3 THE TWO CALL-IMPORT TABLES IN DETAIL

  Documented at length because they are the newest and the least covered elsewhere.

  order58_call_import_batches  - ONE ADMIN SYNC CLICK
    triggered_by           varchar(16) CHECK IN ('MANUAL','AUTOMATIC'). varchar + CHECK
                           rather than ENUM so adding a trigger source is not a
                           migration. AUTOMATIC is reserved for a future scheduler;
                           nothing writes it today.
    requested_by_admin_id  bigint NULL, FK admin_users ON DELETE RESTRICT. Nullable for
                           that same future. RESTRICT means an admin who queued an
                           import cannot be deleted out from under the audit trail.
    recording_company      varchar(100) NOT NULL, CHECK <> ''. A SNAPSHOT of
                           order58_stores.company AT QUEUE TIME (INV-8). A later mirror
                           sync overwrites order58_stores wholesale; the snapshot means
                           that cannot change what an already-queued batch fetches, and
                           the row is the audit trail of exactly which code was sent.
    transcription_provider varchar(16) CHECK IN ('WHISPER','DEEPGRAM')
    call_count             smallint unsigned DEFAULT 0 - exists but is NOT maintained
                           by the current code.

  order58_call_imports  - ONE ROW PER RECORDING CHANNEL
    channel           varchar(16) CHECK IN ('mixed','caller','callee')  -- LOWERCASE
    status            varchar(16) CHECK IN ('PENDING','FETCHING','IMPORTED',
                      'NOT_AVAILABLE','TOO_LARGE','FAILED')             -- UPPERCASE
      THE CASE MISMATCH IS DELIBERATE AND ENFORCED. `channel` uses RecordingChannel's
      own vocabulary (the provider's, lowercase); `status` uses the application's
      (uppercase). An early version of this migration had an UPPERCASE channel CHECK -
      it would never have round-tripped, and it was rolled back with `migrate:down`,
      corrected and reapplied before anything used it [CODE].
    call_session_id   varchar(32), CHECK REGEXP '^[0-9]{1,20}$'
    call_time_raw     varchar(64) - the provider's `callTime` string UNPARSED, kept
                      alongside the derived `call_date`. The raw string is what the
                      history table displays and what any future timezone investigation
                      would need.
    call_date         date - what goes into `?time=` on the fetch URL
    error_message     varchar(1000) - matches redactAndTruncate($msg, 1000) exactly
    bytes             bigint unsigned - evidence for a TOO_LARGE decision
    duration_seconds  decimal(9,2) - exists; current code always passes null and
                      records `bytes` instead
    conversation_public_id char(32) - the ONLY link kept to Audio-to-Text

    UNIQUE ux_order58_call_imports_identity (store_source_id, call_session_id, channel)
      THE IDEMPOTENCY KEY (INV-11). store_source_id is included CONSERVATIVELY because
      whether call_session_id is globally unique is UNVERIFIED with the provider.
      order_id is NEVER part of it - one order can have several calls, each with three
      channels.
    KEY ix_order58_call_imports_queue (status, next_attempt_at, id)
      Matches claimNext()'s WHERE + ORDER BY exactly, so claiming is an index range
      scan regardless of table size.
    FK batch_id -> order58_call_import_batches ON DELETE RESTRICT

15. ENVIRONMENT VARIABLES - ALL 126 KEYS

Source of truth: the `SPEC` array in `src/Environment.php` [CODE].

HOW IT WORKS
  Every key is declared with a type, a default, and optionally min/max and a `secret`
  flag. `Environment::prepare()` validates ALL of them at boot. A missing required key
  or an unparseable value throws AT STARTUP with the key named - it never becomes null.
  `config/common/params.php` then turns them into typed params, and
  `config/common/di/app-params.php` turns those into typed readonly objects.

NO SECRET VALUE APPEARS IN THIS DOCUMENT. Six keys are marked `secret` in the SPEC and
their DEFAULT column below reads "(secret - value never printed)":
  DB_PASSWORD, DEEPGRAM_API_KEY, OPENAI_ADMIN_API_KEY, OPENAI_API_KEY,
  ORDER58_API_TOKEN, ORDER58_VALIDATE_API_TOKEN
The redactor in `SecretRedactor` is seeded with these at construction, so even a
provider error body echoing a request back cannot carry one into a log (INV-13).

WHAT HAPPENS IF A KEY IS MISSING
  - has a default  -> the default is used, silently and safely
  - no default     -> `Environment::prepare()` throws at boot, naming the key
  - unparseable    -> throws at boot (e.g. `SOME_BOOL=maybe`)
  - `.env` UNREADABLE -> `safeLoad()` ignores it and EVERY key falls back to its
    default. The first symptom is "Environment variable DB_USER is not set". See 5.4.

17. FILE STORAGE, SECURITY, CONCURRENCY
--------------------------------------------------------------------------------------

17.1 STORAGE LAYOUT

  runtime/storage/            uploaded documents
  runtime/audio-to-text/jobs/ one directory per job (2.1 MB across 102 dirs [DEV])
  runtime/tmp/                TMPDIR for the Order58 importer (same filesystem as the
                              destination, so the hand-off rename cannot fail)
  runtime/locks/              lock files (see 9.5)
  runtime/logs/               application logs
  runtime/backups/            ad-hoc

  Job directories are created mode 0700 BY PHP-FPM, which runs as www-data. This is why
  EVERY background unit must run as www-data - as any other user the last step of every
  import fails, after the download has already been paid for [CODE].

  RETENTION: AUDIO_TRANSCRIPTION_RETENTION_SECONDS = 0 means KEEP INDEFINITELY (the
  shipped and local setting [DEV]). Real Order58 calls are 8 kHz mono at ~4.6 MB, so
  the practical growth rate is modest, but it IS unbounded over time.

  THE `.env` ACL TRAP (a real incident, 25 Sep 2026)
    `.env` is deliberately NOT world-readable - it holds the DB password and API keys.
    www-data reads it through a POSIX ACL. An editor that replaces the file rather than
    writing in place DROPS THAT ACL, and because `safeLoad()` ignores an unreadable
    file, every setting silently falls back to its default. Remedy:
        chmod o= .env && setfacl -m "u:www-data:r--" .env
    which is what `docs/deploy/grant-web-access-acl.sh` does [CODE].
    ADD THIS CHECK TO THE END OF ANY DEPLOY THAT EDITS `.env`.

17.2 SECURITY SUMMARY

  Authentication   two realms, database-backed, re-loaded per request
  Authorization    structural, by route group (6.2)
  CSRF             application-wide middleware; hidden input, or X-CSRF-Token header
  CSP              script-src 'self' and style-src 'self' - no inline JS, no inline
                   style, no CDN (INV-14)
  Headers          SecurityHeadersMiddleware, app-owned rather than nginx-owned so they
                   are identical in every deployment
  SQL              parameterised throughout via the Yii query builder
  Uploads          extension + size + libmagic MIME sniff, and the bytes are sniffed
                   even when the filename lies
  Path validation  recording ids are validated BEFORE becoming a filename or a path
                   segment; `RecordingChannel::fileNameFor()` documents that its caller
                   must have validated first, and a test asserts every id it is called
                   with has been through the validator [CODE]
  Secrets          never rendered, never logged (INV-13); never in this document
  Private files    job directories are 0700 and served only through authenticated
                   actions, never as static files

17.3 CONCURRENCY AND IDEMPOTENCY - THE FIVE MECHANISMS

  1. UNIQUE CONSTRAINTS as idempotency keys, with insert-and-catch (INV-11).
     `order58_call_imports` identity; `order58_daily_sync_schedules` UNIQUE(sync_type,
     ny_date); `integration_sync_runs.active_key`.
  2. CONDITIONAL UPDATE claims, where the affected-row count IS the lock (INV-12).
  3. flock, per worker, held for the process lifetime (INV-5). The kernel releases it
     however the process dies, so there is no stale lock to clean up.
  4. FOREIGN flock - participating in ANOTHER project's lock file to serialise across
     applications (9.2.1).
  5. OPTIMISTIC LOCKING in the review layer, so two reviewers cannot clobber each
     other silently.

  Plus `sync_hash` as a change detector, which is idempotency of a different kind: it
  makes a full re-scan cheap rather than preventing a duplicate.

19. TROUBLESHOOTING
--------------------------------------------------------------------------------------

EVERY PAGE RETURNS 500, "Environment variable DB_USER is not set"
  It is almost certainly NOT the database. www-data cannot read `.env`, and
  `safeLoad()` ignores a file it cannot read, so every key fell back to its default.
      getfacl .env | grep www-data          # expect user:www-data:r--
      chmod o= .env && setfacl -m "u:www-data:r--" .env
  See 17.1.

AUDIO JOBS SIT IN QUEUED FOREVER
  1. Is the scheduler running?
       systemctl list-timers | grep knowledge-forge
  2. Is the worker DEFERRING rather than failing? Deferral is silent to the queue but
     loud in the log:
       journalctl -u knowledge-forge-audio-worker -n 50
       grep audio_worker_deferred runtime/logs/app.log
  3. THE MOST LIKELY CAUSE ON A SMALL SERVER: AUDIO_WORKER_MIN_AVAILABLE_MB=1500 is 37%
     of a 4 GB box. If MemAvailable never reaches it, the worker defers EVERY tick,
     forever, and it looks like a stall rather than an error (INV-7).
       grep MemAvailable /proc/meminfo
  4. FOREIGN LOCK, FAILING CLOSED: if AUDIO_WORKER_FOREIGN_LOCKS points at a file the
     worker's user cannot READ, every tick defers. Run as www-data, or blank the
     setting.
       grep audio_worker_foreign_lock runtime/logs/app.log

ORDER58 CALLS WILL NOT LOAD
  Expected off the allowlist. Check the wording on the page - `ip-not-whitelisted`
  means exactly what it says and no credential will fix it (10.2). A LOCAL FAILURE
  PROVES NOTHING ABOUT THE API.

ORDER58 IMPORTS STAY PENDING
  1. ORDER58_RECORDING_IMPORT_ENABLED - the command says so on stdout if it is off.
  2. Is there a scheduler for it at all? (On dev there is not [DEV].)
  3. TMPDIR unusable -> the command exits DATAERR with an explicit message (9.2.3).
  4. Resource deferral -> `grep order58_import_deferred`.
  5. Lock held by a stray long-running instance -> `ps -ef | grep import-recordings`.

A JOB IS STUCK IN FETCHING / PROCESSING
  A killed worker leaves its row claimed. The next run's stale sweep returns anything
  claimed for more than 15 minutes (Order58) or past
  AUDIO_TRANSCRIPTION_STALE_AFTER (audio). Just wait for the next tick.

EVERY WORKER RUN "SKIPS" SILENTLY
  Classic symptom of INV-5: the cron wrapper and the application share a lock file.
  `flock -n` exits 1 with NO OUTPUT, so it is invisible. Give them different files.

DIARIZATION ALWAYS SAYS NEEDS_REVIEW
  Find WHICH of the five gates (11.6). The reason string is stored and shown on the
  review page. Gate 2 (separation balance) on a recording where one party barely speaks
  is not a bug - it is the system declining to guess.

CHAT SAYS IT HAS NO ANSWER
  Check chat AVAILABILITY first: the store needs a usable qualifying document, meaning
  a COMPLETED `document_index_files` row - not merely `documents.status = ready`
  (12.3). Then check grounding: an ungrounded answer falls back deliberately.

OPENAI INDEXING NEVER COMPLETES
  `kf:worker:run` is the only thing that advances it. Confirm it is scheduled at all,
  then read `document_processing_events` for that document. For an ambiguous create,
  run `kf:ai:reconcile` - it ADOPTS the existing remote object rather than duplicating.

A TIMER IS INSTALLED BUT NOT FIRING
    systemctl status knowledge-forge-audio-worker.timer
    systemctl list-timers --all | grep knowledge-forge
    journalctl -u knowledge-forge-audio-worker --no-pager -n 50
    systemctl show knowledge-forge-audio-worker.service -p MemoryPeak -p Result

  L-3  PHP CLI `memory_limit = -1` [DEV]. Nothing in PHP caps a runaway worker; the
       only backstop is the systemd cgroup, and only where a unit is installed.

  L-4  The recording provider's `name` parameter has NO documented meaning on the

  L-7  Three first-live-run assumptions about the recording provider remain
       unverified, and each fails VISIBLY rather than silently:
         (a) accountId == order58_stores.source_id - evidenced for stores 871 and 831
             only; all mirrored ids end in `1`, so it is a derived id space. A wrong id
             returns no calls, which the page reports plainly.
         (b) `callTime` is the provider's LOCAL wall clock. Its leading date is compared
             to the New-York business date with NO conversion. If the provider is
             actually UTC, the "today" list can be wrong near midnight. The
             administrator still sees the real times, and `call_time_raw` preserves the
             original string for whoever settles this.
         (c) per-store `company` is what the provider expects. A mismatch shows up as a
             404 or, worse, THE WRONG AUDIO.
       THE VERIFICATION FOR ALL THREE IS THE SAME AND HAS NOT BEEN DONE: from an
       allowlisted server, sync a SINGLE call on ONE store, play the fetched WAV back on
       the store page, and confirm it is that call - before syncing in bulk.

  L-8  `AUDIO_WORKER_MIN_AVAILABLE_MB=1500` was derived on a 16 GB machine. On a 4 GB
       server it is 37% of total RAM, and if MemAvailable never reaches it the audio
       queue stalls SILENTLY (INV-7). Measure before enabling import on a small box.
