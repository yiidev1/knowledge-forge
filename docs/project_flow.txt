1. EXECUTIVE SUMMARY
================================================================================

Knowledge Forge is an admin-operated, single-tenant knowledge-base chat
application built on Yii 3 / PHP 8.2, server-rendered, backed by MySQL 8.
It has grown four distinct capability areas that are only loosely coupled:

  1. Knowledge bases + documents + grounded chat   (OpenAI-backed retrieval)
  2. Order58 mirror                                (stores, agents, rules)
  3. Rules catalogue                               (classification + projection)
  4. Audio-to-Text                                 (100% local transcription)

The five findings that matter most for the work you are about to request:

  F1. There is NO correction-learning / custom-vocabulary mechanism of any
      kind. Verified by exhaustive repository search (section 12). The system
      cannot today remember that "one ton" should be "wonton".

  F2. There is NO transcription-provider abstraction. `AudioTranscriber` is a
      concrete final class that shells out to whisper.cpp. There is no
      `TranscriberInterface`. Swapping or adding a provider requires
      introducing that seam first (sections 8 and 31).

  F3. Audio-to-Text is genuinely isolated. It references NO other business
      module (verified: `grep -rlE "App\\(KnowledgeBase|Rules|Chat|Ai|Order58)"
      src/AudioToText/` returns nothing), and it calls NO external AI provider
      at all. Knowledge bases and rules have ZERO influence on transcription.

  F4. Store association is the ONLY link between Audio-to-Text and the rest of
      the system, and it is a soft numeric reference
      (`audio_conversations.store_source_id` -> `order58_stores.source_id`),
      with no foreign key by deliberate design.

  F5. The machine's transcription result is immutable. Corrections live in a
      separate reviewed layer plus an append-only audit table. This is verified
      at the SQL level (section 11) and is the foundation any future
      learned-dictionary feature could build on.

Overall health: high. 1,190 unit tests / 3,526 assertions pass; module
isolation, web-tier/whisper separation and correction contiguity are all
enforced by tests rather than convention. Technical debt is small and named in
section 33.

3.2 ARCHITECTURAL PATTERN

Layered, per-module, with a consistent four-layer split inside each module:

  Domain/          Immutable value objects, enums, repository INTERFACES (ports)
  Application/     Services, orchestration, settings objects
  Infrastructure/  Db* repository implementations, process runners, HTTP clients
  Web/             One directory per page: Action.php + template.php
  Console/         Commands

Example (AudioToText), verified:
  Domain/TranscriptionJobRepositoryInterface.php      <- port
  Infrastructure/DbTranscriptionJobRepository.php     <- adapter
  Application/TranscriptionQueue.php                  <- service
  Web/Job/Review/Action.php + template.php            <- page
  Console/AudioTranscriptionWorkerCommand.php         <- worker

3.3 SINGLE-ACTION CONTROLLERS

There are no multi-method controllers. Every route points at a
`final readonly class Action` with a single `__invoke()`.
Route arguments arrive via `#[RouteArgument]` attribute hydration.

  Example: src/AudioToText/Web/Job/Review/Action.php
    public function __invoke(#[RouteArgument] string $publicId): ResponseInterface

3.4 DEPENDENCY INJECTION

  yiisoft/di with autowiring. Interfaces are bound in config/common/di/*.php.
  `config/configuration.php` globs `common/di/*.php`, so adding a module needs
  no edit to an existing config file.

  Verified bindings (config/common/di/audio-to-text.php):
    TranscriptionJobRepositoryInterface  => DbTranscriptionJobRepository
    AudioConversationRepositoryInterface => DbAudioConversationRepository
    AudioStoreLookupInterface            => DbAudioStoreLookup
    SegmentRevisionRepositoryInterface   => DbSegmentRevisionRepository
    SpeakerDiarizerInterface             => SherpaOnnxSpeakerDiarizer
                                            (or NullSpeakerDiarizer)
    WorkerHeartbeatRepositoryInterface   => DbWorkerHeartbeatRepository
    SystemResourceProbeInterface         => ProcSystemResourceProbe

  Classes with no interface (ConversationHistoryBuilder,
  MachineConversationReader, EffectiveConversationReader) are autowired with no
  DI entry at all.

3.5 MIDDLEWARE / AUTH ARCHITECTURE

  config/common/routes.php has exactly three zones:
    (a) Public:  /login (GET,POST), /agent/login (GET,POST)
    (b) Group::create()->middleware(RequireAdminMiddleware::class)
                       ->middleware(DomainExceptionMiddleware::class)
        -> everything admin, including ALL Audio-to-Text routes
    (c) Group::create()->middleware(RequireAgentMiddleware::class)
                       ->middleware(DomainExceptionMiddleware::class)
        -> /agent/* only

  src/Auth/Web/Middleware/RequireAdminMiddleware.php reloads the account from
  the database on every request (not trusting session contents alone).
  src/Agent/Web/Middleware/RequireAgentMiddleware.php is a SEPARATE realm;
  Order58 agents can never reach an admin route.

  Authorization model for Audio-to-Text is explicitly:
      "authenticated administrator + the job exists"
  There is NO per-store or per-uploader access control. `uploaded_by_admin_id`
  is audit metadata only. Documented in docs/AUDIO_TO_TEXT.md §1 and confirmed
  in code: no action consults the uploader before rendering.

8. TRANSCRIPTION ENGINE
================================================================================

VERIFIED FROM CODE, NOT DOCUMENTATION.

  Engine            whisper.cpp  (NOT OpenAI Whisper API, NOT a PHP library)
  Invoked from      src/AudioToText/Infrastructure/AudioTranscriber.php
  Binary            WHISPER_BINARY = /opt/whisper.cpp/build/bin/whisper-cli
                    Version on this host: 1.9.3-dev
  Model             WHISPER_MODEL = /opt/whisper.cpp/models/ggml-small.bin
                    ~487 MB, MULTILINGUAL (deliberately not ggml-small.en.bin
                    — recordings mix English, Spanish, Gujarati and Hindi)
  Preflight         AudioTranscriber:122-127 — is_file + is_executable on the
                    binary; is_file + is_readable on the model. Throws
                    AudioTranscriptionException::whisperMissing / modelMissing.

  FFMPEG PREPROCESSING (AudioTranscriber:167-177) — NOT optional:
    ffmpeg -nostdin -hide_banner -loglevel error -y -threads 1
           -i <source> -ar 16000 -ac 1 -c:a pcm_s16le <out.wav>
    whisper.cpp will not resample; 16 kHz mono PCM s16le is required.

  WHISPER COMMAND (AudioTranscriber:196-208):
    <WHISPER_BINARY>
      -m  <WHISPER_MODEL>
      -f  <audio.wav>
      -l  auto                 <- language auto-detection
      -t  <AUDIO_TRANSCRIPTION_THREADS>   (currently 1)
      -np                      <- no progress animation
      -otxt                    <- plain transcript (shown + downloaded)
      -oj                      <- JSON sidecar, read for detected language
      -ojf                     <- FULL token-level timestamps (speaker alignment)
      -of <outputStem>

  Timeout           AUDIO_TRANSCRIPTION_TIMEOUT = 600 s, applied to BOTH the
                    ffmpeg call and the whisper call.
                    On expiry: AudioTranscriptionException::conversionTimedOut /
                    ::transcriptionTimedOut
  Max duration      AUDIO_TRANSCRIPTION_MAX_DURATION = 300 s (5 min)
  Max upload size   AUDIO_TRANSCRIPTION_MAX_SIZE = 31,457,280 B (30 MB) per file
  Input formats     wav, mp3, m4a, ogg, webm (extension allow-list + MIME sniff)
  Output            transcript.txt + transcript.json (language + tokens)
  Token timestamps  YES, via -ojf, read by AudioTranscriber::readTokens()
  Language detect   YES, read by AudioTranscriber::readLanguage() from the JSON

10. SPEAKER ROLE MAPPING — HOW SPEAKER 1 BECOMES CUSTOMER OR AGENT
================================================================================

  Class   src/AudioToText/Application/Speaker/SpeakerRoleMapper.php
  Acts    src/AudioToText/Domain/Speaker/DialogueAct.php
  Weights src/AudioToText/Domain/Speaker/RoleScoreWeights.php

10.1 WHY NOT KEYWORDS

  Documented in SpeakerRoleMapper:36-45 and confirmed by the code: counting
  role-ish keywords FAILED, because the two sides use the same words. "Cash"
  and "card" are substrings of the agent's own question; a competent agent
  repeats the address back and recites items during the recap. Every one of
  those scored as customer evidence AGAINST the agent. On a call whose roles
  were obvious to a human, the margin came out at 0.077.

10.2 WHAT IS ACTUALLY SCORED: ADJACENCY PAIRS

  The mapper detects DialogueActs and scores question/answer pairs across two
  DIFFERENT speakers. It never infers a speaker from words alone and never
  assumes the first voice is the agent.

  AGENT-SIDE ACTS   GREET_BUSINESS, ASK_ORDER, ASK_DELIVERY_METHOD,
                    ASK_ADDRESS, ASK_PAYMENT, ASK_QUANTITY, ASK_ANYTHING_ELSE,
                    CONFIRM_ORDER, QUOTE_PRICE, QUOTE_DELIVERY_TIME
  CUSTOMER-SIDE     REQUEST_ORDER, PROVIDE_ORDER_ITEM, SELECT_DELIVERY_METHOD,
                    PROVIDE_ADDRESS, SELECT_PAYMENT, PROVIDE_QUANTITY,
                    DECLINE_MORE

  PAIRED WEIGHTS (question + its answer, two different speakers)
    PAIR_ADDRESS           3.0
    PAIR_PAYMENT           3.0
    PAIR_DELIVERY_METHOD   3.0
    PAIR_ORDER             3.0
    PAIR_ANYTHING_ELSE     2.5
    PAIR_QUANTITY          1.5

  UNPAIRED WEIGHTS (agent move with no answer found)
    UNPAIRED_QUOTE_PRICE           1.5
    UNPAIRED_QUOTE_DELIVERY_TIME   1.5
    UNPAIRED_GREET_BUSINESS        1.0
    UNPAIRED_CONFIRM_ORDER         1.0
    UNPAIRED_QUESTION              0.75

  UNPAIRED CUSTOMER MOVES
    UNPAIRED_REQUEST_ORDER            1.0   <- the one move an order-taker
                                              never makes
    UNPAIRED_DECLINE_MORE             0.5
    UNPAIRED_ECHOABLE_CUSTOMER_MOVE   0.0   <- indistinguishable from the agent
                                              echoing; carries no orientation

  OTHER CONSTANTS
    ANSWER_WINDOW         2      how far ahead to look for the answer
    RELIABLE_WORD_COUNT   6      an unpaired act is scaled by utterance length,
                                 so a strong act on a two-word fragment cannot
                                 cancel a completed exchange
    SUFFICIENT_EVIDENCE   6.0    the volume denominator

10.3 CONFIDENCE FORMULA (SpeakerRoleMapper:111-117) — EXACT

    $agreement  = abs($forward - $backward) / $total;
    $volume     = min(1.0, $total / RoleScoreWeights::SUFFICIENT_EVIDENCE);
    $confidence = $agreement * $volume;

  agreement = how one-sided the evidence is (contradictory signals cancel)
  volume    = how much evidence there is at all
  Without volume, a single lucky pair in a short call would score a perfect
  ratio and publish.

  Within one utterance the MOST SPECIFIC ACT WINS: "cash or card?" is a payment
  QUESTION and never also a payment CHOICE.

10.4 THE FIVE GATES (src/AudioToText/Application/Speaker/SpeakerSeparationService.php)

  Checked IN ORDER; the first failure decides the outcome. Order matters —
  each question only makes sense once the previous one is answered.

  PRE-GATES (not NEEDS_REVIEW)
    diarization disabled            -> NOT_SUPPORTED   (line 60-62)
    toolchain not installed         -> NOT_SUPPORTED   (line 64-66)
    whisper produced no tokens      -> FAILED          (line 68)
    diarizer threw / timed out      -> FAILED          (line 84)
    diarizer returned no segments   -> FAILED          (line 87)
    no token matched any segment    -> FAILED          (line 103)

  GATE 1  ALIGNMENT       quality->attributedShare < MIN_ATTRIBUTED_SHARE (0.75)
                          -> NEEDS_REVIEW                       (line 114)
  GATE 2  SEPARATION      SeparationBalance::of()->isUsable() false
          BALANCE         -> NEEDS_REVIEW                       (line 129)
                          thresholds (SeparationBalance.php):
                            MIN_MINOR_SHARE    0.05
                            MIN_MINOR_SECONDS  5.0
                            MIN_MINOR_WORDS    10
                            MIN_ALTERNATIONS   4
  GATE 3  ROLE MAPPING    mapping['reason'] !== null (one cluster, 3+, or no

11.4 THE SHARED REQUEST HANDLER

  src/AudioToText/Web/Job/Review/ReviewRequest.php
    adminId()          -> CurrentAdmin
    expectedVersion()  -> form's `expected_review_count`; ABSENT OR UNPARSEABLE
                          BECOMES -1, not 0, because 0 is a real version (every
                          never-corrected job has it). A missing field must LOSE
                          the race, not silently win it.
    apply()            -> run, flash, redirect 303 to JOB_REVIEW

11.5 CONCURRENCY + AUDIT (src/AudioToText/Application/ReviewConversationService.php)

    load job by public_id             -> ReviewRejected if unknown/not COMPLETED
    load current turns                -> reviewed layer if present, else machine
    apply the change (pure, in memory)-> ReviewRejected if the rule refuses
    BEGIN
        revisions->add(jobId, priorSegmentsJson, operation, adminId)
        applied = jobs->saveReview(... expectedReviewCount)   -- conditional UPDATE
        if (!applied) throw ReviewConflict                    -- rolls back the revision too
    COMMIT

  * Validation happens BEFORE the transaction opens — a refused correction
    costs nothing and leaves no trace.
  * The revision is written FIRST, so a lost race unwinds both and never
    leaves an orphan audit row.
  * The optimistic lock is a CONDITIONAL STATEMENT, not read-then-write:
      UPDATE ... SET review_count = review_count + 1
      WHERE id = ? AND review_count = ?
  * `revert` ADVANCES the version too — the count is of corrections MADE, not
    layers present, so a stale tab cannot become current because somebody
    else reverted.

11.6 WHAT A CLIENT MAY ASSERT

  A turn has NO id. Its only handle is its index in the current conversation.
  So the client sends an index and a DIRECTION, never a target — the server
  derives the neighbour itself, and adjacency is structural rather than
  something a crafted request can claim.
  For a range move the client sends CODEPOINT offsets plus the selected text as
  a checksum; the server slices by offset and refuses if the slice disagrees.
  Offsets are converted to codepoints in the browser because JavaScript counts
  UTF-16 units and mb_substr counts codepoints — they diverge from the first
  emoji.

11.7 PER-MESSAGE CORRECTION HISTORY (added 2026-09-03)

  src/AudioToText/Application/ConversationHistoryBuilder.php
  src/AudioToText/Domain/Speaker/ConversationDiff.php
  src/AudioToText/Domain/Speaker/HistoryEvent.php
  src/AudioToText/Domain/Speaker/TurnLineage.php

  Because turns have no identity, history is DERIVED by diffing consecutive
  `audio_segment_revisions` snapshots (longest common prefix + longest common
  suffix) to isolate the contiguous changed run, then propagating lineage.
  Validated against all 112 recorded corrections at the time of writing; the
  changed-run shapes were:
    EDIT_TEXT 1->1 | SPLIT 1->2 | MERGE 2->1 or 2->2 | MOVE 1->1 or 1->3
    CONFIRM_ROLES 0->0 (23/23 occurrences — never a structural change)
  A 2->2 range merge shows ONE SHARED region-level event on both messages;
  no one-to-one child ancestry is claimed, because the data cannot prove it.
  REVERT resets the lineage baseline.
  The underlying property is enforced by
  tests/Unit/AudioToText/ReviewedConversationTurnsContiguityTest.php.

15.5 WHO CHANGES WHAT
  QUEUED             the web request (TranscriptionQueue::enqueueConversation)
  PROCESSING         the worker, atomic conditional claim only
  COMPLETED / FAILED the worker
  stage              the worker, markStage() at each step
  NOTHING ELSE writes status. There is no admin "retry" button and no API.

15.6 RETRY / RECOVERY — VERIFIED
  RETRY               DOES NOT EXIST. No automatic retry anywhere.
  CRASH               the job stays PROCESSING until the stale sweep.
  STALE RECOVERY      AUDIO_TRANSCRIPTION_STALE_AFTER = 1200 s.
                      Housekeeping only ever moves jobs OUT of PROCESSING
                      (into COMPLETED or FAILED), NEVER back into QUEUED.
                      IF THE TRANSCRIPT WAS ALREADY COMMITTED, the job is
                      COMPLETED with the speaker split marked failed; only a
                      crash BEFORE transcription fails the job.
  TIMEOUT             ProcessRunner SIGTERM -> grace -> SIGKILL; the stage's
                      exception fails the job (or completes it if the
                      transcript already landed).
  OOM at MemoryMax    survivable by design, same rule as above.
  REPROCESSING        IMPOSSIBLE. Both halves of the claim filter on
                      status='QUEUED' — the candidate scan AND the conditional
                      UPDATE. A COMPLETED or FAILED row can never be selected.
  RETRYING A FAILED   would require creating a NEW job; reopening a terminal
  RECORDING           row would silently overwrite the original result and lose
                      its audit trail.

16. QUEUE & WORKER
================================================================================

16.1 COMMAND
  kf:audio:worker            registered in config/console/commands.php
  Class  src/AudioToText/Console/AudioTranscriptionWorkerCommand.php
  Modes  (no flag) continuous | --once (what the timer runs, and what tests use)
  A second worker refuses the lock, says so, and EXITS 0 — a correctly-refused
  duplicate is not a failure and a supervisor must not restart it in a loop.

16.2 FIFO
  claimNextQueued() scans WHERE status='QUEUED' ORDER BY id ASC, then claims
  with UPDATE ... WHERE id=? AND status='QUEUED'. `id` is monotonic, so a
  recording uploaded later can never be taken before an earlier one. The queue
  position shown on a job page uses the same ordering.

16.3 FOUR INDEPENDENT CONCURRENCY MECHANISMS

  1. flock on runtime/audio-to-text/worker.lock
     LOCK_EX | LOCK_NB, held for the whole process lifetime.
     AudioTranscriptionWorkerCommand:516 (acquire), :542 (release)
     Chosen over a database advisory lock because the KERNEL releases it
     however the process dies — no stale lock to detect, no recovery code to
     get subtly wrong. Trade-off: it covers ONE MACHINE.
     The lock file lives BESIDE jobs/, never inside it, so the orphan sweep
     cannot delete the file that guarantees single-worker operation. It is
     never unlinked (unlinking races with a process that already opened it).

  2. Atomic conditional claim (see 16.2).
     The claim ALONE is not enough: it would let worker A take job 1 while
     worker B takes job 2 — two whisper processes on one CPU. The lock is what
     prevents that.

  3. Foreign lock  AUDIO_WORKER_FOREIGN_LOCKS
     src/AudioToText/Application/ForeignLockGuard.php
     Currently set to:
       /var/www/html/telecom-billing/runtime/audio-to-text/cron-worker.lock
     Takes an exclusive non-blocking flock on ANOTHER PROJECT'S lock file
     before claiming, and holds it until the job finishes. Both projects are
     then in one kernel-arbitrated queue. The file is opened READ-ONLY, so it
     is never created. FAILS CLOSED: a configured lock that is held, missing OR
     UNREADABLE defers the tick, with an explicit startup warning naming the
     path.

  4. AUDIO_WORKER_YIELD_TO_OTHER_WHISPER (default true)
     A process scan catching a foreign worker started BY HAND, which takes no
     cron lock. EXPLICITLY DOCUMENTED AS RACY BY CONSTRUCTION and never the
     basis of an exclusivity claim.

  MAXIMUM CONCURRENT TRANSCRIPTION JOBS = 1 (machine-wide, within this feature)

16.4 ADMISSION GUARD
  src/AudioToText/Application/WorkerAdmissionGuard.php
    free RAM >= AUDIO_WORKER_MIN_AVAILABLE_MB   (1500)
    load per core <= AUDIO_WORKER_MAX_LOAD_PER_CORE  (1.5)
  Probe: src/AudioToText/Infrastructure/ProcSystemResourceProbe.php (/proc)

16.5 HEARTBEAT
  AUDIO_WORKER_HEARTBEAT_SECONDS = 5    write cadence
  AUDIO_WORKER_STALE_AFTER       = 30   process presumed dead
  AUDIO_WORKER_TICK_STALE_AFTER  = 180  ticks presumed stopped (~3 missed
                                        2-minute ticks)
  Between ticks NO worker process exists, so the admin page reads
  "Scheduled — last ran N ago", not "Running".
  src/AudioToText/Application/WorkerHealthService.php

16.6 SCHEDULING
  CHOSEN: systemd timer.
    docs/server/systemd/knowledge-forge-audio-worker.timer
      OnBootSec=2min ; OnUnitActiveSec=2min
    docs/server/systemd/knowledge-forge-audio-worker.service
      ExecStart=/usr/bin/php8.2 /var/www/html/knowledge-forge/yii kf:audio:worker --once
      TimeoutStartSec=1200
      CPUQuota=100%      <- exactly one core
      MemoryHigh=1200M   <- throttles by reclaiming
      MemoryMax=1600M    <- OOM backstop

    systemd will NOT start a second run of a unit that is still active, so the

  NOTHING IN THIS PROJECT WRITES TO /etc. Installation is manual.

16.7 ENQUEUE LOCK

  lock is SKIPPED ENTIRELY). Lock name is
  CONCAT(DATABASE(), ':audio-to-text:enqueue') — the prefix matters because
  MySQL named locks are SERVER-GLOBAL, not per-schema.

17. AUDIO STORAGE & RETENTION
================================================================================

  TWO SIBLING TREES — the separation IS the safety property.

  runtime/audio-to-text/
    worker.lock                 the single-worker guarantee. OUTSIDE both trees
    jobs/<publicId>/            TEMPORARY workspace. SWEPT. Deleted when done.
        source.<ext>  audio.wav  transcript.txt  transcript.json
    recordings/<publicId>/      PERMANENT. NEVER SWEPT.
        source.<ext>

  VERIFIED ON DISK (this audit):
    drwxrwx---  runtime/audio-to-text
    drwxrwx---  runtime/audio-to-text/jobs         (32 entries)
    drwxrwx---  runtime/audio-to-text/recordings   (29 entries)
    -rw-rwxr--  runtime/audio-to-text/worker.lock

  PUBLIC ACCESSIBILITY: NO.
    The web root is public/ and contains ONLY: index.php, assets/, favicon.ico,
    favicon.svg, robots.txt. `find public -name "*.wav"` returns nothing.
    runtime/ is a sibling of public/, not inside it.
    No filesystem path is ever shown in the UI or returned by any endpoint —
    the job page says only "Retained on this server".

  ON SUCCESS the recording is MOVED — rename(), atomic within a filesystem —
  out of jobs/ and into recordings/ BEFORE the row is marked complete. A move
  rather than a copy means the file exists in exactly one place at any moment,
  so there is never a window where the sweeper could collect something the
  database already considers retained.

  NAMING: the client filename NEVER becomes a path. The server names the file
  source.<ext> where <ext> comes from the validated extension allow-list.

  ORPHAN SWEEP walks ONLY jobs/. Retained recordings are in a SIBLING TREE, not
  a subdirectory, so "the sweeper cannot reach them" is a fact about the layout
  rather than a rule someone has to remember.

  RETENTION: AUDIO_TRANSCRIPTION_RETENTION_SECONDS
    0 (CURRENT)  keep indefinitely. expires_at = NULL, and the purge query
                 filters expires_at IS NOT NULL, so nothing can match.
    positive     expire that many seconds after creation.
  LIVE STATE MEASURED: 28 jobs, 28 with expires_at NULL, 27 with a retained
  file. Nothing is currently eligible for deletion.

  HOUSEKEEPING STILL DELETES (even with retention off):
    - abandoned jobs/<publicId>/ workspaces older than the stale window
    - the workspace of every finished job, success or failure
    - stale PROCESSING jobs are recovered (section 15.6)
    - AudioConversationRepositoryInterface::deleteChildless() removes parents
      with no children left:
        DELETE c FROM audio_conversations c
        WHERE NOT EXISTS (SELECT 1 FROM audio_transcription_jobs j
                          WHERE j.conversation_id = c.id)

    AudioToTextStoreCest::aPostedStoreIdIsIgnored.
    Rationale: consulting the body would let anyone who can reach one store's
    page write onto another store's history.

  STORE NAME / COMPANY / ACTIVE
    src/AudioToText/Domain/AudioStoreLookupInterface.php   (the PORT)
    src/AudioToText/Infrastructure/DbAudioStoreLookup.php  (the ADAPTER)
      const STORES = order58_stores ; const KB = knowledge_bases
      const SOURCE = 'order58'
      SELECT s.source_id, kb.name AS name, s.company, kb.source_active AS active
      FROM order58_stores s
      INNER JOIN knowledge_bases kb ON kb.source_store_id = s.source_id
      WHERE kb.source_system = 'order58' AND s.source_id = ?
    NOTE: the NAME comes from knowledge_bases.name, NOT order58_stores.name,
    because that is the column the picker sorts, buckets and displays. Reading
    the other one would show a different name on the page you arrived at than
    on the card you clicked.

  STORE SOURCE ID FOR AN EXISTING JOB
    src/AudioToText/Domain/AudioConversationRepositoryInterface::storeSourceIdFor(int)
    SELECT store_source_id FROM audio_conversations WHERE id = ?

18.2 DOES AUDIO-TO-TEXT DEPEND ON ORDER58 CLASSES?

  NO. Verified: `grep -rlE "App\\(KnowledgeBase|Rules|Chat|Ai|Order58)"
  src/AudioToText/` returns NOTHING.

  Audio-to-Text reads the order58_stores and knowledge_bases TABLES through its
  own narrow port (DbAudioStoreLookup, ONE query). It duplicates only a lookup,
  following the existing AgentStoreDirectoryInterface precedent.

  The reverse direction is equally constrained: no file outside
  src/AudioToText/ may contain "App\AudioToText". So the Order58 store picker
  links to audio by ROUTE NAME:
    src/Order58/Web/StoreAudio/template.php
      $urlGenerator->generate('audio-to-text.store', ['sourceId' => ...])
  Store chat solved the same problem earlier the same way ('chat.index').

  CONSEQUENCE: the picker LIVES IN ORDER58 (src/Order58/Web/StoreAudio/) and
  reuses StoreDirectoryReaderInterface verbatim — the search SQL, letter
  buckets, filters, counts and pagination are not reimplemented, only asked
  for. It adds NO CSS (reuses .dir-toolbar, .filter-bar, .alpha-nav,
  .store-card, pager).

  Unlike Store chat, audio has NO ELIGIBILITY GATE: a store with no knowledge
  base content can still have a recording transcribed, so every card is a live
  link. (The store must still HAVE a knowledge_bases row to appear at all —
  see the inner join above.)

20. KNOWLEDGE / KNOWLEDGE BASE
================================================================================

  A knowledge base is one retrieval corpus with its own OpenAI vector store.
  For Order58 it is ONE PER STORE (237 rows against 235 mirrored stores).

  TABLES: knowledge_bases, documents, document_index_files,
          document_processing_events

  PROVISIONING
    vector_store_status ENUM('pending','provisioning','ready','failed') with
    provision_attempts / provision_started_at / provision_next_attempt_at and
    error code+message. Done by kf:worker:run, never in a web request.

  DOCUMENTS
    Uploaded (PDF/PNG/JPG/WEBP), stored outside the web root, SHA-256
    deduplicated (checksum_sha256 + dedupe_hash), queued. Text PDFs indexed
    directly; images and scanned PDFs converted to Markdown by a vision model
    first (role='derived_markdown' in document_index_files).
    Manual text documents supported via source_text + is_source_overridden.
    Per-document enable/disable via is_enabled.

  RETRIEVAL
    OpenAI-hosted Vector Stores via the Responses API File Search tool.
    openai_vector_store_id on the knowledge base; openai_file_id per index file.
    THERE IS NO LOCAL VECTOR DATABASE AND NO LOCAL EMBEDDING STORE.

  CHAT INTEGRATION
    conversations -> messages -> message_revisions / chat_answer_scores.
    Retrieval is forced and a server-side grounding check runs on every answer.

20.1 THE THREE CRITICAL ANSWERS

  Q: Does Audio-to-Text use Knowledge Base data during transcription?
  A: **NO.**
     Verified three ways:
       1. src/AudioToText/ contains no reference to App\KnowledgeBase
          (ModuleIsolationTest enforces this).
       2. The whisper argv (AudioTranscriber:196-208) contains no prompt,
          no vocabulary and no hint parameter of any kind.
       3. DbAudioStoreLookup reads knowledge_bases for exactly two fields —
          `name` and `source_active` — for a page heading. Nothing else.

     Base?
  A: **NO.** No document content is read by the audio module at any point.

  Q: Does Audio-to-Text use restaurant-specific vocabulary from any existing
     store data?
  A: **NO.** The only store data it reads is the store's display name,
     company and active flag — for page chrome.

  The ONLY domain knowledge in the audio pipeline is the hard-coded English
  dialogue-act patterns in
  src/AudioToText/Application/Speaker/DialogueActDetector.php, used for ROLE

21. RULES SYSTEM
================================================================================

  There is ONE rule system, not several. "Rule" in this codebase means a
  business rule mirrored from Order58 and turned into retrievable knowledge.
  There is NO condition/action/trigger engine, NO rule priority evaluation, and
  NO runtime rule interpreter.

  IMPORTANT: there are NO audio-related rules of any kind.

  PIPELINE (traced)

    Order58 API
      |  kf:order58:schedule-rules  (daily scheduler)
      v
    order58_rule_records            380 rows — the RAW MIRROR, never edited
      |
      |  Rules\Application deduplication + classification
      |  canonical_hash / description_hash collapse duplicates
      v
    rule_catalog_rules              352 rows — the CANONICAL CATALOGUE
      |    scope_type               store-scoped vs global
      |    classification_status    pending / approved / rejected
      |    classification_confidence
      |    detected_store_text      what the classifier thought it saw
      |    is_active, is_globally_available
      |
      +--> rule_catalog_sources     provenance: which mirrored record(s)
      |                             produced this canonical rule
      +--> rule_store_links         234 rows — which stores this rule applies to
      +--> rule_classification_events  audit of classification decisions
      |
      |  ADMIN REVIEW
      |  POST /admin/order58/rules/review   (Rules\Web\Review\Action)
      v
    DUAL PROJECTION (the design decision recorded in project memory)
      An approved rule is projected into BOTH:
        - the store's own knowledge base            (order58_rule_store)
        - the hidden global rules knowledge base    (order58_rule_global)
      so ANY store can answer a global rule at chat stage 2.
      Reconciler: kf:rules:reconcile-global
      Lifecycle repair: kf:rules:repair-lifecycle
      Retirement: kf:rules:retire-store-projections
      v
    documents rows inside knowledge bases
      v
    indexed into the OpenAI vector store
      v
    RETRIEVED AT CHAT TIME — this is the rule's final effect.

  TRACING ONE RULE END TO END
    1. order58_rule_records row arrives from the API (source_store_id set).
    2. Mapper computes canonical_hash; a matching rule_catalog_rules row is
       reused or created, and rule_catalog_sources records the link.
    3. Classification proposes scope_type + confidence + detected_store_text.
    4. An administrator approves at /admin/order58/rules/review; the decision
       is recorded in rule_classification_events and the projection is
       reconciled IMMEDIATELY (not on a later schedule).
    5. rule_store_links gains a row per applicable store.
    6. A document is written into each target knowledge base and indexed.
    7. At chat time the rule is retrieved by File Search like any other
       document, and is cited like any other document.

  RULE-FACING PAGES

    /admin/order58/rules/{ruleId}    per-rule detail
    POST /admin/order58/rules/review admin decision
    /admin/rule-chat                 chat against the hidden global base

  knowledge_base_rules TABLE: EMPTY (0 rows). NOT DETERMINED whether it is
  superseded by rule_store_links or simply unused — reason: no write path was
  traced during this audit and there are no rows to infer from.

22.2 EACH INTEGRATION, ANSWERED

  Order58 -> Audio-to-Text
    HOW: indirectly and weakly. The store PICKER is an Order58 page that links
    to the audio route BY ROUTE NAME STRING ('audio-to-text.store'). Order58
    also reads audio counts via DbStoreAudioCounts. No class dependency either
    way.

  Store -> Audio-to-Text
    HOW: audio_conversations.store_source_id, set at upload time from the URL
    segment. Read back via storeSourceIdFor(). The store's NAME and ACTIVE
    flag are fetched through AudioStoreLookupInterface for page chrome and the
    upload gate. THIS IS THE ENTIRE INTEGRATION.

  Knowledge -> Audio-to-Text
    HOW: **ONLY** as the source of the store's DISPLAY NAME and source_active
    flag (DbAudioStoreLookup joins knowledge_bases). NO document content, NO
    embeddings, NO vocabulary, NO influence on transcription whatsoever.

  Rules -> Audio-to-Text
    **DOES NOT EXIST.** No code path connects them. No rule affects any audio
    behaviour. No audio-scoped rule type exists.

  Knowledge -> Order58
    HOW: knowledge_bases.source_system='order58' + source_store_id links a
    knowledge base to a mirrored store. The store DIRECTORY is built on an
    INNER JOIN between them, so the two are effectively one concept in the UI.

  Rules -> Knowledge
    HOW: an approved catalogue rule is PROJECTED as a document row into one or
    more knowledge bases (store-specific and/or the hidden global base), then
    indexed. That projection is the rule's only runtime effect.

  Rules -> Order58
    HOW: rule_catalog_sources.order58_rule_record_id (hard FK) traces every
    canonical rule back to the mirrored record(s) it came from.
    rule_store_links.store_source_id scopes a rule to stores by soft reference.

22.3 INTEGRATIONS THAT DO NOT EXIST (explicitly verified)

    Audio-to-Text  ->  Knowledge Base content        NONE
    Audio-to-Text  ->  Rules                         NONE
    Audio-to-Text  ->  Chat                          NONE
    Audio-to-Text  ->  Ai / OpenAI                   NONE
    Audio-to-Text  ->  Order58 classes               NONE
    Audio transcripts -> vector store / retrieval    NONE
    Rules          ->  transcription behaviour       NONE
    Knowledge      ->  transcription behaviour       NONE

  A transcript produced by Audio-to-Text is NEVER indexed, NEVER retrievable
  by chat, and NEVER sent anywhere. It lives only in
  audio_transcription_jobs.transcript and its reviewed counterpart.

25.1 STARTUP VALIDATION
  AudioToTextSettings::problems() runs before the worker claims any work and
  REFUSES TO START on a problem, naming the variable to fix. It checks:
    - binaries and models exist and are executable/readable
    - AUDIO_TRANSCRIPTION_TIMEOUT >= AUDIO_TRANSCRIPTION_MAX_DURATION x 1.5
    - every configured foreign lock is READABLE (the one misconfiguration that
      would otherwise stall the queue in total silence)
  Non-fatal observations print as notes and the worker carries on.

25.2 THE DURATION CHAIN (the one setting that is NOT self-contained)
    MAX_DURATION 300  --(x1.19 measured RTF)-->  ~355 s of whisper

      DIARIZATION_TIMEOUT   300   measured ~49 s at 5 min, ~6x headroom
      STALE_AFTER          1200   must exceed 600 + 300 = 900
      TimeoutStartSec      1200   systemd; must also exceed 900   <- LIVES IN /etc
  The last one is the ONLY part of this feature that cannot be changed from
  .env alone.

  patterns, SeparationBalance thresholds, MIN_ATTRIBUTED_SHARE (0.75).
  These are algorithm coefficients, not operator settings.
  AUDIO_DIARIZATION_MIN_CONFIDENCE remains the ONLY dial, and it decides how
  much certainty is required to publish, not how certainty is reached.

26.1 RISKS (REPORTED, NOT FIXED)

  R1  NO PER-STORE AUTHORIZATION.  Any authenticated administrator can view,
      correct, confirm and download EVERY store's recordings and transcripts.
      This is a documented product decision ("shared administrator demo"), not
      an oversight — but it is worth restating because call recordings may
      contain customer names, addresses and payment discussion. If the admin
      population ever grows beyond one trusted operator, this becomes the
      first thing to revisit. Live admin_users count today: 1.

  R2  FOREIGN-LOCK COUPLING TO ANOTHER PROJECT'S FILESYSTEM.
      AUDIO_WORKER_FOREIGN_LOCKS points at
      /var/www/html/telecom-billing/runtime/audio-to-text/cron-worker.lock.
      That directory is 0750 www-data:www-data. If this worker ever runs as a
      different user it will defer EVERY tick. It fails closed with a warning,
      which is correct — but the queue stalls silently to anyone not reading
      the startup output.

  R3  AUDIO_WORKER_YIELD_TO_OTHER_WHISPER IS RACY BY CONSTRUCTION.
      Documented as such. It must never be treated as an exclusivity
      guarantee. Only the flock mechanisms are.

  R4  DEAD AUDIO_CHAT_* CONFIGURATION IN .env (section 24.8).
      Not exploitable — the values are never read — but a future reader could
      reasonably assume transcripts are being sent to gpt-4o-mini, which they
      are not. Misleading configuration is a security-communication risk.

  R5  RETAINED RECORDINGS ARE KEPT FOREVER BY DEFAULT.
      AUDIO_TRANSCRIPTION_RETENTION_SECONDS=0. 27 recordings currently on
      disk with expires_at NULL. There is no data-retention expiry and no
      deletion UI. This is a deliberate setting, but it is a compliance
      surface for recordings of real customer calls.

  R6  INTEGRATION TESTS OPERATE ON THE LIVE DATABASE (section 28.2).
      Not a production risk, but a real operational one.

  tests/Integration/AudioToText/TranscriptionJobRepositoryTest.php exercises
  claimNextQueued() against the **LIVE** database — one case drains the queue
  in a loop. It WILL claim a real administrator's queued jobs and leave them
  PROCESSING when the test ends. The stale sweep then fails them after
  AUDIO_TRANSCRIPTION_STALE_AFTER and the recording must be uploaded again.

  CHECK BEFORE RUNNING ANY DB-TOUCHING SUITE:

              WHERE status IN ('QUEUED','PROCESSING')" knowledge_forge_db

  RECOVERY (nothing is lost — no transcript was written yet):

       SET status='QUEUED', processing_stage='QUEUED', started_at=NULL
     WHERE id IN (...) AND status='PROCESSING';

29.1 THROUGHPUT — THE 50-FILE QUESTION, ANSWERED

  Q: If 50 files are uploaded at once, what happens?
  A: ALL 50 ARE QUEUED IMMEDIATELY. AUDIO_TRANSCRIPTION_MAX_QUEUE = 0 means no
     cap, so no upload is refused. All 50 rows land in
     audio_transcription_jobs with status='QUEUED'.

  Q: How many process concurrently?
  A: EXACTLY ONE. Machine-wide. Guaranteed by flock on worker.lock plus the
     atomic conditional claim (section 16.3).

  Q: In what order?
  A: Strict FIFO by auto-increment id. ORDER BY id ASC. A recording uploaded
     later can never be taken before an earlier one.

  Q: A mix of 2 min / 4 min / 1 min / 5 min?
  A: Each is transcribed at roughly 1.19-1.36x real time end to end, one after
     another, with a timer tick every 2 minutes. Worked example for
     2+4+1+5 = 12 minutes of audio:
       ~2.4 + ~4.8 + ~1.2 + ~6.0  =  ~14.4 minutes of processing
     plus up to 2 minutes of queue wait per job, because the unit is
     `--once` and a new tick is needed after each job finishes.
     PRACTICAL RULE: throughput ceiling is roughly 45 minutes of audio per
     hour of wall clock, minus tick latency. Fifty 5-minute files (250 minutes
     of audio) would take on the order of 5-6 hours to drain.

  Q: Does a long job block the next tick?
  A: systemd will not start a second run while the unit is active, so the tick
     that lands mid-job is SKIPPED, not queued in parallel. A 5-minute
     recording (~404 s) outlives the 2-minute interval and skips ~3 ticks.

  Q: What limits throughput?
  A: Deliberately, everything: one core (CPUQuota=100%), one thread
     (AUDIO_TRANSCRIPTION_THREADS=1), one job, a 2-minute tick, an admission
     guard, and a shared lock with another project. This is a demo box running
     nginx, PHP-FPM and MySQL alongside.

31. DEEPGRAM INTEGRATION READINESS   (ANALYSIS ONLY — NOTHING IMPLEMENTED)
================================================================================

  31.1 WHERE WOULD IT BELONG?
    src/AudioToText/Infrastructure/  alongside AudioTranscriber.php, as a
    sibling adapter (e.g. DeepgramTranscriber), with a new port in
    src/AudioToText/Domain/ and the binding in
    config/common/di/audio-to-text.php. This mirrors EXACTLY how diarization
    already works: SpeakerDiarizerInterface with SherpaOnnxSpeakerDiarizer and
    NullSpeakerDiarizer behind it.

  31.2 WHAT EXISTING INTERFACE COULD SUPPORT IT?
    NONE for transcription. There is no TranscriberInterface.
    The nearest precedent that shows the intended shape:
      src/AudioToText/Domain/Speaker/SpeakerDiarizerInterface.php

  31.3 WHAT IS CURRENTLY COUPLED TO WHISPER?
    (a) src/AudioToText/Infrastructure/AudioTranscriber.php — the whole class
    (b) TranscriptionSettings properties `whisperBinary`, `whisperModel`
    (c) env names WHISPER_BINARY / WHISPER_MODEL and their Environment.php SPEC
    (d) AudioTranscriptionException::whisperMissing() / ::modelMissing()
    (e) the direct call sites in AudioTranscriptionWorkerCommand
    (f) startup validation in AudioToTextSettings::problems()
    (g) tests/Unit/AudioToText/WebTierCannotRunWhisperTest.php (names the class)
    (h) the local-only claim in docs and in the UI copy

  31.4 WHICH TABLES COULD REMAIN UNCHANGED?
    ALL FOUR AUDIO TABLES, unchanged. Nothing in the schema is Whisper-shaped:
      audio_transcription_jobs   transcript, detected_language, duration,
                                 speaker_segments are all provider-neutral
      audio_conversations        provider-agnostic entirely
      audio_segment_revisions    provider-agnostic entirely
      audio_worker_heartbeat     provider-agnostic entirely

  31.5 WHICH FIELDS ARE WHISPER-SPECIFIC?
    NONE at the column level.
    `speaker_separation_method` is a free-text identifier that would simply
    carry a different value. `speaker_role_confidence` is computed by OUR
    mapper, not by the engine — if Deepgram supplied its own diarization, the
    meaning of this column would need a deliberate decision (see 31.6).

  31.6 COULD DIARIZATION COME FROM DEEPGRAM INSTEAD OF SHERPA?
    YES, structurally — SpeakerDiarizerInterface already abstracts it, so a
    DeepgramDiarizer could satisfy the same port.
    BUT two consequences would need deciding, not assuming:
      (i)  Deepgram returns speaker labels WITH the transcript in one call, so
           the current two-stage shape (transcribe, then diarize, then align)
           would collapse. SpeakerTranscriptAligner might become unnecessary
           for that provider while remaining necessary for whisper.
      (ii) `speaker_role_confidence` and the five gates are OURS. Deepgram
           gives speaker separation but NOT customer/agent role assignment, so
           SpeakerRoleMapper, the dialogue acts and the gates WOULD STILL RUN.
           This is a strength: the role logic is provider-independent.

  31.7 COULD MANUAL REVIEW CONTINUE WORKING?
    YES, entirely unchanged. The review layer consumes `speaker_segments` (a
    neutral JSON shape) and knows nothing about where it came from. Every
    correction operation, the audit trail, the optimistic lock, the history
    derivation and the Original-transcript page would all keep working
    untouched.

  31.8 COULD COMMON AND SEPARATE MODES CONTINUE WORKING?
    YES. The mode branch is on `$job->sourceRole?->isProvided()` in the worker,
    which is entirely independent of the transcription provider. SEPARATE would
    still skip diarization; COMMON would still run it.

  31.9 COULD WE SEND RESTAURANT-SPECIFIC KEYTERMS PER STORE?
    STRUCTURALLY YES — the store is already known at job time
    (audio_conversations.store_source_id) and resolvable in the worker.
    BUT TODAY NOTHING IS BUILT: no keyterm source, no keyterm storage, no
    plumbing from a job to any vocabulary, and the worker does not currently
    load the store at all. This would be new work in three places: a source of
    terms, a way to attach them to a job, and a provider that accepts them
    (whisper.cpp does not; Deepgram does).

  31.10 IS THERE EXISTING STORE/KNOWLEDGE DATA THAT COULD GENERATE KEYTERMS?
    YES, and this is the most promising finding in this section.
      documents            425 rows, with `source_text` (mediumtext) holding
                           extracted/manual document text per knowledge base
      knowledge_bases      237 rows, one per store, linked by
                           source_store_id -> order58_stores.source_id
      order58_knowledge_records  115 rows of mirrored store knowledge
      rule_catalog_rules   352 rows of rule text, scoped to stores via
                           rule_store_links (234 rows)
    A store's menu terminology, if it is present anywhere, is in those document
    bodies. The JOIN PATH ALREADY EXISTS AND IS SHORT:
      audio_conversations.store_source_id
        -> knowledge_bases (source_system='order58', source_store_id=...)
          -> documents.knowledge_base_id
    CAVEAT NOT TO GLOSS OVER: nobody has verified that these documents actually
    CONTAIN menu items. They may be policies, hours or rules. Extracting useful
    keyterms would need a term-extraction step, not a straight read.
    NOTE ALSO: any such link would be the FIRST dependency from Audio-to-Text
    to Knowledge, and ModuleIsolationTest FORBIDS naming App\KnowledgeBase from
    inside src/AudioToText/. It would have to go through a narrow port in the
    DbAudioStoreLookup style (read the tables, name no foreign class), or the
    isolation rule would have to be deliberately amended.

  31.11 WHERE COULD A LEARNED-CORRECTIONS DICTIONARY BE STORED?
    No such table exists. A new one would be needed. The natural shape,
    following this codebase's existing conventions:
      - scoped by store_source_id (soft reference, like every other store link)
      - or global, with a scope column, mirroring rule_catalog_rules.scope_type
      - with an occurrence counter to implement "after 2-3 times, remember it"
      - with an approval flag, mirroring the rules classification workflow
        (nothing in this system auto-publishes a machine inference — every
        comparable feature has an admin gate)
    It would be a NEW migration. This audit creates none.

  31.12 WOULD EXISTING CORRECTION HISTORY HELP BUILD THAT DICTIONARY?
    YES — this is the strongest existing asset for the feature.
    `audio_segment_revisions` (118 rows today) stores the FULL conversation
    BEFORE every accepted correction, with operation, editor and timestamp,
    and the current state is on the job. The infrastructure to extract exactly
    what changed ALREADY EXISTS AND IS TESTED:
      src/AudioToText/Domain/Speaker/ConversationDiff.php
        -> isolates the contiguous changed run between two snapshots
      src/AudioToText/Application/ConversationHistoryBuilder.php
        -> walks the whole chain and produces before/after pairs per message
    Filtering those events to `operation = EDIT_TEXT` with a 1->1 shape yields
    a clean corpus of (before text, after text) wording corrections, already
    attributed to an administrator and a moment.
    LIMITATIONS TO STATE HONESTLY:
      - only 118 revisions exist, across 8 corrected jobs. That is a very small
        corpus; "2-3 occurrences" thresholds would rarely trigger yet.
      - EDIT_TEXT events replace a WHOLE TURN's text, not a word. Extracting
        "one ton" -> "wonton" from "we have one ton soup" -> "we have wonton
        soup" needs a word-level diff that does not exist today.
      - corrections made before a REVERT describe a conversation that was
        discarded; the history builder already excludes those, and a dictionary
        builder would need the same rule or it would learn from withdrawn edits.

  31.13 SUMMARY OF WORK REQUIRED (NOT DONE, NOT PLANNED HERE)
    To add a second provider, the minimum honest list is:
      1. Introduce a transcription port (interface) in Domain/
      2. Make AudioTranscriber implement it (no behaviour change)
      3. Rename or generalise the whisper-specific settings/env names, OR keep
         them and add provider-specific ones alongside
      4. Add the new adapter + its settings + its startup validation
      5. Bind by configuration in config/common/di/audio-to-text.php
      6. Decide what happens to diarization when the provider supplies it
      7. Update WebTierCannotRunWhisperTest so the guard still holds
    Steps 1-2 alone are a safe, behaviour-preserving refactor that would make
    everything after it optional.

          uploads drains over hours, with no visibility beyond the queue count.
  RISK-5  Gate 2 exists because a confidently-wrong split reached COMPLETED
          once (21911549.wav). The gates are sound now, but the class of bug —
          "confident and useless" — recurs whenever a new gate is added
          without asking what question it answers.
  RISK-6  Single point of failure: flock covers one machine. Any move to a
          second host silently breaks the single-worker guarantee.
  RISK-7  The role mapper is tuned for English restaurant/order calls. Any
          other domain or language will transcribe fine and then land in
          NEEDS_REVIEW, which looks like a failure but is the system being
          honest.
