--------------------------------------------------
1. OVERVIEW
--------------------------------------------------

"Test Recording Channels" is a hidden, admin-only diagnostic page. Its single job is to prove, by
making one real HTTP request at a time, that this server can fetch a specific channel of a specific
call recording from the client's external Order58 recording API - and to say in plain words what
happened when it cannot.

The client's telephony platform produces up to three files per recorded call:

    22342359.wav          the mixed recording  (both parties in one file)
    22342359-caller.wav   the caller's channel  (one side only)
    22342359-callee.wav   the callee's channel  (one side only)

This page lets an operator pick a call, pick one of those three channels, fire exactly one GET at
the external API, and see: the exact URL that was sent, the HTTP status, the Content-Type, the byte
count, whether the bytes are really a WAV file, a plain-English diagnosis, and - when it really is
audio - an inline player and a download button.

What it deliberately does NOT do (verified, and enforced by
tests/Unit/Order58/RecordingChannelIsolationTest.php):

  * it reads no database and writes no database
  * it enqueues no job and touches no worker
  * it saves no file anywhere
  * it shares no code with the Order58 sync client or with the Audio-to-Text feature
  * it sends no credential of any kind (no Bearer token, no Authorization header)

It is a debugging aid bolted onto the side of the application, and it is kept that way on purpose.

--------------------------------------------------
3. PURPOSE OF THE TEST RECORDING CHANNELS PAGE
--------------------------------------------------

Three concrete purposes, in the order an operator meets them:

  (a) Find a call. The "Latest calls" card lists an account's recent calls from the external API so
      a real call session id can be picked rather than typed from memory.

  (b) Test one channel of one call. The "Request" card builds exactly one URL and sends exactly one
      GET, then reports everything about the answer.

  (c) Prove the bytes are the right thing. The dangerous failure here is NOT a 404. It is a request
      that returns HTTP 200 with the MIXED recording while the page claims it is the caller channel.
      That reads as success, gets believed, and is only caught later by somebody listening to a
      training file and hearing two voices where they expected one. Almost every design decision in
      this feature exists to make that specific failure impossible or visible.

5. COMPLETE REQUEST FLOW
--------------------------------------------------

There are three distinct flows. They are independent: loading calls never fetches a recording, and
fetching a recording never reloads the call list unless the form carried load_calls=1 through.

FLOW A - open the page (no probing)

  browser GET /admin/order58/test-recording-channels
    -> RequireAdminMiddleware (admin group, config/common/routes.php:64-66)
    -> Action::__invoke()
         reads query params, applies the DEFAULT_* constants for anything missing
         $submitted = ($params['submitted'] ?? null) === '1'   -> false
         $loadCalls = ($params['load_calls'] ?? null) === '1'  -> false
         $latest = null ; $outcome = null
    -> renders template.php with the form pre-filled
    -> NOTHING is sent anywhere. A bare URL never probes.

FLOW B - "Load Latest Calls"  (submits load_calls=1)

  browser GET ...?load_calls=1&account_id=871&limit=10&<channel form values carried along>
    -> Action::__invoke() -> Action::runLatestCalls()
    -> LatestCallsRequest::validate()      invalid -> validationError, nothing sent
    -> LatestCallsRequest::fromStrings()
    -> (fixtures?) FixtureRecordingSource::latestCalls()
       (live)      ChannelApiProbe::latestCalls()
                     -> ChannelRequestMapping::latestCallsUrl()
                     -> ChannelApiProbe::send()  ... GET {base}/{accountId}/latest-calls?limit={n}
                     -> readBounded() -> ChannelDiagnosis::forJson()
                     -> json_decode(..., depth 32, JSON_THROW_ON_ERROR)
                     -> CallSummary::fromDecoded()
    -> LatestCallsResult
    -> template prints the URL, the diagnosis, and a table of calls with a "Use This Call" link.
       That link is a plain GET back to this same page carrying recording_id (and a derived date,
       when one could be read with certainty). It carries NO submitted=1, so selecting a call
       fetches nothing.

FLOW C - "Test / Fetch Recording"  (submits submitted=1)

  browser GET ...?submitted=1&recording_id=22447829&merchant_id=871&channel=callee
                 &time=2026-03-11&company=SWCC&name=test&account_id=871&limit=10
    -> Action::__invoke() -> Action::run()
    -> ChannelRecordingRequest::validate(recordingId, merchantId, time, company, name)
         invalid -> outcome['validationError'], NOTHING is sent, no URL is even built
    -> new ChannelRecordingRequest(...)
    -> Action::runLive()  (or runFixture() when ?source=fixture and env is dev/test)
         -> ChannelApiProbe::urlFor() -> ChannelRequestMapping::urlFor()
              mixed  -> mixedUrl()
              caller
              callee -> channelUrl()   <- the confirmed format
            (throws UnconfirmedChannelMapping if the candidate is unrecognised; nothing is sent)
         -> ChannelApiProbe::inspect()
              -> send() (Guzzle GET, no auth, streamed)
              -> readBounded()  (whole body counted, first 8192 bytes kept)
              -> WavSignature::inspect()
              -> ChannelDiagnosis::fromResponse(status, contentType, sample, totalBytes)
         -> ChannelProbeResult
         (any Throwable from the transport is caught here and turned into
          ChannelDiagnosis::fromTransportFailure() + a "Class: message" details block)
    -> template prints: Recording ID, Merchant ID, Channel, Path segment, Name sent, Source,
       the exact request URL, the diagnosis, status/Content-Type/bytes/Content-Length/Valid WAV,
       and - only when $result->isPlayable() - the <audio> player and the Download button.

FLOW D - play or download (a separate request, made by the browser)

  browser GET /admin/order58/test-recording-channels/download?recording_id=...&channel=callee
              &time=...&company=...&name=...&merchant_id=...[&disposition=inline][&source=fixture]
    -> DownloadAction::__invoke()
         channel unknown            -> 400 text/plain diagnostic
         ChannelRecordingRequest::validate() fails -> 400 text/plain diagnostic
    -> DownloadAction::fromLive()
         -> ChannelApiProbe::urlFor()   (same builder as the page - cannot drift)
         -> ChannelApiProbe::open()     (same GET, body left unread)
         -> non-2xx                 -> 502 text/plain with the diagnosis + upstream snippet
         -> peek first 64 bytes, WavSignature::inspect()
         -> not a WAV               -> 502 text/plain ("the body is not a WAV file")
         -> deliver(): the peeked head is put back in front of the stream, and the response is
            Content-Type: audio/wav
            X-Content-Type-Options: nosniff
            Cache-Control: no-store, private
            Content-Disposition: inline|attachment; filename="<id>-callee.wav"
            Content-Length: <size>  (when known)


--------------------------------------------------
6. FRONTEND FLOW
--------------------------------------------------

There is no frontend framework here, and this is worth stating plainly because the task description
expected one:

  * No Blade, no Vue, no React.
  * No JavaScript at all - template.php contains no <script> tag and registers no asset bundle.
  * No AJAX, no fetch(), no XMLHttpRequest.
  * No CSRF token: both routes are GET-only and read-only.

Everything is plain HTML:

  1. Two independent <form method="get"> elements, both posting back to the page's own URL.
     - Form 1 ("Latest calls") carries a hidden load_calls=1 plus hidden copies of every channel-
       form value, so loading a list does not wipe a half-filled form below (template.php:109-124).
     - Form 2 ("Request") carries a hidden submitted=1 plus hidden account_id/limit (and load_calls
       when a list is already on screen), so fetching a recording does not wipe the call list
       (template.php:260-269).
  2. The channel is a set of three radio buttons named `channel`, values mixed / caller / callee.
     Each label shows the concrete path segment that channel would use, e.g. `22447829-callee`
     (template.php:294-321). For an invalid recording id it shows the pattern `{id}-callee`
     instead, so no URL-like string is ever printed for input that was refused.
  3. "Use This Call" in the calls table is an ordinary <a href> back to the page with
     recording_id pre-filled and #channel-test as the fragment.
  4. Playback is the browser's native element:
         <audio class="a2t-player__control" controls preload="none" src="<download URL>?...&disposition=inline">
     The src is SAME-ORIGIN - it points at this application's own download route, never at
     order58.xrainbow.com. So the external host, and any future credential, never reach the browser.
     preload="none" means nothing is fetched until the operator presses play.
  5. "Download" is an ordinary <a href> to the same route without disposition=inline, which makes
     it an attachment.


--------------------------------------------------
7. BACKEND FLOW
--------------------------------------------------

Step by step, with the real names:

  1. Routing. config/common/routes.php lines 319-325 map the two URLs to
     Order58TestRecordingChannels\Action::class and ...\DownloadAction::class. Both are inside the
     admin Group (line 64) carrying RequireAdminMiddleware and DomainExceptionMiddleware.

  2. Parameter reading. Action::__invoke() calls Action::text() on each query parameter. text()
     returns the trimmed scalar, or the supplied default when the value is absent, non-scalar or
     empty. This is why a bare page load shows 22342359 / 871 / 2026-03-11 / SWCC / test.

  3. Channel resolution. RecordingChannel::fromStorage($params['channel']) ?? RecordingChannel::Mixed
     - an unknown channel silently becomes Mixed on the PAGE. (The DOWNLOAD endpoint is stricter: an
     unknown channel there is a 400, because that route hands over bytes.)

  4. Fixture gate. FixtureAvailability::isRequested($params['source']) - true only when APP_ENV is
     dev or test AND source=fixture is on this very request.

  5. Validation before anything goes on the wire. ChannelRecordingRequest::validate() returns the
     first problem as a sentence, or null. On a problem the action returns immediately with
     validationError set; no URL is constructed, so the page cannot even display one.

  6. URL construction. ChannelApiProbe::urlFor() -> ChannelRequestMapping::urlFor(). This is the
     only place a URL is built. RecordingChannelIsolationTest asserts that no other file in the
     directory builds channel strings.

  7. The call. ChannelApiProbe::send() - Guzzle, GET, no Authorization header, http_errors disabled
     (so a 403/404 is data to report, not an exception), redirects followed, body streamed.

  8. Bounded reading. ChannelApiProbe::readBounded() reads the WHOLE body to get an honest byte
     count but keeps only the first 8192 bytes. The honest count is what catches a truncated
     download - a file that has a perfectly valid header and is cut short.

  9. Verdicts. WavSignature::inspect() answers "is this a WAV, and is it complete?" from the bytes.
     ChannelDiagnosis::fromResponse() turns status + content type + sample + size into a headline
     and an action. Neither of them ever echoes a header, a token or a credential.

 10. Rendering. The template decides nothing; every verdict arrives already settled.


--------------------------------------------------
8. EXTERNAL ORDER58 API INTEGRATION
--------------------------------------------------

Host / base URL (ChannelRequestMapping::BASE_URL):

    https://order58.xrainbow.com/api/external/recording

Authentication: NONE. No Bearer token, no API key, no Authorization header, no cookie. The only
header sent is `Accept: application/json` (ChannelApiProbe::send()). The endpoint is gated on the
provider's side by an IP ALLOWLIST - this server's public IP has to be whitelisted by the client.
That is why ChannelDiagnosis has a dedicated `ip-not-whitelisted` verdict, detected from the
provider's own wording in the 403 body (`403 Forbidden - IP not authorized: <address>`) rather than
assumed from the status code.

Timeouts: connect 10s, total 60s. Redirects are followed. HTTP error statuses do NOT throw.

Nothing is cached, retried or persisted. One page submit = one outbound GET.


--------------------------------------------------
9. API ENDPOINTS
--------------------------------------------------

ENDPOINT 1 - latest calls for an account
----------------------------------------
  Method        : GET
  URL           : {BASE_URL}/{accountId}/latest-calls?limit={limit}
  Built in      : ChannelRequestMapping::latestCallsUrl(int $accountId, int $limit)
  Called from   : ChannelApiProbe::latestCalls(), from Action::runLatestCalls()
  Query params  : limit (int, 1..500, page default 10) - built with http_build_query
  Path params   : accountId (positive int, <= 9 digits)
  Headers       : Accept: application/json
  Auth          : none
  Body          : none (GET)
  Example       : https://order58.xrainbow.com/api/external/recording/871/latest-calls?limit=10
  Expected resp : a JSON array of call objects. Only three fields are read, because only three are
                  known to exist: callTime, callSessionId, orderId (CallSummary::fromArray()).
  Parsing       : ChannelDiagnosis::forJson(status, body) first; then, on success,
                  json_decode($body, true, 32, JSON_THROW_ON_ERROR) and CallSummary::fromDecoded().
                  A JsonException becomes ChannelDiagnosis::invalidJson(). Valid JSON that is not a
                  list of calls becomes invalidJson() too; a valid but empty array becomes
                  ChannelDiagnosis::noCalls(). Those are deliberately different messages.
  Used for      : the table of calls, each with a "Use This Call" link that pre-fills the channel
                  form's Recording ID (and Time, when CallSummary::derivedDate() can read one).
  Errors        : any non-2xx routes through the shared branches of ChannelDiagnosis::fromResponse();
                  a transport failure is caught in Action::runLatestCalls() and shown as
                  "Class: message" with no stack trace.
  Channel note  : this endpoint knows nothing about channels.

ENDPOINT 2 - fetch a MIXED recording
------------------------------------
  Method        : GET
  URL           : {BASE_URL}/fetch/{recordingId}?time={time}&company={company}&name={name}
  Built in      : ChannelRequestMapping::mixedUrl()
  Called from   : ChannelApiProbe::inspect() (page) and ChannelApiProbe::open() (download)
  Path params   : recordingId - the call session id, rawurlencode()d
  Query params  : time, company, name - all http_build_query()d
  Headers/auth  : Accept: application/json ; no credential
  Example       : https://order58.xrainbow.com/api/external/recording/fetch/22447829
                  ?time=2026-03-11&company=SWCC&name=test
  Expected resp : the WAV bytes. The live endpoint answers Content-Type: application/octet-stream
                  for perfectly good audio, which is why Content-Type is reported but never used as
                  the verdict (WavSignature class docblock).
  Parsing       : body counted whole, first 8192 bytes sampled, WavSignature::inspect(),
                  ChannelDiagnosis::fromResponse().
  Used for      : the result card, the inline player, the download.
  Channel note  : `name` here is passed through from the form EXACTLY as the operator typed it
                  (default "test"). It is not derived and not used for addressing.

ENDPOINT 3 - fetch a CALLER or CALLEE recording   (the format fixed yesterday)
-----------------------------------------------------------------------------
  Method        : GET
  URL           : {BASE_URL}/fetch/{recordingId}-caller?time={time}&company={company}
                  &name={recordingId}-caller
                  (and the same with -callee)
  Built in      : ChannelRequestMapping::channelUrl(), arm CANDIDATE_ID_CARRIES_SUFFIX
  Called from   : ChannelApiProbe::inspect() and ChannelApiProbe::open()
  Path params   : rawurlencode($channel->requestSegmentFor($request->recordingId))
                  -> "22447829-callee"
  Query params  : time      = the form's Time field, verbatim
                  company   = the form's Company field, verbatim
                  name      = $channel->downloadNameFor($request->recordingId) -> "22447829-callee"
                              NOTE: this OVERRIDES whatever the operator typed in the Name field,
                              and carries NO .wav extension.
  Headers/auth  : Accept: application/json ; no credential
  Example       : https://order58.xrainbow.com/api/external/recording/fetch/22447829-callee
                  ?time=2026-03-11&company=SWCC&name=22447829-callee
  Expected resp : the WAV bytes of that one channel.
  Parsing/usage : identical to endpoint 2 - the tool treats the response the same way whichever
                  channel was asked for. That sameness is deliberate: the ONLY difference between a
                  mixed and a caller request is the URL.
  Errors        : a 404 here most often means this merchant has no separated channels at all (see
                  section 23), not that the URL is wrong.

10. REQUEST PARAMETERS AND THEIR SOURCES
--------------------------------------------------

Taking the example the task asked about:

        ?time=2026-03-11&company=SWCC&name=22447829-callee

               setting, not a database row. Confirmed: a grep finds this host only in

      Source : the Latest calls form only. They address endpoint 1 and never appear in a fetch URL.

--------------------------------------------------
11. RECORDING NAMING / IDENTIFIER LOGIC
--------------------------------------------------

Three different strings are derived from one recording id, and keeping them apart is the whole
lesson of yesterday's fix. All three live in RecordingChannel.php and nowhere else.

  method                     mixed          caller                callee
  -------------------------------------------------------------------------------------
  requestSegmentFor($id)     22447829       22447829-caller       22447829-callee
  downloadNameFor($id)       22447829       22447829-caller       22447829-callee
  fileNameFor($id)           22447829.wav   22447829-caller.wav   22447829-callee.wav

  requestSegmentFor()  -> goes in the URL PATH. This is how the file is addressed.
  downloadNameFor()    -> goes in the `name` QUERY PARAMETER (caller/callee only). Display name.
                          Currently identical to requestSegmentFor(), but it is a separate method
                          on purpose: they answer different questions, and if the provider ever
                          changes one, only that one moves.
  fileNameFor()        -> used in THREE places, none of them the live URL:
                            1. DownloadAction::deliver() - the Content-Disposition filename this
                               application gives the browser;
                            2. FixtureRecordingSource::pathFor()/describe() - the local sample file
                               name;
                            3. Action::__invoke()'s `$fileName` variable, which is used only as a
                               "did validation pass?" flag for the template.
                          It also still appears inside the REJECTED CANDIDATE_NAME_IS_FILENAME arm
                          of ChannelRequestMapping::channelUrl(), which production never takes.

Why downloadNameFor() has no extension: the provider appends one. Sending
`name=22447829-caller.wav` produces `22447829-caller.wav.wav` on the recipient's disk. The client
called this out explicitly; the commit message records it, and the separate method exists so the
two strings cannot be accidentally unified again.

Safety: RecordingChannel::fileNameFor() and requestSegmentFor() cannot refuse bad input, so their
docblocks state - and a test asserts - that every id reaching them has already passed
ChannelRecordingRequest::validate(). Digits-only makes `../`, absolute paths, NUL bytes, quotes,
newlines and separators structurally impossible rather than filtered afterwards.

--------------------------------------------------
16. ROOT CAUSE
--------------------------------------------------

The channel suffix was being put in the WRONG PART OF THE URL.

The provider addresses a recording by its PATH SEGMENT. The `name` query parameter is only the
download display name - it does not select anything. So the old request:

  * asked for `/fetch/22447829` - which is the address of the MIXED file;
  * decorated it with `name=22447829-caller.wav`, which the provider used only to name the download.

The provider therefore did exactly what it was asked: it returned the mixed recording, with a 200,
named "caller". Nothing in the response distinguished it from a correct answer - same status, same
Content-Type, same RIFF/WAVE header, same plausible size - which is why it could not be caught by
any of the page's own checks and had to be caught by the client telling us the right URL.

A second, smaller defect rode along: even when `name` was used as a display name, it was being sent
WITH a .wav extension, and the provider appends its own, so downloads landed as
`22447829-caller.wav.wav`.

Root cause in one sentence: the application inferred the caller/callee request format from a
filename convention the client had supplied, rather than from a worked example URL, and picked the
reading that put the channel in `name` while leaving the addressing path bare.

--------------------------------------------------
22. API RESPONSE HANDLING
--------------------------------------------------

Recording responses (endpoints 2 and 3), in ChannelApiProbe::inspect():

  * The body is streamed and read in 8192-byte chunks. EVERY byte is counted; only the first 8192
    are retained. A multi-megabyte recording never reaches the HTML and is never written to disk.
  * WavSignature::inspect(sample, totalBytes) decides:
      - 0 bytes                      -> "The response body was empty."
      - < 12 bytes                   -> "Too short to contain a WAV header."
      - no 'RIFF' at offset 0        -> not a WAV
      - 'RIFF' but no 'WAVE' at 8    -> a RIFF file but not audio (AVI/WebP also start with RIFF)
      - < 44 bytes                   -> valid header, far too small to hold audio
      - received < declared size + 8 -> valid header but TRUNCATED
      - otherwise                    -> valid, complete WAV
  * Content-Type is recorded and displayed but never decides anything: the live endpoint sends
    application/octet-stream for real audio.
  * ChannelDiagnosis::fromResponse() turns (status, contentType, sample, totalBytes) into a headline
    and advice - see section 23 for the branches.
  * ChannelProbeResult::textPreview() prints the body ONLY when it is not a WAV (an error page or a
    JSON refusal), control characters stripped, capped at 2000 characters.

Call-list responses (endpoint 1), in ChannelApiProbe::latestCalls():

  * ChannelDiagnosis::forJson() first; on success json_decode(depth 32, JSON_THROW_ON_ERROR).
  * CallSummary::fromDecoded() takes only array items and reads only callSessionId, callTime,
    orderId. A row with no session id, or one that would fail the digits-only rule, is still SHOWN
    in the table but gets no "Use This Call" button, and LatestCallsResult::unusableCount() tells
    the operator how many such rows there were.

Download responses, in DownloadAction::fromLive():

  * Only the first 64 bytes are peeked for the RIFF/WAVE check, then put back in front of the stream
    so the browser gets the whole file.
  * The upstream Content-Disposition is deliberately IGNORED - it is a hint from an external server,
    and this tool knows exactly what it asked for.


--------------------------------------------------
23. ERROR HANDLING AND FALLBACKS
--------------------------------------------------

THE HEADLINE ANSWER: there is NO fallback to mixed audio. Anywhere. If a caller or callee request
fails, it is reported as a failure. The tool never retries with a bare path, never substitutes the
mixed file, and never silently degrades. This is a deliberate design rule, stated in
ChannelRequestMapping's class docblock and in UnconfirmedChannelMapping, and it is why the
UnconfirmedChannelMapping exception exists: refusing to build a URL beats guessing one, because a
guess that answers 200 with the mixed file reads as success.

Diagnosis branches (ChannelDiagnosis::fromResponse):

  401  unauthorized        -> the endpoint is IP-gated and sends no credential, so a 401 means the
                              provider changed how it authenticates. Ask the client.
  403  ip-not-whitelisted  -> only when the body matches the provider's allowlist wording
                              (looksLikeIpRejection(): /\bip\b[^\n]{0,40}\b(not authoriz|not allow|
                              whitelist|allowlist)/i or the reverse order). Advice: send the client
                              this server's public IP.
  403  forbidden           -> a 403 whose body does NOT look like an allowlist rejection: about this
                              recording, not this server.
  404  not-found           -> the file is not there for these parameters.
  429  rate-limited        -> wait and retry.
  408  timeout             -> transient.
  >=500 server-error       -> the provider's side.
  other non-2xx            -> unexpected-status, raw response shown.
  200 + 0 bytes            -> empty-body, explicitly called a failure ("an empty file saved as .wav
                              would look like a working download and play silence").
  200 + not a WAV          -> not-audio, with the body preview.
  200 + truncated WAV      -> truncated. This is the ONE non-success verdict that is treated as a
                              caveat rather than an outright failure (ChannelDiagnosis::isFailure()
                              excludes it), so the page styles it as a warning.
  200 + complete WAV       -> ok. Only this state makes the player and Download button appear
                              (ChannelProbeResult::isPlayable() === diagnosis->isSuccess()).

Transport failures (no HTTP response at all - DNS, TLS, refused connection, client timeout) are
caught inside Action::runLive() / Action::runLatestCalls() and turned into
ChannelDiagnosis::fromTransportFailure() plus a "Class: message" details block. The exception class
and message only - never a stack trace, because this page is reachable by any administrator and a
trace is internal filesystem layout. Catching locally also means no other route's error behaviour
changes.

Validation failures never reach the network: the page shows "Nothing was sent." and the offending
rule, and no URL is displayed at all.

What happens when a channel-specific recording is unavailable: the provider answers 404 and the page
shows the not-found diagnosis. The page's standing notice (template.php:83-98) explains the most
likely reason first:

    "Separated channels exist only for the merchants on the client's list. Every account has a mixed
     recording. Caller and callee files are generated only for listed merchants, so a session id
     belonging to any other merchant returns nothing for those two however well-formed the request
     is. A 404 on caller or callee therefore usually means THIS MERCHANT HAS NO SEPARATED CHANNELS,
     not that the URL is wrong."

On the download route the same situations produce plain-text diagnostics rather than a file:
  400 - unknown channel, or a value the form would have rejected
  501 - the channel mapping is unconfirmed (unreachable with the current DEFAULT_CANDIDATE)
  502 - upstream non-2xx, upstream transport failure, or a 2xx whose body is not a WAV
Plain text on purpose: whatever went wrong, the browser must not be told to save it as a .wav.

24. IMPORTANT IMPLEMENTATION NOTES
--------------------------------------------------

  1. One URL builder. ChannelRequestMapping is the only place any URL is constructed, and
     RecordingChannelIsolationTest enforces it. If a second place ever starts building them, the two
     will disagree and the disagreement will present as "the caller channel returned the mixed
     file", which looks like success.

  2. The rejected readings are kept on purpose. CANDIDATE_NAME_IS_FILENAME and
     CANDIDATE_NAME_IS_CHANNEL still exist, are still exercised by tests, and are documented as
     REJECTED. They are the regression guard against someone putting the channel back into `name`.

  3. Merchant ID is never sent. It is validated and displayed only. The confirmed endpoint has no
     merchant parameter.

  4. Account ID and Merchant ID are deliberately separate fields. Action::runLatestCalls()'s
     docblock records why: account 871 is a store source_id in this database and most
     order58_agents.account_id values are too, but 1119 - the example given for the latest-calls
     endpoint - is not in the store mirror at all. Guessing an equivalence would mislabel a field on
     a page whose only job is to report facts.

  5. Caller/callee are NOT Customer/Agent. See section 14.

  6. Fixtures cannot activate silently or in production. Two independent conditions, plus a second
     refusal inside FixtureRecordingSource::assertPermitted(). The environment check is a positive
     allow-list (dev or test), never "!== prod", so an unrecognised APP_ENV falls through to the
     live API - the safe direction.

  7. Digits-only ids are a security property, not a formality. They make traversal structurally
     impossible in both the URL path and the fixture filesystem path. Regexes are anchored with

  8. No response headers are echoed wholesale. Only Content-Type, Content-Disposition and
     Content-Length are kept by name. A header dump is a standing invitation to print something a
     provider decides to start sending.

28. SUMMARY
--------------------------------------------------

  * The page is a read-only, admin-only, JavaScript-free diagnostic for the client's external
    recording API at https://order58.xrainbow.com/api/external/recording. Yii 3, not Laravel.

  * Three channels: mixed (`<id>`), caller (`<id>-caller`), callee (`<id>-callee`). The suffix goes
    in the URL PATH SEGMENT. `name` is only the provider's download display name and carries no
    file extension.

  * The mixed-audio bug: before 2026-09-21 the code left the path bare (`/fetch/<id>` - the mixed
    file's own address) and put the channel into `?name=<id>-caller.wav`. The provider returned the
    mixed recording with HTTP 200 and a valid WAV header, so it read as success.

  * The fix (commit 9481fe6): switch ChannelRequestMapping::DEFAULT_CANDIDATE to
    CANDIDATE_ID_CARRIES_SUFFIX and build the path from
    RecordingChannel::requestSegmentFor(), with `name` from
    RecordingChannel::downloadNameFor() (no extension). Different path = different resource =
    correct channel.

  * There is no fallback to mixed audio anywhere, by design. A caller/callee 404 most often means
    the merchant is not on the client's separated-channels list.

  * Every outbound URL is built in exactly one file, ChannelRequestMapping.php, and a test enforces
    that.
